The Matt Pocock Skills — Workflow Map & Glossary

One system, one main flow, a spec-driven spine, and a shared vocabulary underneath.

These skills are not a pile of isolated commands. They form one main flow — idea → ship — with two on-ramps that merge onto it, and a documentation layer that runs underneath the whole thing. This page is the compressed map. Every claim traces back to the skills' own SKILL.md files (the ground truth) and the public repo.

The main flow: idea → ship

The route most work travels. You have an idea and want it built. The authoritative description lives in ask-matt, the router skill.

grill-with-docs → to-spec → to-tickets → implement → code-review
underneath, the whole way: domain-modeling writes CONTEXT.md + ADRs
  1. /grill-with-docs — sharpen the idea by relentless interview. Start here when you have a codebase. It is stateful: it retains what it learns in CONTEXT.md and ADRs. No codebase? Use /grill-me (same /grilling primitive, no paper trail).
  2. Branch — does a question need a runnable answer? If a question needs state, business logic, or a UI you must see, detour through a prototype, bridged both ways by /handoff: out → fresh session → /prototype → /handoff back.
  3. Branch — is this a multi-session build?
    • Yes → /to-spec (turn the thread into a spec), then /to-tickets to split it into tracer-bullet tickets each declaring its blocking edges. Then /implement per ticket, clearing context between each one.
    • No → /implement right here, in the same context window.
  4. Either way, /implement builds each issue by driving /tdd internally (one red-green slice at a time), then closes with /code-review — a two-axis review (Standards + Spec) of the diff — before committing.
Context hygiene — the rule that breaks most people Keep steps 1–3 (grill → spec → tickets) in one unbroken context window. Don't compact or clear until after /to-tickets — the grilling, spec, and tickets must all build on the same thinking. Each /implement then starts fresh, working from its ticket alone. The limit is the smart zone (~120k tokens). If a session nears it before /to-tickets, don't push on degraded reasoning — /handoff and continue fresh.

The two on-ramps

Starting situations that generate work, then merge onto the main flow.

  • Bugs and requests piling up → /triage. It moves issues through the five triage roles and produces agent-ready issues, which /implement later picks up.
Don't triage your own tickets Triage is only for issues you didn't create — bug reports, incoming feature requests, anything raw. Tickets that /to-tickets produced are already agent-ready. Running them through /triage is wasted work.

The spec-driven spine (your focus)

Spec-driven development is the stretch of the main flow from a sharpened idea to an agent-ready ticket. Four skills, one supporting discipline:

SkillWhat it doesProducesWhen
grill-with-docs Relentless interview that sharpens a plan/design. Edits to CONTEXT.md + ADRs as terms/decisions crystallise. Start of the flow, with a codebase.
to-spec Synthesizes the conversation into a spec/PRD. No interview — just writes what's already discussed. A spec published to the issue tracker, labelled ready-for-agent. When the idea is settled & multi-session.
to-tickets Splits the spec into tracer-bullet tickets with blocking edges. Agent-ready tickets, ordered blockers-first. Multi-session builds, after the spec.
implement Builds one ticket, driving tdd internally, then code-review. Committed, reviewed code. Per ticket, in a fresh context.
domain-modeling (underneath) The active discipline of building the glossary + recording decisions. CONTEXT.md terms; ADRs in docs/adr/. Inline, whenever a term or decision resolves.

Anatomy of a to-spec spec

From to-spec/SKILL.md. A spec has a fixed shape:

  • Problem Statement — the problem from the user's perspective.
  • Solution — the solution from the user's perspective.
  • User Stories — a long, numbered list: "As an <actor>, I want <feature>, so that <benefit>." Extensive — cover all aspects.
  • Implementation Decisions — modules, interfaces, schema, API contracts, interactions. No file paths or code snippets (they go stale). Exception: a prototype snippet that encodes a decision (state machine, schema, type shape) better than prose.
  • Testing Decisions — what makes a good test (external behaviour, not internals), which modules, prior art.
  • Out of Scope & Further Notes.
The test-seam rule Before writing the spec, sketch the seams at which you'll test the feature. Prefer existing seams to new ones. Use the highest seam possible. Fewest seams across the codebase — the ideal number is one. Confirm them with the user first.

The documentation layer (the backbone)

Two artefacts live underneath every spec-driven skill. They are created lazily — only when there's something to write — and every skill reads them before exploring.

CONTEXT.md — the glossary

From CONTEXT-FORMAT.md. It is the project's ubiquitous language and nothing else.

  • Opinionated. When several words name one concept, pick the best and list the rest under _Avoid_:.
  • Tight. One or two sentences. Define what it is, not what it does.
  • Project-specific only. General programming concepts (timeouts, error types) don't belong, even if heavily used.
  • Devoid of implementation. Not a spec, not a scratchpad, not a place for decisions.

ADRs — architectural decision records

From ADR-FORMAT.md. Live in docs/adr/, sequentially numbered (0001-slug.md). Can be a single paragraph.

Offer an ADR only when all three are true: hard to reverse · surprising without context · the result of a real trade-off. If any is missing, skip it.

What qualifies: architectural shape, integration patterns between contexts, lock-in-bearing tech choices, boundary/scope decisions, deliberate deviations from the obvious path, constraints not visible in code, non-obvious rejected alternatives.

Best-practice principles

  1. One window for grill → spec → tickets; fresh per implement. The thinking must be continuous; the building is compartmentalised.
  2. Respect the smart zone. Near ~120k tokens before to-tickets? Handoff, don't push.
  3. CONTEXT.md is a glossary, not a spec. Keep implementation out.
  4. Use the ubiquitous language everywhere. Every output (issue title, spec, test name) uses CONTEXT.md terms. Don't drift to synonyms.
  5. ADRs sparingly. Only the three criteria. Don't record the obvious or the easily reversible.
  6. Create docs lazily. No CONTEXT.md until a term resolves; no docs/adr/ until a decision earns one.
  7. Respect ADRs — don't re-litigate. Only reopen when the friction is real enough to warrant it, and say so explicitly.
  8. Fewest test seams; ideal = 1. Prefer existing seams; use the highest one.
  9. No file paths or code in specs (except decision-encoding prototypes). They go stale.
  10. Don't triage your own tickets. to-tickets output is already agent-ready.
  11. Use ask-matt as the router. When you forget which skill fits, ask the router instead of guessing.
