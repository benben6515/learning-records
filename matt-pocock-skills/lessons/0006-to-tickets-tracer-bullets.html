to-tickets — Tracer Bullets & the Frontier

The last stop of the spec-driven spine. One spec becomes a set of tickets an agent can work fresh.

In Lesson 5 you turned the conversation into a spec. to-tickets takes that spec and breaks it into tickets — each one a self-contained, demoable slice that a fresh implement session can build on its own. This is awareness level: you won't drill it until your first real multi-session build. But the mental model is small and worth holding now, because it's why Lesson 1's "fresh context per implement" rule actually works.

The one idea: a tracer bullet is a vertical slice

Each ticket cuts a narrow but complete path through every layer — schema, API, UI, tests. Vertical, not horizontal. Demoable on its own. Sized to one context window.

The word that breaks people is vertical. The instinct is to slice by layer — "do all the schema, then all the API, then all the UI." That's a horizontal slice, and it's wrong here: nothing is demoable until the very last layer lands. A tracer bullet instead goes end-to-end through all layers for a thin sliver of behaviour:

Horizontal slice (avoid)Vertical slice / tracer bullet (aim for)
"Build the whole auth schema."
Not demoable alone.		 "User can log in and see one protected page, end-to-end."
Demoable the moment it lands.
"Build the whole sidebar UI." "The menu filters its items by the permissionBits bitmask, end-to-end."
Prefactor first While slicing, look for a chance to prefactor — "make the change easy, then make the easy change." Any prefactoring becomes its own leading ticket(s) that the slices depend on.

Blocking edges & the frontier

Each ticket declares its blocking edges — the other tickets that must finish before it can start. A ticket with no blockers can start immediately. The set of currently-unblocked tickets is called the frontier, and that's always what you work:

T1 · login end-to-end
↓ blocks
T2 · menu filters by permissionBits
↓ blocks
T3 · per-role menu management
start: frontier = {T1} · after T1 closes: {T2} · after T2: {T3}

This is the bridge back to Lesson 1. Because tickets are independent vertical slices with explicit blockers, each implement can start fresh, read only its ticket, and work the frontier without clobbering other sessions. The unbroken-window rule (grill → spec → tickets) exists precisely so these edges are captured while the thinking is still warm — then the building fans out into clean, separate contexts.

The exception you should at least recognise

Not everything is a tracer bullet. A wide refactor — one mechanical change whose blast radius spans the whole codebase (rename a column, retype a shared symbol) — can't land green in a single vertical slice, because one edit breaks thousands of call sites at once. Forcing it into a tracer bullet just produces a broken build.

Wide refactor → expand–contract Don't tracer-bullet it. Sequence it: expand (add the new form beside the old, nothing breaks) → migrate the call sites in batches, each its own ticket, CI staying green because the old form still exists → contract (delete the old form once no caller remains). You only need to recognise this case for now; the mechanics come when you hit one.

How it publishes

to-tickets writes one ticket per item, in dependency order (blockers first). The shape of the edges depends on what setup-matt-pocock-skills configured for your repo:

  • Local files → one file per ticket under .scratch/<feature>/issues/NN-slug.md, "Blocked by" as text. (Your repo is on GitHub, so this isn't you — but it's the solo/no-remote path.)
  • Real tracker (GitHub, Linear…) → one issue per ticket, using the platform's native blocking / sub-issue links. This is your path. Each ticket gets the ready-for-agent label — agent-grabbable by construction, no triage.

Same rule as the spec: no file paths or code snippets in tickets (they rot) — except a decision-encoding prototype.

Your tangible win — say these out loud

  1. Define a tracer bullet in one sentence (the four properties: vertical, complete-through-all-layers, demoable, one context window).
  2. Why is a horizontal slice wrong here?
  3. What is the frontier, and why does making blocking edges explicit let each implement run fresh?
  4. Name the one case that is not a tracer bullet, and the pattern that handles it.

Awareness level — if you can answer these, you've got the model. The drill comes when you run your first real multi-session build on your own project.
