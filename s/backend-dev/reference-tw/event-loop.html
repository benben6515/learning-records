事件迴圈速查表

心智模型、四條規則、阻塞 API 黑名單，以及 30 秒就能驗證一切的 curl 指令——濃縮自第 02 課、Node 官方指南與 Philip Roberts 的經典演講。適合列印。

六步驟模型

1 · 你的 handler 在呼叫堆疊上執行              ← 一條執行緒，承載你全部的 JS
2 · 它把耗時工作交給 Node（計時器、磁碟……）
3 · handler 返回 → 堆疊清空                     ← 迴圈又能動了
4 · 耗時工作在 JavaScript 之外完成              ← OS 非同步 + libuv 執行緒池（4 條）
5 · 它的回呼在佇列裡排隊
6 · 事件迴圈把它推上堆疊                         ← 永遠只在堆疊清空時

四條規則

1 · 一次一件事

你所有的 JavaScript 都在同一個呼叫堆疊上執行。你的程式碼任何兩行之間都不會並行。

2 · I/O 在別處跑

等待發生在執行緒之外：socket／計時器走 OS 非同步 API，磁碟／DNS／加密走 libuv 執行緒池（預設 4 條）。

3 · 迴圈要等安靜

佇列裡的回呼，只在堆疊清空後執行。同步工作就是堆疊——所以它會暫停整個迴圈。

4 · 一個大戶堵住所有人

第 3 條的後果：一個忙等 while 凍結每一個請求——新的、等待中的，無一倖免。

阻塞黑名單

在 request handler 裡，這些會霸佔堆疊、拖垮整台伺服器——換成它們的非同步雙胞胎：

會堵住迴圈改用
fs.readFileSync()fs.promises.readFile()
crypto.pbkdf2Sync() 一族crypto.pbkdf2()（回呼／promise 版）
JSON.parse(超大payload)串流解析，或在 proxy 擋下 payload 上限
忙等 while／for 迴圈（CPU 工作）worker threads／工作佇列（之後的課）
災難性回溯的正規表達式用生成的輸入測試；加逾時保護

30 秒驗證

$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → 0.005s 基準

$ curl "http://localhost:3000/work?ms=3000" &   # 3 秒同步工作，背景執行
$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → ~3.0s  ← 整台伺服器被一個同步 handler 凍住了

$ curl "http://localhost:3000/idle?ms=3000" &   # 3 秒非同步等待，背景執行
$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → 0.005s ← 一樣三秒，但堆疊一直是空的

兩則備忘（日後深究）

  • 微任務會插隊。Promise 回呼（.then）會搶在下一個計時器／I/O 回呼之前消化完——MDN：Event loop。
  • 單執行緒撐 I/O，不撐 CPU。數千個同時等待：沒問題。重度運算：搬離迴圈（worker threads、child process 或佇列）。
