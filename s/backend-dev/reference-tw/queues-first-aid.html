佇列（queue）急救包

第 11 課一頁濃縮：先回應規則、三種策略、你 migrate 出來的 jobs 資料表、SKIP LOCKED 認領、工作者迴圈、202 合約，以及讓佇列變黑洞的各種坑——根基在 pg-boss，它就是這張卡穿著 README。列印我。

先回應規則（把關一切）

當你自己的結果已知就回應；回應不需要的工作，排隊。回應只報告請求本身——帳號存在了、筆記建好了。後續工作（寄信、匯出、webhook）放上持久的待辦清單，在回答之前寫下來。你在 handler 裡 await 的依賴，就是你的 endpoint 繼承的依賴——它的延遲、它的失敗、它的掛點。

三種策略

策略使用者等嗎做到一半 crash重試兩個行程
Inline await整整等完跟著請求一起失敗不行—
發後不理（fire-and-forget）不等工作遺失，無跡可尋不行不行
jobs 表 + 工作者（worker）不等那列留著，工作者接手可以可以，靠 SKIP LOCKED
Redis + BullMQ不等可以可以，外加限流、優先序、儀表板業界預設

jobs 資料表（migration 骨架）

CREATE TABLE jobs (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  type TEXT NOT NULL,                        // 挑選處理器
  payload JSONB NOT NULL DEFAULT '{}',       // 輸入，JSON 格式
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'running', 'done', 'failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at TIMESTAMPTZ,
  finished_at TIMESTAMPTZ
)

在記錄「事實」的同一個資料庫裡排隊——這就是寄件匣（outbox）的概念：發生了什麼與接下來必須發生什麼住在一起，重啟之後接得上「接下來」。

認領工作（整個協調問題，四個詞）

UPDATE jobs SET status = 'running', started_at = now()
WHERE id = (
  SELECT id FROM jobs WHERE status = 'pending'
  ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED   // 第二個工作者跳過鎖住的那列
)
RETURNING *

N 個工作者、一張表、零重複。接著：跑處理器、標記 done（或 failed——有紀錄的失敗勝過消失的 promise）、沒事做就每 500ms 輪詢一次。升級路線：LISTEN/NOTIFY 免輪詢，或 Redis 的 blocking pop。

202 合約

  • 201——資源現在存在（筆記那列已插入）。202——已受理、結果稍後：匯出還不存在，存在的是那個工作。
  • 回 202 + Location: /jobs/:id；客戶端輪詢（polling）那個 URL，直到 status 說 done。
  • 工作是有主人的資料——跟筆記同一套範圍限縮：沒登入 401、不是你的工作 403（L07 再生）。

值得現在就知道的坑

  • 回應需要的東西不准排隊。只有客戶端沒要求等的後續工作上清單。
  • 保證是至少一次（at-least-once）。在「工作做完」與「標記完成」之間 crash → 處理器再跑一次。冪等（idempotent）的處理器讓至少一次表現得像恰好一次——只說「恰好一次」是行銷術語。
  • 可見性是義務。沒有狀態 endpoint 的佇列是黑洞：工作永遠坐著 pending 而無人知曉。把 endpoint 建起來，留著。
  • 失敗需要一個故事。標記 failed、查看、手動重跑——今天這樣夠。真實系統會加重試上限與死信佇列（dead-letter queue）；那列資料早就給了失敗一個地址。
  • JSONB payload 有彈性但沒驗證。在處理器裡驗證；生產端一個錯字，會變成工作者裡的執行期驚喜。
  • setTimeout 不是儲存裝置。發後不理會在 crash 時丟工作——不可見、永遠。丟了會痛的東西，就該放進表裡。
  • 一個行程分享不了迴圈；多個行程分享得了表。當工作者搬到自己的行程、或吞吐量超過輪詢：pg-boss（同一張表，已打包）或 Redis + BullMQ（共享記憶體）。詞彙相同。
