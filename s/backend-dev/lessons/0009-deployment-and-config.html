Lesson 09 · Ops

Deployment & Config: Off the Laptop

Right now your API exists only while your Mac stays awake: localhost:3322, a Postgres in Docker on the same machine, a .env next to the code. Close the lid and the product is down. Today it moves to a machine that isn't yours — config from the environment, the database behind a public socket, HTTPS in front, and a health check that defines what "up" means.

~45 min hands-on ops

Why this lesson

Everything you built in Lessons 01–08 runs on one precondition: your laptop, awake, with Docker up. That's fine for a dev server; it's not a product. The mission said "ship it: a public URL, a real database, secured." The gap between node server7.mjs on your Mac and the same code on a server has a name — deployment — and it is mostly one idea done four ways: everything that differs between your machine and the cloud travels through the environment, never through the code.

The one idea

Config is everything that varies between environments — port, database URL, secrets — and it enters the program only through process.env, read once at boot. The same commit then runs unchanged on your laptop and in production; the environment supplies the differences (the classic statement is the twelve-factor Config principle). Deployment, in turn, is: copy the code to a supervised machine, hand it its config, put TLS in front of it, and prove it's alive with a health check.

Step 1 — the port and the URL stop being constants

Your server7 already does half of this: utils/db.mjs reads process.env.DATABASE_URL — you built that in Lesson 06. But the port is still a constant:

// server7.mjs — was: const PORT = 3322
const PORT = process.env.PORT ?? 3322

?? 3322 keeps every local habit working — no env var, same port as always. In production the platform assigns the port and hands it to you as PORT; a server that refuses to listen on it is a server that never goes live.

Locally, the environment lives in .env (still untracked — correct), and Node loads it with zero dependencies:

$ node --env-file=.env server7.mjs

One guard is still missing. pg.Pool connects lazily — with no DATABASE_URL the server boots happily and then 500s on the first request, the worst possible time to learn about it. Fail fast instead:

// top of utils/db.mjs
if (!process.env.DATABASE_URL) {
  console.error("DATABASE_URL is not set — refusing to start without a database")
  process.exit(1)
}

A missing-config error at boot is one red line in a deploy log. The same error at request time is a user staring at 500 INTERNAL. Both come from the same mistake; only the timing differs.

Step 2 — the database leaves the laptop

Your Postgres is a Docker container on the same machine as the server. One disk, one power button, one point of failure. It moves to a managed service: we're using Render's free tier — no credit card, and a free Postgres you create in two clicks. Create the database first, note the region, and take the Internal Database URL (not External): internal stays on the platform's private network — faster, and no TLS setup. External URLs work too but need ?ssl=true.

Then comes the moment your migration runner has been waiting for since Lesson 06. A fresh database replays your ledger exactly as committed — utils/migrations/*.sql, nothing else. Every hotfix you ever applied directly to the local database but never wrote back into a migration file comes back here. That is not a nuisance; it is the first honest test your ledger has ever had. (Run it and see. I read your committed 0004_auth.sql — something in there is about to meet you.)

Push to main and Render rebuilds and redeploys automatically — git push is the deploy button. Watch the first deploy's logs: npm install, your own migration runner printing applying 0001_init.sql…, then your own line: server is running. Same code, different machine. That's the whole trick.

Two things Render sets for you: PORT (Step 1 made your server listen on it) and NODE_ENV=production — you'll use that one in Step 5.

Step 4 — what "up" means: the health check

The process running is not the service working. The pool could be dead, DNS could lie, the database could be restarting. "Up" is a claim, and claims need evidence:

async function health(_req, res) {
  try {
    await pool.query("SELECT 1")                     // deepest dependency, cheapest probe
    return json(res, 200, { ok: true })
  } catch {
    return fail(res, 503, "UNHEALTHY", "database unreachable")
  }
}

// routes:
{ method: "GET", pattern: "/health", handler: health },

Note what it checks: not "did the file load" but "can I reach the thing I cannot work without." Set Health Check Path to /health in the service settings — now the platform polls it, treats a failing deploy as a failed deploy, and a crashing process gets restarted by the platform's supervisor. That supervisor is the part a PaaS does for you: on a VPS you'd write it yourself as a systemd unit or pm2. The drill includes crashing your own server on purpose to watch it come back.

Free-tier honesty: the instance sleeps after ~15 minutes without traffic, and the first visitor after that waits ~1 minute for the cold start. The health check doesn't prevent sleep — it prevents lying. Fine for a course API; a paid instance is the fix when it matters.

Step 5 — HTTPS and the Secure flag

Your URL is https:// from the first second. You wrote no TLS code — Render terminates TLS at its edge: browser ↔ Render is HTTPS with a real certificate (Let's Encrypt, auto-renewed), and inside the private network Render speaks plain HTTP to your process. TLS termination = decryption happens at the proxy, not in your code. Same shape as nginx or Caddy in front of a VPS — a thing you'll configure by hand someday, consumed as a feature today.

HTTPS earns you the last cookie flag. L07's session cookie is HttpOnly; SameSite=Lax — add Secure so the browser refuses to ever send it over plain HTTP:

const SECURE = process.env.NODE_ENV === "production" ? "; Secure" : ""

return json(res, 200, { id: user.id, email: user.email }, {
  "set-cookie": `sid=${sid}; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800${SECURE}`,
})

Why conditional? On localhost there is no TLS — a Secure cookie would never be sent back, and local login would silently break. One more decision that lives in the environment, not in a second version of the code.

Four things to notice

  • Nothing about your handlers changed. Routing, auth, validation — all of it deployed as-is. That's Lessons 01–08 paying off: code that never depended on localhost deploys without fear.
  • The deploy replays your history. Fresh machine: npm install from package-lock.json, schema from the migration ledger. Anything that exists only on your laptop (a hand-fixed column, a table you dropped in psql) does not exist in production. The repo is the source of truth, or nothing is.
  • Secrets are dashboard data, not repo data. DATABASE_URL is a credential — anyone who reads it can read your users' notes. It lives in Render's env settings; the repo holds only the knowledge that it must exist (and if it ever leaks: rotate it, one click, redeploy).
  • Your tests deploy with you. The L08 suite speaks plain HTTP — point it at the production URL and it audits the live contract, not a local copy.
