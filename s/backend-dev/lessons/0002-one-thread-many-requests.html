Lesson 02 · The event loop

One Thread, Many Requests

Your Lesson 01 server is one JavaScript function — and it can still serve hundreds of requests at once. Today you'll watch the trick work, then watch it break.

~30 min hands-on Node.js

Why this lesson

The mission says no layer is magic. Last lesson you built the server; today you meet the engine that calls your function. This is the difference between "I use async/await" and "I know why the whole API froze for three seconds when one user uploaded a big file."

The one idea

Your JavaScript runs on one call stack — one thread. The expensive work doesn't. Timers, disk, sockets, DNS: Node hands those to the operating system and a small worker pool (libuv, bundled with Node). When the work finishes, its callback queues up, and the event loop pushes it back onto the stack — but only once the stack is empty.

1 · your handler runs on the stack → 2 · asks Node for slow I/O → 3 · handler returns, stack empties
4 · I/O finishes off-thread → 5 · callback waits in the queue → 6 · loop runs it on the stack

You already know this model — it's the browser's event loop, moved server-side (MDN: Event loop). Same single stack, same queue. Node just points it at sockets and disks instead of the DOM.

The four rules

  1. One at a time. All your JS executes on one call stack.
  2. I/O runs elsewhere. The waiting happens off-thread (OS async APIs + libuv's pool, 4 threads by default).
  3. The loop waits for quiet. A queued callback only runs when the stack is empty.
  4. So one sync hog blocks everyone. A 3-second synchronous loop freezes every request — new and pending. That's not a bug in Node; it's rule 3 doing exactly what it says (Node official: The Node.js Event Loop).
Why this scales

For I/O-bound work, the CPU idles through every wait — so one thread plus async I/O handles thousands of simultaneous waits. The trade: for CPU-heavy work (image processing, big JSON, crypto), one thread is a bottleneck, and the fix is worker threads or a queue — a later lesson.

The code — three endpoints, one truth

Save as server2.mjs next to Lesson 01's file:

import { createServer } from "node:http";

const server = createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");

  // GET /hello — instant, pure sync, microseconds
  if (req.method === "GET" && url.pathname === "/hello") {
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ msg: "hello" }));
    return;
  }

  // GET /work?ms=3000 — 3s of SYNCHRONOUS CPU work. Blocks the whole server.
  if (req.method === "GET" && url.pathname === "/work") {
    const ms = Number(url.searchParams.get("ms") ?? 3000);
    const start = Date.now();
    while (Date.now() - start < ms) {}   // busy-wait: the event loop is frozen
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ blockedForMs: Date.now() - start }));
    return;
  }

  // GET /idle?ms=3000 — 3s of ASYNCHRONOUS waiting. Blocks nobody.
  if (req.method === "GET" && url.pathname === "/idle") {
    const ms = Number(url.searchParams.get("ms") ?? 3000);
    setTimeout(() => {
      res.writeHead(200, { "content-type": "application/json" });
      res.end(JSON.stringify({ waitedMs: ms }));
    }, ms);                              // timer runs outside JS; we return now
    return;
  }

  res.writeHead(404);
  res.end();
});

server.listen(3000, () => console.log("listening on http://localhost:3000"));

The only difference between /work and /idle is where the three seconds happen: on the stack, or off it. Same latency, opposite blast radius.

The drill — watch it break, watch it hold

Hands-on · two terminals, three seconds, one revelation

Timing is the feedback: -w "%{time_total}" prints how long each request took. Watch the numbers, not the code.

  • Save and start: node server2.mjs — then baseline: curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello → a few milliseconds
  • Terminal A: curl "http://localhost:3000/work?ms=3000" (3s of sync work — don't press anything)
  • Immediately, terminal B: time /hello again → ~3 seconds. The whole server froze behind one request
  • Now the fix: terminal A: curl "http://localhost:3000/idle?ms=3000" (3s of async wait)
  • While it waits, terminal B: time /hello → milliseconds. Same 3 seconds, zero collateral
  • Explain out loud, in one sentence each: why did step 3 stall? Why didn't step 5? (If you can say it, you own rule 3)
What you just proved

"Node is fast because it's async" is a slogan. You now have the mechanism: async means the stack empties, so the loop can keep serving. Any sync code that hogs the stack — while loops, fs.readFileSync, JSON.parse on a 100 MB payload, crypto.pbkdf2Sync — suspends every other request in the building.

Fine print for later: promise callbacks (.then) are microtasks — they jump ahead of timers. That ordering matters once you mix them; the official event-loop guide covers it when you're ready.
