Lesson 08 · Testing

Testing the API: Red, Green, Refactor

Your server7 shipped two real bugs past both of us — a one-character drift in getSid, and read endpoints that lost their ownership guard in your refactor. The curl drills never noticed, because drills only check what you remembered to try. Today: node --test, zero new dependencies, and the tests that catch exactly those two bugs.

~40 min hands-on quality

Why this lesson

Nothing in Lessons 01–07 verifies itself. You ran curls, saw 200s, felt good — and two bugs sailed through: startsWith("sid") instead of startsWith("sid=") (you found that one last lesson), and getNoteById answering 200 to a stranger reading your note, because the refactor into utils/ dropped the guard. I only found them because I read your code. Tests are how code gets read every time it changes, by a machine that never gets tired of checking.

The one idea

A test is a function that runs your code with a chosen input and asserts the output — written to fail loudly the moment behavior drifts. The habit around it is three beats (Fowler: TDD): write the test and watch it fail (red — it must fail first, or it tests nothing), make it pass the simplest honest way (green), then clean up (refactor) with the test standing guard.

Step 1 — the decoy test kills the one-character bug

First, testability: getSid moves into utils/index.mjs with an export. Then the test — note its shape: arrange, act, assert, one behavior, a name that reads like a sentence:

// utils/get-sid.test.mjs
import test from "node:test";
import assert from "node:assert/strict";
import { getSid } from "./index.mjs";

test("returns the sid when a decoy cookie merely starts with sid", () => {
  const req = { headers: { cookie: "sidebar=hide; sid=the-real-one" } };   // arrange
  assert.equal(getSid(req), "the-real-one");                               // act + assert
});

test("returns undefined when no cookie header exists", () => {
  assert.equal(getSid({ headers: {} }), undefined);
});

Run it against the buggy version — the failure is the lesson, so look at it:

$ node --test utils/get-sid.test.mjs
✖ returns the sid when a decoy cookie merely starts with sid
    AssertionError: Expected values to be strictly equal:
    + actual: 'bar=hide'          // ← the decoy cookie, half-sliced
    expected: 'the-real-one'

sidebar=hide starts with sid, so .find() grabs it and slice(4) returns bar=hide as your session id. Fix the one character — startsWith("sid=") — and the suite goes green. You knew the bug; now it cannot come back: any future edit that drifts those four characters turns the build red in 40 ms.

Step 2 — testability is a design property

Those curls you typed by hand? They were tests — slow, manual, forgettable. The server just needs one accommodation: don't listen at import time, export a start instead:

// bottom of server7.mjs — was: app.listen(3322, …)
export function start(port = 3322) {
  return new Promise((resolve) => app.listen(port, () => resolve(app)));
}

start(0) asks the OS for an ephemeral port — tests can run in parallel, and never fight your dev server for 3000/3322.

Step 3 — the integration test: your whole contract, through real HTTP

Node has global fetch and node --test — no supertest, no jest, nothing to install (node:test docs). This one file pins L04's and L07's promises at once:

// api.test.mjs — integration: real HTTP, real Postgres, real contract
import test from "node:test";
import assert from "node:assert/strict";
import { start } from "./server7.mjs";

let app, base;
const api = (path, opts = {}) => fetch(base + path, opts);
const post = (path, body, cookie) => api(path, {
  method: "POST",
  headers: { "content-type": "application/json", ...(cookie ? { cookie } : {}) },
  body: JSON.stringify(body),
});

test("the notes contract, through real HTTP", async () => {
  app = await start(0);                                 // ephemeral port
  base = `http://localhost:${app.address().port}`;
  const mail = `t${Date.now()}@x.dev`;                  // unique per run — no cleanup fixtures needed

  assert.equal((await post("/auth/register", { email: mail, password: "correct horse" })).status, 201);
  assert.equal((await post("/auth/register", { email: mail, password: "x" })).status, 409);

  const wrong = await post("/auth/login", { email: mail, password: "WRONG" });
  const ghost = await post("/auth/login", { email: "ghost@x.dev", password: "WRONG" });
  assert.equal(wrong.status, 401);
  assert.equal(await wrong.text(), await ghost.text());          // identical bodies — no enumeration

  const ok = await post("/auth/login", { email: mail, password: "correct horse" });
  assert.equal(ok.status, 200);
  const cookie = ok.headers.getSetCookie()[0].split(";")[0];     // "sid=…"

  const created = await post("/notes", { title: "from a test" }, cookie);
  assert.equal(created.status, 201);
  assert.ok(created.headers.get("location"));

  // a stranger, fully logged in, asks for that note →
  const stranger = await post("/auth/register", { email: `s${Date.now()}@x.dev`, password: "p" });
  const sLogin = await post("/auth/login", { email: (await stranger.json()).email, password: "p" });
  const sCookie = sLogin.headers.getSetCookie()[0].split(";")[0];
  assert.equal((await api(`/notes/${(await created.json()).id}`, { headers: { cookie: sCookie } })).status, 403);

  assert.equal((await post("/auth/logout", {}, cookie)).status, 204);
  assert.equal((await api("/auth/me", { headers: { cookie } })).status, 401);
});

test.after(() => app?.close());

What happened when I ran it against your server7

200 !== 403. The stranger read the note. Your refactor into utils/ had quietly dropped getUser and the ownership check from getNoteById — anyone, not even logged in, could read any note by id. That's an IDOR vulnerability (Insecure Direct Object Reference), the exact missing-WHERE family Lesson 07 warned about, sitting in code whose curls all returned 200. The fix is the guard you already know:

async function getNoteById(req, res, p) {
  const me = await getUser(req);
  if (!me) return fail(res, 401, "UNAUTHENTICATED", "log in first");
  const note = await q.get(Number(p.id));
  if (!note) return fail(res, 404, "NOT_FOUND", "note not found");
  if (note.user_id !== me.id) return fail(res, 403, "FORBIDDEN", "not your note");
  return json(res, 200, note);
}

…and the suite goes pass 4, fail 0. Check your own getNotes list handler too — same refactor, same risk.

Four things to notice

  • Red first, or it tests nothing. I re-broke getSid after fixing it (a mutation check) and watched the decoy test fail again — proof the test has teeth. A test that has never failed is a test that has never worked.
  • Unit vs integration is a zoom level. The decoy test pins one function in milliseconds; the API test pins the whole contract (auth, cookies, status codes, ownership) in ~600 ms. You need both: the API test caught the 403 hole the unit test can't see; the unit test names the exact line when it breaks (Fowler: test pyramid).
  • Tests are documentation that executes. A new teammate reads get-sid.test.mjs and knows exactly what getSid promises — decoys included — without opening your head.
  • Every bug becomes a test. Both of today's bugs are now permanently fenced. That's the long game: your suite is a list of every way this code has ever been wrong, each with a tripwire on it.

The drill — fence your own codebase

Hands-on · red, green, and the mutation game
  • Move getSid into utils/index.mjs with export; write get-sid.test.mjs with the decoy test; run node --test utils/get-sid.test.mjs — if your bug is still there, savor the red, then fix and go green
  • Add export function start(port) to server7 (replacing bare app.listen); confirm node server7.mjs-style runs still work via a tiny start(3322) call at the bottom
  • Write api.test.mjs from the listing; run the full suite: node --test — expect the stranger test to fail 200 !== 403 if your handlers still lack the guard
  • Fix the read path (guard + ownership, as above); audit getNotes/postNote/deleteNoteById for the same dropped-guard disease; suite to fail 0
  • Mutation game: deliberately re-break something (delete the 403 line, or flip sid= back) → watch the exact test go red → revert. Feel what the safety net catches
  • Grow the fence: add tests for PUT idempotency (second identical PUT → 200), 405 + Allow on a wrong verb, bad JSON → 400, and note-list scoping (stranger's list is [])
  • Make it a habit: add "test": "node --test" to package.json scripts; from now on, the loop for any change is red → green → refactor
