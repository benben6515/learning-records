Lesson 05 · Persistence I

Persistence I: Files → SQLite

Your notes die with the process. First fix: write the whole store to a JSON file — it works, until you see its three cracks. Real fix: SQLite — a database in one file, built into Node, that keeps your Lesson-04 contract intact while your data starts surviving restarts.

~40 min hands-on data

Why this lesson

Everything so far lived in a Map — restart the server and it's empty. "Just write it to a file" is the obvious fix, and it's a great teacher, because it almost works. Today: implement the file version, break it on paper, then swap the engine to SQLite via Node's built-in node:sqlite — zero npm installs, same API contract, durable data. PostgreSQL arrives next lesson, once SQLite has earned its limits honestly.

The one idea

A database is a file plus a protocol for writing it safely and asking it questions. Nothing more mystical. Today you watch that sentence become true: notes.db is literally one file on disk (ls it in the drill) — but the SQLite protocol gives you atomic writes, crash safety, and a query language. A raw JSON file gives you none of the three.

Step 1 — the 10-minute fix that almost works

Patch server4.mjs with file persistence — load on boot, save after every write:

import { readFileSync, writeFileSync } from "node:fs";   // top of file

// boot: read the file (or start empty on first run)
const notes = new Map(
  JSON.parse(readFileSync("notes.json", "utf8") || "[]").map((n) => [n.id, n])
);
const save = () => writeFileSync("notes.json", JSON.stringify([...notes.values()]));

// then call save() at the end of POST / PUT / DELETE handlers

Run it: create a note, Ctrl-C, start again — the note survives. Genuine progress. Now the three cracks, and why every one of them is a protocol problem, not a code bug:

  1. Crash mid-write. writeFileSync rewrites the whole file. Die halfway (disk full, kill -9, deploy) and notes.json is truncated garbage — your next boot crashes on JSON.parse. A database writes to a journal first, then flips — atomic even when killed (node:fs docs have no answer for this).
  2. Lost updates. Two requests, two whole-file rewrites — the second overwrites the first's note. Your event loop is single-threaded, but the file is the shared state; anyone else touching it (a second process, a script, you in an editor) races you.
  3. No questions. "Notes containing milk, newest first" = load everything into JS and filter. No WHERE, no indexes, no pagination. The instant data grows, this design dies.

Step 2 — server5.mjs: same contract, SQLite engine

Node 22.5+ ships SQLite built in — DatabaseSync, no npm, no flags on Node 23+. The swap touches only the data layer; routing, dispatch, 405s, and the error contract are byte-for-byte Lesson 04's:

import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";

// ——— the database: one file, notes.db — schema is the data's contract (L04 echo) ———
const db = new DatabaseSync("notes.db");
db.exec(`
  CREATE TABLE IF NOT EXISTS notes (
    id         INTEGER PRIMARY KEY,             // SQLite assigns it, like nextId++ did
    title      TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now'))
  )
`);

// ——— prepared statements: the ? keeps data OUT of the SQL text ———
const q = {
  list:   db.prepare("SELECT id, title, created_at FROM notes ORDER BY id"),
  get:    db.prepare("SELECT id, title, created_at FROM notes WHERE id = ?"),
  has:    db.prepare("SELECT 1 FROM notes WHERE id = ?"),
  insert: db.prepare("INSERT INTO notes (title) VALUES (?) RETURNING id, title, created_at"),
  upsert: db.prepare(`INSERT INTO notes (id, title) VALUES (?, ?)
                      ON CONFLICT(id) DO UPDATE SET title = excluded.title
                      RETURNING id, title, created_at`),
  del:    db.prepare("DELETE FROM notes WHERE id = ?"),
};

// ——— helpers, route table, dispatch: unchanged since Lesson 04 ———
// (readBody, parseJson, json, fail, toRegex, compiled, the 405 loop — copy from server4.mjs)

const routes = [
  { method: "GET", pattern: "/notes", handler: (req, res) =>
      json(res, 200, q.list.all()) },

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const created = q.insert.get(note.title);   // SQLite mints the id
      return json(res, 201, created, { location: `/notes/${created.id}` });
  } },

  { method: "GET", pattern: "/notes/:id", handler: (req, res, p) => {
      const note = q.get.get(Number(p.id));
      if (!note) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 200, note);
  } },

  { method: "PUT", pattern: "/notes/:id", handler: async (req, res, p) => {
      const id = Number(p.id);
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const existed = !!q.has.get(id);
      q.upsert.get(id, note.title);               // write to THE id in the URL — still idempotent
      return json(res, existed ? 200 : 201, { id, title: note.title }, { location: `/notes/${id}` });
  } },

  { method: "DELETE", pattern: "/notes/:id", handler: (req, res, p) => {
      if (q.del.run(Number(p.id)).changes === 0) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 204);
  } },
];

// … dispatch (path-then-method, 405 + Allow, error net) — identical to server4.mjs

Four things to notice

  • INTEGER PRIMARY KEY replaces nextId++. SQLite's rowid machinery assigns ids at insert — one less thing to own, and it can't collide. And the L04 semantics survive the engine swap untouched: POST's id is still server-minted (not idempotent); PUT still writes to the id in the URL via ON CONFLICT … DO UPDATE (idempotent — an upsert).
  • The ? is the whole SQL-injection defense. Data travels as a parameter, never inside the SQL text — so a title of a"); DROP TABLE notes;-- is stored as literal text (I tested it: 201, table intact). The moment you interpolate — db.prepare(\`… VALUES ('${title}')\`) — that title executes. Never concatenate, anywhere, in any language (OWASP: SQL Injection).
  • Prepared once, run forever. db.prepare() parses and plans the SQL once; .get()/.all()/.run() reuse the plan with new params. One line per statement in the q object = your data access layer, whole (node:sqlite docs).
  • The schema is a contract — L04's idea, applied to data. title TEXT NOT NULL is the DB-level twin of our 400 validation; DEFAULT (datetime('now')) is behavior we no longer write. Invalid data can't get in, no matter which bug tries to put it there (SQLite language docs).

The drill — watch data survive you killing it

Hands-on · durability, upsert, injection, the file itself
  • Check your Node: node --version — need 23+ for flag-free node:sqlite (22.5+ works with --experimental-sqlite; I verified on v26)
  • Build server5.mjs (server4 + the data layer above), start it: node server5.mjs
  • Create: curl -i -X POST -H "content-type: application/json" -d '{"title":"buy milk"}' http://localhost:3000/notes → 201 — notice created_at you never wrote code for
  • The win: Ctrl-C the server, restart node server5.mjs, curl http://localhost:3000/notes → still there
  • See the file: ls -la notes.db — one 8 KB file is the entire database; sqlite3 notes.db ".schema" shows your contract
  • Query it directly: sqlite3 notes.db "SELECT id, title FROM notes WHERE title LIKE '%milk%'" — questions answered by the engine, not by loading everything into JS (sqlite3 CLI docs)
  • Injection, live: curl -X POST -H "content-type: application/json" -d '{"title":"a\"); DROP TABLE notes;--"}' http://localhost:3000/notes → 201; list the notes — the attack is now just a silly title, stored harmlessly
  • Contract regression: rerun L04's checks — PUT /notes/7 twice (201 then 200), wrong verb 405, bad JSON 400 — engine swapped, contract unchanged
  • Reset: rm notes.db and restart — empty but functional. You now know exactly what "the database" is: a file your protocol owns
