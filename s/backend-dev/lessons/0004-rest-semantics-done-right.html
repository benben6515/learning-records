Lesson 04 · REST semantics

REST Semantics Done Right

Your Lesson-03 API works — but it answers 404 for a wrong method and 500 for the client's own bad JSON. Today the contract gets tight: 405 + Allow, idempotent PUT, 201 + Location, and one error shape the frontend can switch on.

~30 min hands-on API design

Why this lesson

Anyone can emit JSON. What separates an API a frontend team can trust from a function that returns strings is semantics: methods with fixed meanings, status codes that tell the truth, and errors a machine can branch on. Today you upgrade server3.mjs → server4.mjs with four upgrades, each ~5 lines. None of them are Express features you "get" — they're decisions you make.

The one idea

HTTP is a contract, and its verbs come with legally fixed meanings. Two properties define every method (MDN's method table · RFC 9110 §9.2.2):

MethodSafe (read-only)?Idempotent (retry-safe)?Success codes
GETyesyes200
POSTnono201 (+Location)
PUTnoyes200 replace / 201 create
DELETEnoyes204

Safe = calling it changes nothing. Idempotent = calling it N times leaves the same state as calling it once. That word — 冪等 — is the whole lesson: it's what makes retries, refreshes, and flaky networks survivable. Retry an idempotent call: harmless. Retry a POST: duplicate charge, duplicate signup, duplicate note.

The code — server4.mjs, four upgrades

Start from server3.mjs (Lesson 03). The new lines are marked L04; everything else you already own:

import { createServer } from "node:http";

// ——— the data (in-memory for now; persistence is Lesson 05) ———
const notes = new Map();
let nextId = 1;

// ——— helpers ———
function readBody(req) {
  return new Promise((resolve) => {
    let body = "";
    req.on("data", (c) => (body += c));
    req.on("end", () => resolve(body));
  });
}

// L04 (1/4): null instead of a throw — so bad JSON can become a 400, not a 500
const parseJson = (raw) => {
  try { return JSON.parse(raw || "{}"); } catch { return null; }
};

function json(res, status, data, headers = {}) {
  res.writeHead(status, { "content-type": "application/json", ...headers });
  res.end(data === undefined ? "" : JSON.stringify(data));
}

// L04 (2/4): the error contract — every failure answers this exact shape
function fail(res, status, code, message, headers = {}) {
  json(res, status, { error: { code, message } }, headers);
}

// ——— the route table ———
const routes = [
  { method: "GET", pattern: "/notes", handler: (req, res) =>
      json(res, 200, [...notes.values()]) },

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      note.id = nextId++;               // server picks the id → not idempotent
      notes.set(note.id, note);
      return json(res, 201, note, { location: `/notes/${note.id}` });  // L04 (3/4)
  } },

  { method: "GET", pattern: "/notes/:id", handler: (req, res, p) => {
      const note = notes.get(Number(p.id));
      if (!note) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 200, note);
  } },

  { method: "PUT", pattern: "/notes/:id", handler: async (req, res, p) => {
      const id = Number(p.id);
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const existed = notes.has(id);
      note.id = id;                     // client picks the id → replace-or-create
      notes.set(id, note);              // same request twice → same state. idempotent.
      return json(res, existed ? 200 : 201, note, { location: `/notes/${id}` });
  } },

  { method: "DELETE", pattern: "/notes/:id", handler: (req, res, p) => {
      if (!notes.delete(Number(p.id))) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 204);
  } },
];

// "/notes/:id" → /^\/notes\/(?<id>\d+)\/?$/
const toRegex = (pattern) =>
  new RegExp("^" + pattern.replace(/:(\w+)/g, "(?<$1>\\d+)") + "/?$");

const compiled = routes.map((r) => ({ ...r, regex: toRegex(r.pattern) }));

// ——— L04 (4/4): dispatch — match the PATH first, then the method ———
// that order is what unlocks 405: you must know the path exists to say "wrong verb"
const server = createServer(async (req, res) => {
  const { pathname } = new URL(req.url, "http://localhost");
  console.log(`${req.method} ${pathname}`);
  try {
    const allowed = new Set();          // every method that knows this path
    for (const route of compiled) {
      if (!route.regex.test(pathname)) continue;
      allowed.add(route.method);
      if (req.method !== route.method) continue;
      const match = pathname.match(route.regex);
      return await route.handler(req, res, match.groups ?? {});
    }
    if (allowed.size) {                 // path exists, method doesn't
      const allow = [...allowed].sort().join(", ");
      return fail(res, 405, "METHOD_NOT_ALLOWED", `allowed: ${allow}`, { allow });
    }
    return fail(res, 404, "NOT_FOUND", "no such path");
  } catch (err) {                       // the error net (Lesson 03)
    console.error(err);
    fail(res, 500, "INTERNAL", "internal error");
  }
});

server.listen(3000, () => console.log("listening on http://localhost:3000"));

Three things to notice

  • Idempotency isn't a keyword — it's where the id comes from. POST lets the server assign nextId++, so an identical retry creates a second note. PUT writes to the id in the URL, so an identical retry lands on the same entry. Same Map, opposite semantics — the verb promises the behavior, and your code must keep the promise (RFC 9110 §9.2.2).
  • 405 needs two questions, in order. "Does any route know this path?" (collect them in the allowed Set) — then "does one accept this method?" Path yes + method no → 405 + an Allow header telling the client what would have worked. Path no → 404. Answering 404 for a wrong verb hides a route that actually exists (MDN: 405).
  • 4xx means "caller's fault", 5xx means "your fault". Malformed JSON is the client's mistake — Lesson 03 answered 500 (and logged a scary stack for a non-bug); the contract-correct answer is 400. Reserve 500 for the truly unexpected, and give every error the same { error: { code, message } } shape so the frontend can switch (body.error.code) instead of string-matching messages (MDN: HTTP status).

The drill — prove each upgrade on curl

Hands-on · 405, Location, idempotency, error contract
  • Save as server4.mjs, start it: node server4.mjs
  • Wrong verb: curl -i -X PUT http://localhost:3000/notes → 405 + allow: GET, POST (Lesson 03 said 404 here — spot the difference)
  • Create: curl -i -X POST -H "content-type: application/json" -d '{"title":"first"}' http://localhost:3000/notes → 201 + location: /notes/1; run it again → 201 with a new id — POST is not idempotent, on purpose
  • Idempotency: curl -i -X PUT -H "content-type: application/json" -d '{"title":"put one"}' http://localhost:3000/notes/7 → 201; the exact same PUT again → 200; curl http://localhost:3000/notes → still exactly one note 7
  • Retry story: imagine the network ate the PUT response and your frontend retried. Say out loud why that's safe — and why the same story with POST is a duplicate note
  • Bad JSON, upgraded: curl -i -X POST -d '{oops' http://localhost:3000/notes → 400 BAD_JSON, no stack trace in the log (Lesson 03 answered 500 here)
  • Contract check: make three different mistakes (wrong verb, unknown path, empty body) — confirm every response is the same { "error": { "code", "message" } } shape, only the code changes
  • Read the MDN method table — find the safe/idempotent columns and check them against your server's actual behavior
The status-code dialect (so far)

The 4xx/5xx split is a debugging compass: 4xx → reproduce with the client's request; 5xx → read your server log. (401/403 join in Lesson 06 — auth.)
