Lesson 11 · Architecture

Queues: Respond First, Work Later

Your handlers have obeyed one rule since Lesson 03: finish all the work, then answer. Today we break the rule deliberately — bolt a fake two-second welcome email onto register and watch latency and failure couple. Then we fix it for real: a jobs table in Postgres (the outbox idea), an in-process worker, a 202, and one clause — FOR UPDATE SKIP LOCKED — that lets many workers share one queue without doing anything twice.

~40 min hands-on architecture

Why this lesson

Every endpoint you've built answers only after its work is done. For queries, right. But real services accumulate work the response doesn't need: welcome emails, CSV exports, webhooks, thumbnail generation. That work charges two taxes. Latency — the user waits for SMTP because the await sits in the handler. Coupling — when the email service is down, registration is down too, because they share a try/catch. And there's a hidden third: loss — crash mid-email and the work is gone, with no record it ever existed. One move fixes all three: respond when your outcome is known; put the rest on a durable to-do list.

The one idea

A queue decouples accepting work from completing it. The response reports on the request's outcome — the note was created, the account exists. Follow-up work goes on a to-do list the request writes down before answering, and a worker drains it whenever it drains it. Durable means a row in Postgres — the same insight that made your notes survive restarts in Lesson 05 — not a setTimeout in memory. HTTP even has vocabulary for this: 202 Accepted, the missing member of your L04 status family.

Step 1 — feel the pain (measure, as always)

The fake SMTP call — slow, like the real one:

const sleep = (ms) => new Promise(r => setTimeout(r, ms))

async function sendWelcomeEmail(email) {
  await sleep(2000)                       // fake SMTP: slow on purpose
  console.log(`📧 welcome email sent to ${email}`)
}

Bolt it onto register, awaited:

const u = (await pool.query(
  "INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email",
  [body.email, await hashPassword(body.password)]
)).rows[0]
await sendWelcomeEmail(u.email)           // ← the two seconds live here
return json(res, 201, u)

curl -w '%{time_total}\n' on register: single-digit milliseconds becomes 2.0 seconds. And npm test crawls — the suite registers three users per run. Six seconds of pure waiting, added by one line.

Step 2 — the coupling tax

Latency is the polite tax. Flip a SMTP_DOWN flag so the fake email throws, and register answers 500 INTERNAL — after the INSERT already ran. The SQL was fine, the password was fine, the user row exists — but the client saw a 500, concluded the signup failed, and the retry gets 409 EMAIL_TAKEN. Ghost account, from one badly placed await. Two failure domains now share one status code, and your L08 contract can't tell them apart. A dependency you await inside a handler is a dependency your endpoint inherits.

Step 3 — fire-and-forget, and its three cracks

The naive fix is one deleted word:

sendWelcomeEmail(u.email).catch(console.error)   // launch, don't wait

Fast again — single-digit milliseconds, suite snappy, failures logged instead of thrown. This pattern has a name, fire-and-forget, and it's L05's file-based persistence all over again: works until it doesn't, then cracks three ways.

  • Crash loses the work. Kill the server inside the 2-second window: the pending promise dies with the process. No email, and no record an email was ever owed. A setTimeout is not storage.
  • Invisible. "Did user X's welcome email send?" has no answer anywhere — no status, no list, no timestamp. Debugging by vibes.
  • No retry. A transient SMTP hiccup swallows the email forever. Fire once, forget permanently.

Step 4 — the jobs table (the outbox idea)

What made notes survive restarts? A row. Same trick for work. Migration 0005_jobs.sql:

CREATE TABLE jobs (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  type TEXT NOT NULL,
  payload JSONB NOT NULL DEFAULT '{}',
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'running', 'done', 'failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at TIMESTAMPTZ,
  finished_at TIMESTAMPTZ
)

Everything here is a L06 callback: IDENTITY ids, TIMESTAMPTZ, a CHECK constraint as contract. type picks the handler; payload carries the input as JSONB; status is the four-word lifecycle. Register swaps the await for an insert:

const u = (await pool.query(
  "INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email",
  [body.email, await hashPassword(body.password)]
)).rows[0]
await pool.query(
  "INSERT INTO jobs (type, payload) VALUES ('welcome_email', $1)",
  [JSON.stringify({ email: u.email })]
)
return json(res, 201, u)

The response is unchanged — 201, single-digit milliseconds — but the intention is now written down next to the fact, in the same trustworthy database. That's the outbox idea: record what happened and what must happen next, so a restart can pick up the "next" part. (Stretch: wrap both inserts in one transaction, L06-style, so there's never a user without a job.)

Step 5 — the worker

A loop in the same process: claim a pending job, run its handler, mark the result. L02 taught you the loop; this one wears a uniform:

const handlers = {
  welcome_email: async (payload) => {
    await sleep(2000)                     // the same fake SMTP — unchanged
    console.log(`📧 welcome to ${payload.email}`)
  },
  export_notes: async (payload) => {
    await sleep(1000)                     // fake CSV build
    console.log(`📦 notes exported for user ${payload.userId}`)
  },
}

async function tick() {
  const { rows } = await pool.query(`
    UPDATE jobs SET status = 'running', started_at = now()
    WHERE id = (
      SELECT id FROM jobs WHERE status = 'pending'
      ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
    )
    RETURNING *`)
  return rows[0] ?? null
}

async function runWorker(name = "w1") {
  for (;;) {
    const job = await tick()
    if (!job) { await sleep(500); continue }        // idle: poll every 500ms
    console.log(`${name} claimed job #${job.id} (${job.type})`)
    try {
      await handlers[job.type](job.payload)
      await pool.query("UPDATE jobs SET status = 'done', finished_at = now() WHERE id = $1", [job.id])
    } catch (err) {
      console.error(err)
      await pool.query("UPDATE jobs SET status = 'failed', finished_at = now() WHERE id = $1", [job.id])
    }
  }
}
runWorker()

The clause doing the heavy lifting: FOR UPDATE SKIP LOCKED. The inner SELECT locks the row it's about to claim; a second worker's identical query skips that locked row and takes the next one. N workers, one table, zero double-work — the entire coordination problem in four words. (pg-boss, a real Postgres queue, is essentially this query wearing a README.) And failed is now a recorded, visible state — a lost promise never gave you that.

Step 6 — 202, and the status endpoint

Crack #2 was invisibility. Fix it with two endpoints — and notice how much of this course shows up in twenty lines:

async function postExport(req, res) {
  const me = await getUser(req)
  if (!me) return fail(res, 401, "UNAUTHENTICATED", "log in first")
  const { rows } = await pool.query(
    "INSERT INTO jobs (type, payload) VALUES ('export_notes', $1) RETURNING id",
    [JSON.stringify({ userId: me.id })]
  )
  return json(res, 202, { id: rows[0].id, status: "pending" },
    { location: `/jobs/${rows[0].id}` })
}

async function getJobById(req, res, p) {
  const me = await getUser(req)
  if (!me) return fail(res, 401, "UNAUTHENTICATED", "log in first")
  const { rows } = await pool.query("SELECT * FROM jobs WHERE id = $1", [Number(p.id)])
  const job = rows[0]
  if (!job) return fail(res, 404, "NOT_FOUND", "no such job")
  if (job.payload.userId !== me.id) return fail(res, 403, "FORBIDDEN", "not your job")
  return json(res, 200, job)
}

// routes:
{ method: "POST", pattern: "/exports", handler: postExport },
{ method: "GET", pattern: "/jobs/:id", handler: getJobById },

L07's authorization pattern (401 → ownership → 403), applied to jobs. And the status code is L04's family reunion: 201 says the resource exists now (the note row was inserted); 202 says accepted, result later — the export doesn't exist yet, the job does, which is why Location points at /jobs/:id. The client polls that URL until status says done.

One honesty note: the worker polls every 500ms, so a job may sit pending for half a second before starting. Fine for emails and exports; a chat app wouldn't tolerate it. The upgrades are Postgres LISTEN/NOTIFY or Redis blocking pops — say "Redis lesson" and we'll price them.

Step 8 — the discipline: a queue is not a trash chute

Three laws, or the queue starts generating fiction like any cache without invalidation:

  • Don't queue what the response needs. The register response needs the user row — that stays inline. Only queue work the client didn't ask to wait for.
  • Handlers must be idempotent. Crash between "email sent" and "mark done" → restart runs the handler again → two emails. Queues deliver at least once; "exactly once" is a marketing term. An idempotent handler (L04's word, back for an encore) makes at-least-once behave like exactly-once.
  • Visibility is mandatory. A queue without a status endpoint is a black hole — jobs can sit pending forever and nobody would know. You built the endpoint before the drill proves the black hole. Keep it.

And when jobs failed: today you look at the table and re-run by hand. Real systems add retry caps and dead-letter queues. That's an upgrade, not a redesign — the row-based design already gave failure an address.

Four things to notice

  • Restart doesn't forget. Kill the server mid-job, restart, and the new worker finishes the old job — because it was a row all along. Durability you can test, and the drill tests it.
  • The worker is your event loop in a uniform. sleep is setTimeout, the claim is one query, every await yields. Nothing blocks (L02) — a slow email delays jobs, never requests. That inversion is the whole point.
  • 202 was always in the family. L04 taught 201 + Location; 202 + Location is the same shape with "not ready yet" as the twist. You didn't need a framework — you needed a scenario.
  • SKIP LOCKED is the Redis lesson in one clause. Claim work so nobody else claims it twice. When the worker moves to its own process — or you need retries, priorities, and throughput — that's pg-boss (same table, packaged) or Redis + BullMQ (shared memory). Same vocabulary you just built by hand.

The drill — feel, lose, durify, prove

Hands-on · the queue, by hand
  • Feel it: add sendWelcomeEmail (fake, 2s) awaited inside register; curl -w '%{time_total}\n' one register before and after (single-digit ms → ~2000ms); run npm test and feel the suite gain ~6s
  • Feel the coupling tax: flip a flag so the fake email throws — register answers 500 INTERNAL while the SQL was never the problem. Revert
  • Fire-and-forget: drop the await, add .catch(console.error); fast again. Then prove crack #1: POST a register, Ctrl-C the server inside the 2s window, restart — no email, no trace. Leave a comment listing the three cracks
  • Durify: write 0005_jobs.sql (as above), run node --env-file=.env utils/migrate.mjs, confirm the table
  • Swap the await for the jobs INSERT; register still 201 in single-digit ms; watch SELECT id, type, status, created_at FROM jobs ORDER BY id DESC LIMIT 5; in psql
  • Add the worker: tick() with SKIP LOCKED, handlers map, runWorker(); watch status walk pending → running → done, and feel the ~2s lag of "response instant, work later"
  • Durability proof: POST a register, kill the server while the job is pending or running, restart — the new worker finishes the old job. Compare with the fire-and-forget kill: this time, nothing was lost
  • Build POST /exports (202 + Location) and GET /jobs/:id (200/403/404); integration test: poll until done (with a timeout), and assert a stranger's job 403s — L07 scoping, tested
  • See the black hole: comment out runWorker(), POST /exports, watch the job sit pending forever; then restore and watch it drain. Write one line in your notes: why the status endpoint is not optional
  • Stretch A: run a second worker (runWorker("w2")) and log claims — no job claimed twice, thanks to SKIP LOCKED. Stretch B: wrap the user INSERT + job INSERT in one transaction, L06-style
