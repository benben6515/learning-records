Lesson 10 · Performance

Caching: Memory Over the Wire

Your server has one habit it grew in Lesson 07 and never questioned: every authenticated request asks Postgres who you are. List notes? Two queries. Create a note? Two queries. The database re-answers the same question a hundred times a second and nobody blinks — yet. Today: the cache-aside pattern, a TTL, and the exact moment your cache starts lying — which your L08 test suite catches in writing.

~40 min hands-on performance

But first — an old debt

Open server7.mjs. getSid is sitting there inline, still wearing the pre-L08 bug: startsWith("sid"). Meanwhile utils/index.mjs holds the fixed version, exported, guarded by your decoy test — and server7 never imports it. Two copies, one wrong. Integration tests can't see it (plain sid=… cookies parse correctly either way); only the unit test guards the utils copy, and nobody guards the inline one. First drill item: delete the inline copy, import the guarded one. The suite stays green — that silence is the sound of a fence doing its job.

Why this lesson

Count the queries in one ordinary cycle — register, login, list, create, logout. Seven-ish SQL statements, and every authenticated request pays the same tax twice: getUser re-runs the sessions JOIN every single time, then the handler runs its own query. Locally, each round-trip is half a millisecond and Postgres is bored. But you've already tasted the future: Lesson 09 moved the database behind a network socket. The same code against Cloud SQL or RDS pays 1–10 ms per query, per request — and the session lookup is pure repetition: the same sid, asked again and again, usually gets the same answer.

The one idea

A cache remembers an expensive answer next to the asker — together with a policy for when that answer stops being true. The policy has two halves and both are mandatory: expiration (a TTL — how long memory may overrule the database) and invalidation (which code paths must delete the entry the moment the truth changes). The pattern is called cache-aside: check memory, miss, query the database, remember. Storing is the easy half. The other half is why the field's oldest joke says the two hard problems in computer science are cache invalidation and naming things.

Step 1 — measure before you cache

Rule zero: no cache without a measured, repeated, expensive read. Make the invisible visible — one line in getUser:

const t0 = performance.now()
const { rows } = await pool.query(`…sessions JOIN…`, [sid])
console.log(`getUser: ${(performance.now() - t0).toFixed(2)}ms`)

Walk one cycle (register → login → list → logout) and read the log. You'll see the JOIN fire on every authenticated request — /auth/me, list notes, create a note — while register, login, and logout never call getUser. That's your hot path, found with evidence instead of folklore. (And note what you don't cache: /health runs once per platform poll; register inserts unique data. Not repeated, not cached.)

Step 2 — cache-aside on the hot path

A Map, a TTL, three branches:

const sessionCache = new Map()      // sid → { user, expires } — in-memory, per-process
const TTL = 60_000                  // 60s: how long memory may overrule Postgres

async function getUser(req) {
  const sid = getSid(req)
  if (!sid) return null
  const hit = sessionCache.get(sid)
  if (hit && hit.expires > Date.now()) return hit.user        // hit: zero queries

  const { rows } = await pool.query(`…sessions JOIN…`, [sid]) // miss: ask the DB
  const user = rows[0] ?? null
  sessionCache.set(sid, { user, expires: Date.now() + TTL })  // remember the answer
  return user
}

Run the suite before you go further. It goes red — and not by accident.

Step 3 — the moment your cache lies

✖ the notes contract, through real HTTP — the line that asserts logout → /auth/me → 401 now sees 200. Walk through why: logout deleted the session row from Postgres, but the cache still holds { user, expires: … } for that sid. For up to 60 seconds, memory overrules the database — your L07 promise ("logout revokes instantly") is broken, and the L08 fence is the thing that noticed. This is cache invalidation as a lived experience: not a quiz answer, a red test you wrote two lessons before you needed it.

The fix is one line at the mutation point:

async function logout(req, res) {
  const sid = getSid(req)
  if (sid) {
    await pool.query("DELETE FROM sessions WHERE sid = $1", [sid])
    sessionCache.delete(sid)          // evict — or memory keeps lying for the rest of the TTL
  }
  return json(res, 204, undefined, { "set-cookie": "sid=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0" })
}

The rule the line encodes: every place that mutates the underlying data is an invalidation point. For sessions there is exactly one — logout. Login inserts a brand-new sid (nothing cached yet, nothing to evict). If tomorrow a "log out everywhere" feature deletes many sessions, it inherits the same eviction duty. Find the mutation points, or the cache writes fiction.

One more honesty note: this Map grows forever — every sid ever seen stays until a request checks it past expiry. A course API dies of old age first; a real cache evicts (LRU, size caps) or is a separate process with memory limits (Redis). Say the word and we'll build a 30-line LRU some day.

Step 5 — the discipline: don't cache the notes list

It's tempting: cache listByUserId keyed by user, evict on every note write. Don't — not today. Your reads aren't hot, the list has three mutation points (POST, PUT, DELETE), and the lessons of today all say the same thing: cache what you measured, not what you can imagine. The discipline matters more than the pattern: a cache you can't justify is a lie generator you installed on purpose. (Also notice the key question every future cache must answer: whose data is this? A list keyed without the user id would serve strangers each other's notes — your L07 IDOR family, reborn through a Map.)

Four things to notice

  • Your fence caught a bug that didn't exist yet. The logout test was written in L08 against a promise from L07. Caching broke that promise in L10, and the suite went red before you finished typing. That's the whole point of a contract with teeth.
  • The cache lives in one process. Restart the server, cache is empty — users don't notice. That's a feature: cache is disposable, database is truth. When two server processes need to share the lie, you graduate to Redis — same pattern, shared memory.
  • TTL is a business decision. 60 seconds means "a revoked session may still work for a minute — unless we evict." Different data would get different numbers: sessions tight, a currency-rate cache loose, a CSS file basically forever.
  • Measure again. Same cycle as the drill — three authed reads hit the JOIN three times before the cache, once after: repeats cost one query instead of two until the TTL lapses. The number before and after is the only honest sales pitch a cache has.

The drill — measure, cache, lie, fix

Hands-on · the fence, again
  • Kill the old debt: delete server7's inline getSid, import the guarded one from utils/index.mjs; suite stays green; then mutation-check — re-break startsWith("sid=") in utils and watch the decoy test go red. Revert
  • Measure first: log duration (or just an occurrence) of every pool.query for one register → login → list → /auth/me → list → logout cycle; count how many times the sessions JOIN runs (answer: once per authed request — three in this cycle)
  • Add the sessionCache Map + TTL 60s to getUser (cache-aside, as above); run npm test — savor the red logout assertion (200 ≠ 401), that's the cache lying in writing
  • Evict in logout: sessionCache.delete(sid); suite green. Then mutation-check: comment the eviction out, watch the same test go red again, restore
  • Feel the TTL: temporarily set TTL to 200ms, write a test that logs in, waits 300ms (await new Promise(r => setTimeout(r, 300))), hits /auth/me, and asserts it still 200s (session row alive) — then logout, hit /auth/me with no eviction and TTL 200ms, and watch it go 401 on its own once the entry expires. Restore TTL 60s
  • Measure after: same cycle as step 2 — count the JOIN again (3 → 1: once per sid until the TTL lapses, not once per request). That delta is the cache's only honest sales pitch
  • Write the discipline down: one comment (or a line in your notes) stating what you chose NOT to cache (the notes list) and why (no hot reads, three mutation points, unjustified risk)
  • Stretch: the Map never forgets dead sids. Add eviction-on-read (if expired → delete + treat as miss) plus a size cap of 1000 with arbitrary eviction — feel how fast "just a Map" becomes a policy conversation
