Persistence II: PostgreSQL & Migrations

SQLite is a file you trust in-process. PostgreSQL is your data behind a socket — a separate server, real types, many concurrent writers — and schemas that evolve as versioned files. Today: Docker, a connection string, a 30-line migration tool, and server6 with the same contract again.

~45 min hands-on data

Why this lesson

Lesson 05's DatabaseSync runs inside your process — one writer, one machine. Real backends share data across processes, deploys, and machines, which means the database must be its own program, reached over the network. That flip changes everything you touch today: connection strings instead of filenames, async queries instead of sync calls (hello again, Lesson 02), and — because you can no longer just edit CREATE TABLE in your editor — migrations: schema changes as ordered, versioned, run-once files.

The one idea

PostgreSQL is a server; your code is now its client. Same CRUD contract (L03–L05, untouched), but the engine lives in another process — here, a Docker container playing "another machine". Two consequences follow. First, every query crosses the network, so you ask asynchronously and pool connections (pg Pool docs). Second, the schema can't be edited casually anymore — it's shared state with a history, so changes become migrations.

Step 1 — migrations: schema changes as files

migrations/0001_init.sql — the notes table, born (compare with L05: TIMESTAMPTZ instead of TEXT, IDENTITY instead of bare INTEGER PRIMARY KEY, and a CHECK the engine enforces):

CREATE TABLE IF NOT EXISTS notes (
  id         INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title      TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

migrations/0002_add_done.sql — schemas evolve; existing data survives:

ALTER TABLE notes ADD COLUMN done BOOLEAN NOT NULL DEFAULT false;

And the entire "migration tool" — a ledger table, sorted files, a transaction each (CREATE TABLE docs):

import { readdirSync, readFileSync } from "node:fs";
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

await pool.query(`CREATE TABLE IF NOT EXISTS schema_migrations (
  name TEXT PRIMARY KEY,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
)`);

const applied = new Set(
  (await pool.query("SELECT name FROM schema_migrations")).rows.map((r) => r.name)
);
const files = readdirSync("migrations").filter((f) => f.endsWith(".sql")).sort();

for (const f of files) {
  if (applied.has(f)) continue;
  console.log("applying", f);
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query(readFileSync(`migrations/${f}`, "utf8"));
    await client.query("INSERT INTO schema_migrations (name) VALUES ($1)", [f]);
    await client.query("COMMIT");               // both lines, or neither
  } catch (err) {
    await client.query("ROLLBACK");
    console.error(`${f} failed — rolled back:`, err.message);
    process.exit(1);
  } finally {
    client.release();
  }
}

await pool.end();
console.log("up to date");

node migrate.mjs applies 0001 then 0002; run it again and it prints up to date — the ledger knows. That try/ROLLBACK is the error net (L03) wearing a database hat: a failed migration leaves no half-applied schema.

Step 2 — server6.mjs: same contract, network engine

Routing, dispatch, 405s, error net: byte-for-byte L04/L05. The data layer is now strings + $1 params + await (the ? changed clothes; the rule didn't):

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

const q = {
  list:   "SELECT id, title, done, created_at FROM notes ORDER BY id",
  get:    "SELECT id, title, done, created_at FROM notes WHERE id = $1",
  has:    "SELECT 1 FROM notes WHERE id = $1",
  insert: "INSERT INTO notes (title) VALUES ($1) RETURNING id, title, done, created_at",
  upsert: `INSERT INTO notes (id, title) VALUES ($1, $2)
           ON CONFLICT (id) DO UPDATE SET title = excluded.title
           RETURNING id, title, done, created_at`,
  del:    "DELETE FROM notes WHERE id = $1",
};

// handlers change shape: (await pool.query(q.list)).rows — rows[] is the new .all()

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      try {
        const created = (await pool.query(q.insert, [note.title])).rows[0];
        return json(res, 201, created, { location: `/notes/${created.id}` });
      } catch (err) {
        // the CHECK constraint speaks PostgreSQL error code 23514 — translate it into the contract
        if (err.code === "23514") return fail(res, 400, "VALIDATION", "title must be 1–200 chars");
        throw err;                                // not ours? error net decides
      }
  } },

  { method: "DELETE", pattern: "/notes/:id", handler: async (req, res, p) => {
      // .rowCount is the new .changes — zero means 404
      if ((await pool.query(q.del, [Number(p.id)])).rowCount === 0)
        return fail(res, 404, "NOT_FOUND", "note not found");

Four things to notice

  • Everything is await now — and the event loop thanks you. Each query is network I/O; sync DatabaseSync calls would freeze every request (L02's rule). Pool keeps a few warm TCP connections so queries don't pay connect-cost each time — you pool connections, not results (Pool docs).
  • The DB now enforces types and rules you used to hand-check. TIMESTAMPTZ stores a real instant with a timezone (docs) — your API now returns 2026-09-08T03:30:22.111Z, not a SQLite TEXT. The CHECK on title length is engine-enforced; our handler just translates error 23514 into a contract 400 (error codes appendix). Defense in depth: your 400-check and the DB's CHECK both run.
  • Migrations are the schema's git history. Numbered, ordered, run-once. New dev? node migrate.mjs builds their entire schema in order. Need a change? New file — never edit an applied one (the ledger won't re-run it, and teammates' databases would diverge).
  • Concurrent writers just… work. While server6 ran, docker exec … psql — a second client — inserted a row; both saw a consistent view. That's MVCC, PostgreSQL's concurrency machinery, doing what SQLite's single-writer lock can't (MVCC chapter). Bonus realism from my test run: ids came back 1, 4, 7 — the two CHECK-rejected inserts still burned sequence values. Identity ids are unique, not gap-free; don't build logic on contiguity.

The drill — own the whole stack

Hands-on · container, migrations, contract, second writer
  • Start the "other machine": docker run -d --name bd-pg -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=notes -p 5432:5432 postgres:17-alpine, then docker exec bd-pg pg_isready -U postgres (image docs)
  • Project: npm init -y && npm install pg; export DATABASE_URL=postgres://postgres:dev@localhost:5432/notes; write the two migration files + migrate.mjs from above
  • Run node migrate.mjs twice — first run applies 0001 then 0002; second prints up to date. Look at the ledger: docker exec bd-pg psql -U postgres -d notes -c "SELECT * FROM schema_migrations;"
  • Build server6.mjs (server5 + the network data layer), start: node server6.mjs
  • Create: curl -i -X POST -H "content-type: application/json" -d '{"title":"buy milk"}' http://localhost:3000/notes → 201; note done:false (born in migration 0002) and a real ISO timestamp
  • Engine-enforced rules: POST a 250-char title → 400 VALIDATION "title must be 1–200 chars" — a rule your handler never wrote; the DB threw 23514 and the handler translated
  • Contract regression: PUT /notes/7 twice (201, 200), wrong verb 405, bad JSON 400 — third engine, same promises
  • Concurrent writers: while the server runs, docker exec bd-pg psql -U postgres -d notes -t -c "INSERT INTO notes (title) VALUES ('from psql');" → GET /notes shows both writers' rows — no locks, no drama
  • Write your own migrations/0003_add_priority.sql (ALTER TABLE notes ADD COLUMN priority INTEGER NOT NULL DEFAULT 0;), rerun the runner, confirm only 0003 applies
  • Teardown/rebuild: docker rm -f bd-pg, rerun the docker run + migrate + server — the whole stack rebuilds from two migration files. That reproducibility is the point
