Lesson 07 · Auth

Auth: Sessions vs Tokens

HTTP has no memory — so "who is calling?" must ride on every request. Today: password hashing with scrypt, a session table, an HttpOnly cookie, 401 vs 403, and notes that finally have owners. Then we decode a JWT by hand and you'll never find tokens mysterious again.

~45 min hands-on security

Why this lesson

You've used Firebase/Supabase auth — login "just works" and a token appears. Today you own the whole mechanism: registering users, hashing passwords safely, issuing proof-of-login, checking it on every request, and scoping data so bob can't read alice's notes. Same stack as Lesson 06 (Postgres + server skeleton), four new endpoints, zero new dependencies — the crypto is Node's built-in node:crypto.

The one idea

Authentication proves who you are; authorization decides what you may touch — and because HTTP is stateless, both ride on every single request. Two ways to carry "who": the server remembers (a session row + its id in a cookie), or the server verifies (a signed token the client presents). Everything else in auth is details of those two sentences (OWASP Authentication Cheat Sheet).

Step 1 — migration 0003_auth.sql: users, sessions, ownership

CREATE TABLE users (
  id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,                  -- 23505 → your 409
  password_hash TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  sid        TEXT PRIMARY KEY,                 -- 256 bits of randomness, hex
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL DEFAULT now() + interval '7 days'
);

ALTER TABLE notes ADD COLUMN user_id INTEGER REFERENCES users(id) ON DELETE SET NULL;

(Did the optional 0003_add_priority.sql in Lesson 06? Name this 0004_auth.sql — the runner only cares about order.) Three constraints are already working for you: UNIQUE email, the sessions→users REFERENCES, and 7-day expiry enforced by the database clock, not your code.

Step 2 — server7.mjs: hashing, cookies, scoping

Passwords first — the only genuinely dangerous line in this lesson. Hash, never encrypt: encryption reverses; a hash is a one-way grinder. And it must be slow — slowness is the feature that makes brute-forcing billions of guesses uneconomical. Node ships scrypt, an OWASP-approved family:

import { randomBytes, scrypt as _scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";
const scrypt = promisify(_scrypt);                 // async form — scryptSync would block the loop (L02!)

async function hashPassword(password) {
  const salt = randomBytes(16).toString("hex");    // unique per user — kills rainbow tables
  const hash = (await scrypt(password, salt, 64)).toString("hex");
  return `${salt}:${hash}`;                        // store both; never the password
}
async function verifyPassword(password, stored) {
  const [salt, hash] = stored.split(":");
  const test = await scrypt(password, salt, 64);
  return timingSafeEqual(Buffer.from(hash, "hex"), test);   // constant-time compare
}

Now the session machinery — cookie parsing (one header, no dependency) and the lookup every protected handler will call:

const getSid = (req) =>
  (req.headers.cookie || "").split("; ").find((c) => c.startsWith("sid="))?.slice(4);

async function getUser(req) {
  const sid = getSid(req);
  if (!sid) return null;
  const { rows } = await pool.query(
    `SELECT u.id, u.email FROM sessions s
     JOIN users u ON u.id = s.user_id
     WHERE s.sid = $1 AND s.expires_at > now()`, [sid]);
  return rows[0] ?? null;
}

The four auth handlers (routes/dispatch/error net unchanged since L04):

  { method: "POST", pattern: "/auth/register", handler: async (req, res) => {
      const body = parseJson(await readBody(req));
      if (body === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!body.email || !body.password) return fail(res, 400, "VALIDATION", "email and password are required");
      try {
        const u = (await pool.query(
          "INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email",
          [body.email, await hashPassword(body.password)])).rows[0];
        return json(res, 201, u);
      } catch (err) {
        if (err.code === "23505") return fail(res, 409, "EMAIL_TAKEN", "that email is already registered");
        throw err;                                  // L06's error-code translation, again
      }
  } },

  { method: "POST", pattern: "/auth/login", handler: async (req, res) => {
      const body = parseJson(await readBody(req));
      const { rows } = await pool.query("SELECT * FROM users WHERE email = $1", [body?.email]);
      const user = rows[0];
      // same 401 either way — an attacker can't discover which emails exist
      if (!user || !(await verifyPassword(body.password, user.password_hash)))
        return fail(res, 401, "BAD_CREDENTIALS", "invalid email or password");
      const sid = randomBytes(32).toString("hex");  // unguessable = the whole ticket
      await pool.query("INSERT INTO sessions (sid, user_id) VALUES ($1, $2)", [sid, user.id]);
      return json(res, 200, { id: user.id, email: user.email }, {
        "set-cookie": `sid=${sid}; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800`,
      });
  } },

  { method: "GET", pattern: "/auth/me", handler: async (req, res) => {
      const me = await getUser(req);
      if (!me) return fail(res, 401, "UNAUTHENTICATED", "log in first");
      json(res, 200, me);
  } },

  { method: "POST", pattern: "/auth/logout", handler: async (req, res) => {
      const sid = getSid(req);
      if (sid) await pool.query("DELETE FROM sessions WHERE sid = $1", [sid]);
      json(res, 204, undefined, { "set-cookie": "sid=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0" });
  } },

And the notes handlers grow one clause — this is authorization, and notice it's mostly SQL:

  // list: only mine
  "SELECT * FROM notes WHERE user_id = $1 ORDER BY id"          // $1 = me.id

  // read one: exists, then whose?
  if (!note)                          return fail(res, 404, "NOT_FOUND", "note not found");
  if (note.user_id !== me.id)         return fail(res, 403, "FORBIDDEN", "not your note");

Four things to notice

  • The sid is unguessable, and that's its only job. 256 bits of randomness — no signature, no encoding, no meaning. Possession is the proof (like a hotel keycard); the server looks it up in sessions and the DB's expires_at decides if it still opens doors (OWASP Session Management).
  • HttpOnly + SameSite=Lax are two different shields. HttpOnly forbids JavaScript from reading the cookie — XSS can steal what it can't see (MDN cookies). SameSite stops the browser auto-sending it cross-site — defanging CSRF. (Production adds Secure — HTTPS only; we're on localhost.)
  • 401 vs 403 is a contract distinction. 401 = "I don't know you" (no/bad/expired session) — the client should log in. 403 = "I know you, but no" — bob asked for alice's note; logging in again won't help (MDN 401). Our error codes say it outright: UNAUTHENTICATED vs FORBIDDEN.
  • Authorization is a WHERE clause. No middleware magic: list = WHERE user_id = $1; read-one = fetch, then compare owner. Most "unauthorized access" CVEs you'll read about are a missing WHERE or a skipped owner-check — now you can see the line that prevents them.

The other half — JWTs, decoded by hand

The token approach flips where the memory lives: the server signs claims (user id, expiry) and the client carries them; each request verifies the signature instead of looking up a session. A JWT is three base64url parts — decode the middle one yourself in the drill and watch readable JSON fall out: a JWT is signed, not encrypted — anyone can read it; nobody (without the key) can change it (jwt.io intro).

Sessions vs tokens — where the memory lives
Session + cookieJWT (Bearer)
Server remembers?yes — a sessions rowno — verifies a signature
Revoke instantly?yes — DELETE the row (logout works!)hard — until expiry, or a denylist
Stolen credential…cookie theft (HttpOnly helps)token theft (often localStorage: XSS can read it)
Shines whenone server/origin, classic web appmany services verify without shared DB; mobile/native

Firebase/Supabase hand you JWTs because they verify them at the edge — the trade-offs above are still yours to know.

The drill — two users, one boundary

Hands-on · register, login, scope, 403, logout, decode a JWT
  • Write 0003_auth.sql (or 0004), run node migrate.mjs — check with docker exec bd-pg psql -U postgres -d notes -c "\d sessions"
  • Build server7 (server6 + the pieces above). Port note: if EADDRINUSE greets you — something else lives on 3000 (a Vite dev server did it to me during verification) — change the port, curl accordingly
  • Register: curl -i -X POST -H "content-type: application/json" -d '{"email":"alice@test.dev","password":"correct horse"}' http://localhost:3000/auth/register → 201; same email again → 409 EMAIL_TAKEN (that's 23505 wearing a contract)
  • Register bob too. Then three logins: alice with right password (200 + set-cookie: sid=…; HttpOnly; SameSite=Lax), alice with wrong password, ghost@… — confirm the two failures are byte-identical 401s
  • Save alice's sid from the header; then curl -b "sid=ALICE_SID" http://localhost:3000/auth/me → 200; without the cookie → 401 UNAUTHENTICATED
  • Own notes: alice POSTs {"title":"alice secret"} → 201; bob logs in, GET /notes → [] — his list, not hers; the row is invisible, not hidden
  • The boundary: bob GETs alice's note id → 403 {"code":"FORBIDDEN"}; bob DELETEs it → 403. Login again as bob — still 403: 403 ≠ 401
  • Logout: curl -i -X POST -b "sid=ALICE_SID" http://localhost:3000/auth/logout → 204 + cookie cleared; reuse the old sid → 401 — revocation is a DELETE, that's the session win
  • See the secrets: docker exec bd-pg psql -U postgres -d notes -c "SELECT email, left(password_hash,20) FROM users;" — salt+hash gibberish; no password column exists anywhere
  • Decode a JWT by hand: grab any token from jwt.io, split on the dots, echo "MIDDLE_PART" | base64 -d — you just read a "secure" token's claims. Signed ≠ encrypted, now forever
