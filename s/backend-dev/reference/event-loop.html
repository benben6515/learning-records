The Event Loop Cheat Sheet

The mental model, the four rules, the blocking-API blacklist, and the curl commands that prove it all — compressed from Lesson 02, the Node official guide, and Philip Roberts' talk. Print me.

The model in six steps

1 · your handler runs on the call stack        ← one thread, ALL of your JS
2 · it hands slow work to Node (timer, disk…)
3 · handler returns → stack is EMPTY            ← the loop can move again
4 · slow work finishes OUTSIDE JavaScript       ← OS async + libuv pool (4 threads)
5 · its callback waits in the queue
6 · event loop pushes it onto the stack         ← only ever when the stack is empty

The four rules

1 · One at a time

All your JavaScript executes on one call stack. No line of your code ever runs in parallel with another.

2 · I/O runs elsewhere

The waiting happens off-thread: OS async APIs for sockets/timers, libuv's thread pool (4 by default) for disk/DNS/crypto.

3 · The loop waits for quiet

A queued callback only runs once the stack is empty. Sync work is the stack — so it suspends the loop.

4 · One sync hog blocks everyone

Rule 3's consequence: a busy while freezes every request — new and pending alike.

The blocking blacklist

Inside a request handler, these hog the stack and stall the whole server — swap for the async twin:

Blocks the loopUse instead
fs.readFileSync()fs.promises.readFile()
crypto.pbkdf2Sync() & friendscrypto.pbkdf2() callback / promisified
JSON.parse(hugePayload)stream-parse, or cap payload size at the proxy
busy while/for loops (CPU work)worker threads / job queue (later lesson)
catastrophic-backtracking regexestest with generated input; add timeouts

Prove it in 30 seconds

$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → 0.005s baseline

$ curl "http://localhost:3000/work?ms=3000" &   # 3s SYNC work, background
$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → ~3.0s  ← the whole server was frozen behind one sync handler

$ curl "http://localhost:3000/idle?ms=3000" &   # 3s ASYNC wait, background
$ curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello
# → 0.005s ← same 3 seconds, stack stayed empty

Two fine-print facts (for later)

  • Microtasks jump the queue. Promise callbacks (.then) drain before the next timer/I/O callback — MDN: Event loop.
  • Single thread scales for I/O, not CPU. Thousands of simultaneous waits: fine. Heavy computation: move it off the loop (worker threads, child processes, or a queue).
