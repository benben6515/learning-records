Queues First Aid

Lesson 11 in one card: the respond-first rule, the three strategies, the jobs table you migrated, the SKIP LOCKED claim, the worker loop, the 202 contract, and the gotchas that turn a queue into a black hole — grounded in pg-boss, which is this card wearing a README. Print me.

The respond-first rule (gates everything)

Respond when your outcome is known; enqueue the work the response doesn't need. The response reports on the request — the account exists, the note was created. Follow-up work (emails, exports, webhooks) goes on a durable to-do list, written down before answering. A dependency you await inside a handler is a dependency your endpoint inherits — its latency, its failures, its outages.

The jobs table (migration skeleton)

CREATE TABLE jobs (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  type TEXT NOT NULL,                        // picks the handler
  payload JSONB NOT NULL DEFAULT '{}',       // the input, as JSON
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'running', 'done', 'failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at TIMESTAMPTZ,
  finished_at TIMESTAMPTZ
)

Enqueue in the same database that records the fact — that's the outbox idea: what happened and what must happen next live together, so a restart can pick up the "next".

The claim (the whole coordination problem, four words)

UPDATE jobs SET status = 'running', started_at = now()
WHERE id = (
  SELECT id FROM jobs WHERE status = 'pending'
  ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED   // second worker skips the locked row
)
RETURNING *

N workers, one table, zero double-work. Then: run the handler, mark done (or failed — a recorded failure beats a lost promise), idle-poll 500ms. Upgrades: LISTEN/NOTIFY to skip the poll, or Redis blocking pops.

The 202 contract

  • 201 — the resource exists now (the note row was inserted). 202 — accepted, result later: the export doesn't exist yet, the job does.
  • Answer 202 + Location: /jobs/:id; the client polls that URL until status says done.
  • Jobs are owned data — same scoping as notes: 401 without a session, 403 when it's not your job (L07 reborn).

Gotchas worth knowing now

  • Don't queue what the response needs. Only follow-up work the client didn't ask to wait for goes on the list.
  • At-least-once is the guarantee. Crash between "work done" and "mark done" → the handler runs again. Idempotent handlers make at-least-once behave like exactly-once — "exactly-once" alone is a marketing term.
  • Visibility is mandatory. A queue without a status endpoint is a black hole: jobs sit pending forever and nobody knows. Build the endpoint, keep it.
  • Failed needs a story. Mark failed, look, re-run by hand — fine today. Real systems add retry caps and dead-letter queues; the row already gave failure an address.
  • JSONB payload is flexible and unvalidated. Validate inside the handler; a typo in the producer shows up as a runtime surprise in the worker.
  • setTimeout isn't storage. Fire-and-forget loses work on crash, invisibly, permanently. If losing it matters, it belongs in a table.
  • One process can't share a loop; many can share a table. When the worker moves to its own process or throughput outgrows polling: pg-boss (same table, packaged) or Redis + BullMQ (shared memory). Same vocabulary.
