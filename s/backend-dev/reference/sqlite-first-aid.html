SQLite First Aid

Everything from Lesson 05 in one card: the built-in Node module, the five statements of a CRUD data layer, the ? rule that kills SQL injection, and the CLI commands to see your data with your own eyes — compressed from the node:sqlite docs and sqlite3 CLI docs. Print me.

The three-line starter

import { DatabaseSync } from "node:sqlite";        // Node 23+ (22.5+ w/ --experimental-sqlite)

const db = new DatabaseSync("notes.db");           // the whole database is THIS file
db.exec(`CREATE TABLE IF NOT EXISTS notes (
  id INTEGER PRIMARY KEY, title TEXT NOT NULL,
  created_at TEXT DEFAULT (datetime('now'))
)`);

The five statements of a CRUD layer

const q = {
  list:   db.prepare("SELECT id, title FROM notes ORDER BY id"),
  get:    db.prepare("SELECT id, title FROM notes WHERE id = ?"),
  insert: db.prepare("INSERT INTO notes (title) VALUES (?) RETURNING id, title"),
  upsert: db.prepare(`INSERT INTO notes (id, title) VALUES (?, ?)
            ON CONFLICT(id) DO UPDATE SET title = excluded.title
            RETURNING id, title`),                // idempotent PUT (L04) in one clause
  del:    db.prepare("DELETE FROM notes WHERE id = ?"),
};

q.list.all()          // → array of row objects
q.get.get(7)          // → first row object | undefined
q.insert.get("milk")  // → the RETURNING row (id minted by SQLite)
q.del.run(7).changes  // → number of rows touched (0 ⇒ your 404)

Rules that keep you alive

RuleWhy
? params, never template stringsData never enters SQL text ⇒ injection becomes a silly stored title. Concatenation (\`…'${title}'\`) executes it.
INTEGER PRIMARY KEY = auto idSQLite's rowid assigns it — replaces nextId++, can't collide.
NOT NULL + DEFAULT in schemaThe DB-level twin of your 400 validation — invalid rows can't exist, whatever the bug.
Prepare once (module scope), run foreverParse/plan once; params per call. One q object = your whole data layer.
.changes === 0 ⇒ 404DELETE/UPDATE report rows touched — zero means the id wasn't there.

See it with the sqlite3 CLI

$ sqlite3 notes.db ".schema"              # the contract, straight from the file
$ sqlite3 notes.db ".tables"
$ sqlite3 notes.db "SELECT id, title FROM notes WHERE title LIKE '%milk%'"
$ sqlite3 notes.db -box "SELECT * FROM notes"   # pretty tables
$ ls -la notes.db notes.db-wal                # the DB is a file; -wal is its journal

Gotchas worth knowing now

  • DatabaseSync is synchronous — on purpose. Each statement blocks the event loop (Lesson 02!). Fine for local/single-user; one reason real network DBs (PostgreSQL, next lesson) are async over the wire.
  • Params are positional. The second ? binds the second argument — order bugs are silent until the data looks wrong.
  • SQLite types are flexible. TEXT/INTEGER/NULL/REAL/BLOB, with dynamic typing per column. PostgreSQL (next lesson) enforces types like TypeScript does — expect the shock.
  • One writer at a time. Many readers, single writer — the moment you need concurrent writers on different machines, that's PostgreSQL's job.
