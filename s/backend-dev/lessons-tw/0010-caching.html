第 10 課 · 效能

快取：記憶體勝過網路

你的伺服器有個從第 07 課養成、從沒被質疑過的習慣：每個需要驗證的請求都去問一次 Postgres「你是誰」。列筆記？兩個 query。建筆記？兩個 query。資料庫一秒鐘重複回答同一個問題一百次，沒人皺眉——暫時還沒有。今天：cache-aside 模式、一個 TTL，還有你的快取開始說謊的確切那一刻——而你的 L08 測試 suite 會親手抓到它。

約 40 分鐘 動手做 效能

但先還一筆舊債

打開 server7.mjs。getSid 還坐在那裡inline，身上穿著 L08 之前的舊 bug：startsWith("sid")。同時 utils/index.mjs 躺著修正版，有 export、有誘餌測試看守——而 server7 從來沒 import 它。兩份副本，一份是錯的。整合測試看不見它（普通的 sid=… cookie 兩種寫法都解析正確）；只有單元測試守著 utils 那份，而 inline 那份無人看守。第一個練習項目：刪掉 inline 副本，import 被看守的那份。Suite 維持綠燈——那份沉默，是圍籬在盡責的聲音。

為什麼是這一課

數數一個平凡循環裡的 query——註冊、登入、列清單、建筆記、登出。七條上下 SQL，而每個需要驗證的請求都繳兩次同樣的稅：getUser 每一次都重跑 sessions JOIN，handler 再跑自己的 query。本地，每趟半毫秒，Postgres 閒得發慌。但你已經嘗過未來了：第 09 課把資料庫搬到網路 socket 後面。同一份程式碼對上 Cloud SQL 或 RDS，每個 query、每個請求要付 1–10 毫秒——而 session 查詢是純粹的重複：同一個 sid，問了又問，答案幾乎總是同一個。

核心觀念

快取＝把昂貴的答案記在提問者旁邊——連同一份「答案什麼時候不再是對的」的政策。政策有兩半，缺一不可：過期（TTL——記憶體可以勝過資料庫多久）與失效處理（哪些程式路徑必須在真相改變的瞬間刪掉那筆紀錄）。這個模式叫 cache-aside：查記憶體、沒中、問資料庫、記住。儲存是簡單的那一半；另一半，就是資訊工程最老的笑話「兩大難題：快取失效與命名」裡的那一半。

步驟一——快取之前，先測量

規則零：沒有測量過、重複發生、而且昂貴的讀取，就不准上快取。把看不見的變成看得見——getUser 裡一行：

const t0 = performance.now()
const { rows } = await pool.query(`…sessions JOIN…`, [sid])
console.log(`getUser: ${(performance.now() - t0).toFixed(2)}ms`)

走一個循環（註冊 → 登入 → 列清單 → 登出），讀 log。你會看到 JOIN 在每個需要驗證的請求開火——/auth/me、列清單、建筆記——而註冊、登入、登出根本不呼叫 getUser。熱路徑找到了，靠證據不是靠都市傳說。（也注意你不快取什麼：/health 每次平台輪詢才跑一次；register 插入的是獨一無二的資料。不重複，就不快取。）

步驟二——熱路徑上的 cache-aside

一個 Map、一個 TTL、三個分支：

const sessionCache = new Map()      // sid → { user, expires }——行程內記憶體
const TTL = 60_000                  // 60 秒：記憶體可以勝過 Postgres 的時限

async function getUser(req) {
  const sid = getSid(req)
  if (!sid) return null
  const hit = sessionCache.get(sid)
  if (hit && hit.expires > Date.now()) return hit.user        // 中：零 query

  const { rows } = await pool.query(`…sessions JOIN…`, [sid]) // 沒中：問 DB
  const user = rows[0] ?? null
  sessionCache.set(sid, { user, expires: Date.now() + TTL })  // 記住答案
  return user
}

繼續之前先跑 suite。它會紅——而且不是意外。

步驟三——快取說謊的那一刻

✖ the notes contract, through real HTTP——斷言 logout → /auth/me → 401 的那行，現在看到的是 200。走一遍為什麼：logout 從 Postgres 刪了 session row，但快取還握著那個 sid 的 { user, expires: … }。最長 60 秒，記憶體勝過資料庫——你 L07 的承諾（「logout 立即失效」）破了，而發現它的是 L08 的圍籬。這就是快取失效的親身體驗：不是測驗答案，是一個你在兩課之前就寫好、專門等這一刻的紅燈。

修法是突變點上的一行：

async function logout(req, res) {
  const sid = getSid(req)
  if (sid) {
    await pool.query("DELETE FROM sessions WHERE sid = $1", [sid])
    sessionCache.delete(sid)          // 清除——否則記憶體繼續說謊到 TTL 用完
  }
  return json(res, 204, undefined, { "set-cookie": "sid=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0" })
}

這行編碼的規則：每個修改底層資料的地方，都是失效點。sessions 表正好只有一個——logout。登入插入的是全新 sid（快取裡還沒有，無東西可清）。哪天做「登出所有裝置」批次刪 session，它就繼承同樣的清除義務。找齊突變點，否則快取開始寫小說。

步驟四——誠實的取捨表

政策新鮮度成本
不快取永遠為真每個讀取永遠付 DB 的錢
只有 TTL最舊到 TTL 為止——你親手選的說謊窗口一個 Map、零簿記——但窗口內的登出，除非動手清除，記憶體裡照樣有效
每個突變點都清除突變時刻為真；只有「背後改掉的資料」會舊必須找齊所有突變點——漏一個，快取說謊
TTL 加清除（你蓋的這個）兩者兼得真實世界的預設值

另一則誠實聲明：這個 Map 永遠不縮——每個見過的 sid 都留著，直到某個請求發現它過期。課程 API 會先老死；真正的快取會驅逐（LRU、大小上限），或是把記憶體外包給有上限的獨立行程（Redis）。哪天想蓋，30 行的 LRU 我們隨時可以寫。

步驟五——紀律：不要快取筆記清單

很誘人：cache listByUserId、key 用 user、每個寫入都清除。別——今天別。你的讀取不熱、清單有三個突變點（POST、PUT、DELETE），而今天的每個教訓都指向同一件事：快取你測量過的，不是你想像得到的。紀律比模式重要：一個你無法說明正當性的快取，是你刻意安裝的說謊機器。（也注意每個未來快取都必須回答的問題：誰的資料？一個 key 沒帶 user id 的清單快取，會把陌生人彼此的筆記發來發去——你 L07 的 IDOR 家族，藉著一個 Map 轉世。）

四個值得注意的地方

  • 你的圍籬抓到一個還沒誕生的 bug。logout 測試寫於 L08，看守的是 L07 的承諾。快取在 L10 弄破承諾，suite 在你還沒打完字前就紅給你看。這就是「有牙齒的合約」的全部意義。
  • 快取住在一個行程裡。重啟伺服器，快取清空——使用者無感。這是功能：快取是一次性的，資料庫才是真相。等兩個 server 行程需要共享同一份謊言，你就升級到 Redis——同一個模式，共享的記憶體。
  • TTL 是商業決策。60 秒的意思是「被撤銷的 session 也許還能用一分鐘——除非我們動手清」。不同資料配不同數字：session 收緊、匯率快取放鬆、CSS 檔基本上永遠。
  • 再測量一次。同步驟二的循環——三個需要驗證的請求，快取前 JOIN 開火三次；快取後一次：重複的請求從兩個 query 變一個，直到 TTL 用完。前後兩個數字，是快取唯一誠實的推銷詞。

練習——測量、快取、說謊、修復

動手做 · 圍籬，再上陣
  • 還舊債：刪掉 server7 的 inline getSid，從 utils/index.mjs import 被看守的那份；suite 維持綠；然後突變檢查——把 utils 裡的 startsWith("sid=") 改壞，看誘餌測試轉紅。還原
  • 先測量：記錄一個註冊 → 登入 → 列清單 → /auth/me → 再列一次清單 → 登出循環裡每個 pool.query 的時間（或只記出現次數）；數 sessions JOIN 跑幾次（答案：每個需要驗證的請求一次——這個循環是三次）
  • 把 sessionCache Map + TTL 60 秒加進 getUser（cache-aside，照上面）；跑 npm test——細細品嘗紅掉的 logout 斷言（200 ≠ 401），那就是快取在白紙黑字上說謊
  • logout 裡清除：sessionCache.delete(sid)；suite 轉綠。然後突變檢查：註解掉清除那行，看同一個測試再紅一次，還原
  • 感受 TTL：暫時把 TTL 設 200ms，寫一個測試：登入、等 300ms（await new Promise(r => setTimeout(r, 300))）、打 /auth/me、斷言還是 200（session row 還活著）——然後 logout、不清除、打 /auth/me，看它在 200ms 後自己變 401。還原 TTL 60 秒
  • 再測量：同步驟二的循環——再數一次 sessions JOIN（3 → 1：每個 sid 一次、直到 TTL 用完，不是每個請求一次）。前後差額，就是快取唯一誠實的推銷詞
  • 把紀律寫下來：一行註解（或筆記）記下你選擇不快取的東西（筆記清單）與原因（讀取不熱、三個突變點、風險無正當性）
  • 加碼：Map 永遠記著死 sid。加上讀取時驅逐（過期 → delete + 當 miss）加 1000 筆大小上限、滿了任意驅逐——體會「只是一個 Map」多快變成一場政策辯論
