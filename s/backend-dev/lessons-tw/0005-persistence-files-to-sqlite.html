第 05 課 · 持久化 I

持久化 I：檔案 → SQLite

你的筆記跟著程序一起死。第一個修法：把整份資料寫進 JSON 檔——能動，直到你看見它的三道裂縫。真正的修法：SQLite——一個檔案就是一個資料庫，Node 內建，第 04 課的合約原封不動，資料從此活得過重啟。

約 40 分鐘 動手做 資料

為什麼是這一課

到目前為止所有資料都住在 Map 裡——伺服器重啟就清空。「寫到檔案不就好了」是最直覺的修法，也是最好的老師，因為它差一點就對了。今天：先實作檔案版、在紙上弄壞它，再把引擎換成 Node 內建的 node:sqlite——零 npm 安裝、同一份 API 合約、耐久的資料。PostgreSQL 下一課登場，等 SQLite 誠實地掙到它的極限之後。

核心觀念

資料庫＝一個檔案＋一套「安全寫入、接受提問」的協定。沒有更神秘的東西。今天你會親眼看這句話成真：notes.db 就是真的、磁碟上的一個檔案（練習裡自己 ls 它）——但 SQLite 協定給你原子寫入、當機安全、和一套查詢語言。裸 JSON 檔三個都沒有。

步驟一——差十分鐘就正確的修法

替 server4.mjs 加上檔案持久化——開機載入、每次寫入後保存：

import { readFileSync, writeFileSync } from "node:fs";   // 檔案最上方

// 開機：讀檔（第一次跑就是空陣列）
const notes = new Map(
  JSON.parse(readFileSync("notes.json", "utf8") || "[]").map((n) => [n.id, n])
);
const save = () => writeFileSync("notes.json", JSON.stringify([...notes.values()]));

// 然後在 POST / PUT / DELETE handler 結尾呼叫 save()

跑起來：建一筆筆記、Ctrl-C、再啟動——筆記還在。真正的進步。接下來是三道裂縫，以及為什麼每一道都是「協定」問題、不是程式碼 bug：

  1. 寫到一半當機。writeFileSync 重寫整個檔案。中途死掉（磁碟滿、kill -9、部署中）notes.json 就是截斷的垃圾——下次開機死在 JSON.parse。資料庫先寫日誌、再翻轉——被殺也保持原子性（node:fs 文件對此無解）。
  2. 更新遺失（lost update）。兩個請求、兩次整檔重寫——第二個蓋掉第一個的筆記。事件迴圈是單緒沒錯，但檔案才是共享狀態；任何也碰它的人（第二個程序、一支腳本、編輯器裡的你）都在跟你賽跑。
  3. 不能提問。「標題含 milk 的筆記、最新的在前面」＝全部載進 JS 再過濾。沒有 WHERE、沒有索引、沒有分頁。資料一長大，這個設計就死。

步驟二——server5.mjs：同一份合約，SQLite 引擎

Node 22.5+ 內建 SQLite——DatabaseSync，免 npm，Node 23+ 免旗標。這次換引擎只動資料層；路由、分派、405、錯誤合約跟第 04 課一字不差：

import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";

// ——— 資料庫：一個檔案 notes.db — schema 是資料的合約（呼應第 04 課）———
const db = new DatabaseSync("notes.db");
db.exec(`
  CREATE TABLE IF NOT EXISTS notes (
    id         INTEGER PRIMARY KEY,             // SQLite 發號，就像 nextId++
    title      TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now'))
  )
`);

// ——— 預備語句（prepared statement）：? 讓資料進不了 SQL 本文 ———
const q = {
  list:   db.prepare("SELECT id, title, created_at FROM notes ORDER BY id"),
  get:    db.prepare("SELECT id, title, created_at FROM notes WHERE id = ?"),
  has:    db.prepare("SELECT 1 FROM notes WHERE id = ?"),
  insert: db.prepare("INSERT INTO notes (title) VALUES (?) RETURNING id, title, created_at"),
  upsert: db.prepare(`INSERT INTO notes (id, title) VALUES (?, ?)
                      ON CONFLICT(id) DO UPDATE SET title = excluded.title
                      RETURNING id, title, created_at`),
  del:    db.prepare("DELETE FROM notes WHERE id = ?"),
};

// ——— 輔助函式、路由表、分派：自第 04 課以來不變 ———
//（readBody、parseJson、json、fail、toRegex、compiled、405 迴圈——從 server4.mjs 貼來）

const routes = [
  { method: "GET", pattern: "/notes", handler: (req, res) =>
      json(res, 200, q.list.all()) },

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const created = q.insert.get(note.title);   // id 由 SQLite 鑄造
      return json(res, 201, created, { location: `/notes/${created.id}` });
  } },

  { method: "GET", pattern: "/notes/:id", handler: (req, res, p) => {
      const note = q.get.get(Number(p.id));
      if (!note) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 200, note);
  } },

  { method: "PUT", pattern: "/notes/:id", handler: async (req, res, p) => {
      const id = Number(p.id);
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const existed = !!q.has.get(id);
      q.upsert.get(id, note.title);               // 寫進 URL 裡的那個 id — 仍然冪等
      return json(res, existed ? 200 : 201, { id, title: note.title }, { location: `/notes/${id}` });
  } },

  { method: "DELETE", pattern: "/notes/:id", handler: (req, res, p) => {
      if (q.del.run(Number(p.id)).changes === 0) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 204);
  } },
];

// … 分派（先路徑後方法、405＋Allow、防護網）——與 server4.mjs 完全相同

四個值得注意的地方

  • INTEGER PRIMARY KEY 接手 nextId++。SQLite 的 rowid 機制在插入時發 id——少一件事要擁有，而且不會相撞。L04 的語意原封度過引擎移植：POST 的 id 仍由伺服器鑄造（不冪等）；PUT 仍寫進 URL 裡的 id，靠 ON CONFLICT … DO UPDATE（冪等——一個 upsert）。
  • ? 就是整套 SQL injection 防禦。資料以參數身分旅行，永遠不進 SQL 本文——所以 a"); DROP TABLE notes;-- 這種標題只是被當成字串存起來（我測過：201，表格完好）。你一旦插值——db.prepare(\`… VALUES ('${title}')\`)——這個標題就會執行。永遠不接字串，任何語言都一樣（OWASP：SQL Injection）。
  • 預備一次，永遠執行。db.prepare() 把 SQL 解析＋規劃一次；.get()/.all()/.run() 帶新參數重用計畫。q 物件裡一行一個語句＝你的資料存取層，全部就這樣（node:sqlite 文件）。
  • schema 是合約——第 04 課的觀念，套到資料上。title TEXT NOT NULL 是 DB 版的我們 400 驗證；DEFAULT (datetime('now')) 是我們不再需要寫的行為。壞資料進不來，不管哪個 bug 想送它進來（SQLite 語言文件）。

實戰練習——親眼看資料活過你的重啟

動手做 · 耐久性、upsert、注入、那個檔案本體
  • 確認 Node：node --version——免旗標的 node:sqlite 要 23+（22.5+ 加 --experimental-sqlite 也行；我在 v26 驗證過）
  • 組出 server5.mjs（server4＋上面的資料層），啟動：node server5.mjs
  • 建立：curl -i -X POST -H "content-type: application/json" -d '{"title":"buy milk"}' http://localhost:3000/notes → 201——注意你一行都沒寫的 created_at
  • 見證時刻：Ctrl-C 關掉伺服器、重啟 node server5.mjs、curl http://localhost:3000/notes → 還在
  • 看檔案：ls -la notes.db——一個 8 KB 檔案就是整個資料庫；sqlite3 notes.db ".schema" 列出你的合約
  • 直接問它：sqlite3 notes.db "SELECT id, title FROM notes WHERE title LIKE '%milk%'"——問題由引擎回答，不是把全部載進 JS（sqlite3 CLI 文件）
  • 注入現場：curl -X POST -H "content-type: application/json" -d '{"title":"a\"); DROP TABLE notes;--"}' http://localhost:3000/notes → 201；列清單——攻擊現在只是一則蠢標題，無害地躺著
  • 合約回歸測試：重跑 L04 的檢查——PUT /notes/7 兩次（201 再 200）、錯動詞 405、壞 JSON 400——引擎換了，合約沒變
  • 重置：rm notes.db 再重啟——空的但活著。你現在確切知道「資料庫」是什麼：一個由你的協定掌管的檔案
