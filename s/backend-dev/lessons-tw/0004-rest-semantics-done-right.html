第 04 課 · REST 語意

把 REST 語意做對

你第 03 課的 API 能動——但方法不對時它回 404，客戶端自己送壞 JSON 它卻回 500。今天把合約（contract）收緊：405＋Allow、冪等的 PUT、201＋Location，加上一個前端能直接 switch 的統一錯誤格式。

約 30 分鐘 動手做 API 設計

為什麼是這一課

誰都回得了 JSON。讓一個 API「前端團隊敢信賴」、而不只是「一個會吐字串的函式」的，是語意：意義固定不變的方法、誠實的狀態碼、機器能據以分支的錯誤。今天你把 server3.mjs 升級成 server4.mjs——四個升級，各約 5 行。它們沒有一個是 Express「附贈」的功能；它們是你親自做的決定。

核心觀念

HTTP 是一份合約，動詞的意義是法定固定的。兩個性質定義每個方法（MDN 方法表 · RFC 9110 §9.2.2）：

方法安全（safe，唯讀）？冪等（idempotent，可重試）？成功碼
GET是是200
POST否否201（＋Location）
PUT否是200 覆寫 / 201 建立
DELETE否是204

安全＝呼叫它什麼都不改變。冪等＝呼叫 N 次後的狀態，和呼叫一次完全相同。這個詞——冪等（idempotent）——就是整課的重點：它讓重試、重新整理、和不穩網路變得可以生存。重試一個冪等呼叫：無害。重試一個 POST：重複扣款、重複註冊、重複的筆記。

程式碼——server4.mjs，四個升級

從 server3.mjs（第 03 課）出發。新行都標了 L04；其他每一段你已經擁有：

import { createServer } from "node:http";

// ——— 資料（先放記憶體；持久化是第 05 課）———
const notes = new Map();
let nextId = 1;

// ——— 輔助函式 ———
function readBody(req) {
  return new Promise((resolve) => {
    let body = "";
    req.on("data", (c) => (body += c));
    req.on("end", () => resolve(body));
  });
}

// L04 (1/4)：回 null 而不是 throw——壞 JSON 才能變 400，不是 500
const parseJson = (raw) => {
  try { return JSON.parse(raw || "{}"); } catch { return null; }
};

function json(res, status, data, headers = {}) {
  res.writeHead(status, { "content-type": "application/json", ...headers });
  res.end(data === undefined ? "" : JSON.stringify(data));
}

// L04 (2/4)：錯誤合約——每個失敗都回這個一模一樣的形狀
function fail(res, status, code, message, headers = {}) {
  json(res, status, { error: { code, message } }, headers);
}

// ——— 路由表 ———
const routes = [
  { method: "GET", pattern: "/notes", handler: (req, res) =>
      json(res, 200, [...notes.values()]) },

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      note.id = nextId++;               // 伺服器發 id → 不冪等
      notes.set(note.id, note);
      return json(res, 201, note, { location: `/notes/${note.id}` });  // L04 (3/4)
  } },

  { method: "GET", pattern: "/notes/:id", handler: (req, res, p) => {
      const note = notes.get(Number(p.id));
      if (!note) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 200, note);
  } },

  { method: "PUT", pattern: "/notes/:id", handler: async (req, res, p) => {
      const id = Number(p.id);
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      const existed = notes.has(id);
      note.id = id;                     // 客戶端指定 id → 覆寫或建立
      notes.set(id, note);              // 同一請求打兩次 → 同一狀態。冪等。
      return json(res, existed ? 200 : 201, note, { location: `/notes/${id}` });
  } },

  { method: "DELETE", pattern: "/notes/:id", handler: (req, res, p) => {
      if (!notes.delete(Number(p.id))) return fail(res, 404, "NOT_FOUND", "note not found");
      json(res, 204);
  } },
];

// "/notes/:id" → /^\/notes\/(?<id>\d+)\/?$/
const toRegex = (pattern) =>
  new RegExp("^" + pattern.replace(/:(\w+)/g, "(?<$1>\\d+)") + "/?$");

const compiled = routes.map((r) => ({ ...r, regex: toRegex(r.pattern) }));

// ——— L04 (4/4)：分派——先配對「路徑」，再配對「方法」———
// 這個順序正是 405 的鑰匙：你得先知道路徑存在，才能說「動詞不對」
const server = createServer(async (req, res) => {
  const { pathname } = new URL(req.url, "http://localhost");
  console.log(`${req.method} ${pathname}`);
  try {
    const allowed = new Set();          // 認得這個路徑的每一個方法
    for (const route of compiled) {
      if (!route.regex.test(pathname)) continue;
      allowed.add(route.method);
      if (req.method !== route.method) continue;
      const match = pathname.match(route.regex);
      return await route.handler(req, res, match.groups ?? {});
    }
    if (allowed.size) {                 // 路徑存在，方法不存在
      const allow = [...allowed].sort().join(", ");
      return fail(res, 405, "METHOD_NOT_ALLOWED", `allowed: ${allow}`, { allow });
    }
    return fail(res, 404, "NOT_FOUND", "no such path");
  } catch (err) {                       // 錯誤防護網（第 03 課）
    console.error(err);
    fail(res, 500, "INTERNAL", "internal error");
  }
});

server.listen(3000, () => console.log("listening on http://localhost:3000"));

三個值得注意的地方

  • 冪等不是關鍵字——它住在「id 從哪來」。POST 讓伺服器配 nextId++，所以一模一樣的重試會建立第二筆筆記。PUT 寫入的是URL 裡的 id，所以一模一樣的重試落在同一筆上。同一個 Map，相反的語意——動詞許下了承諾，而你的程式碼必須兌現它（RFC 9110 §9.2.2）。
  • 405 需要兩個問題，而且有順序。「有沒有任何路由認得這個路徑？」（把它們收進 allowed 這個 Set）——然後「有沒有一個接受這個方法？」路徑存在＋方法不對 → 405，附 Allow 標頭告訴客戶端本來可以用什麼。路徑不存在 → 404。動詞不對卻回 404，等於把一個真實存在的路由藏起來（MDN：405）。
  • 4xx 是「呼叫方的錯」，5xx 是「你的錯」。畸形 JSON 是客戶端的錯——第 03 課回 500（還為一個非 bug 印了嚇人的 stack）；合約上正確的答案是 400。500 留給真正意料之外的事，而且每個錯誤都用同樣的 { error: { code, message } } 形狀，前端就能 switch (body.error.code)，不必去比對訊息字串（MDN：HTTP 狀態碼）。

實戰練習——用 curl 逐一證明四個升級

動手做 · 405、Location、冪等、錯誤合約
  • 存成 server4.mjs，啟動：node server4.mjs
  • 動詞不對：curl -i -X PUT http://localhost:3000/notes → 405＋allow: GET, POST（第 03 課這裡回 404——找出差別）
  • 建立：curl -i -X POST -H "content-type: application/json" -d '{"title":"first"}' http://localhost:3000/notes → 201＋location: /notes/1；再打一次 → 201 帶新 id——POST 刻意不冪等
  • 冪等：curl -i -X PUT -H "content-type: application/json" -d '{"title":"put one"}' http://localhost:3000/notes/7 → 201；一模一樣的 PUT 再打 → 200；curl http://localhost:3000/notes → 仍然恰好一筆 note 7
  • 重試的故事：想像網路吃掉了 PUT 的回應、於是前端重試。說出來——為什麼這樣很安全？同一個故事換成 POST，為什麼就變成重複的筆記？
  • 壞 JSON，升級版：curl -i -X POST -d '{oops' http://localhost:3000/notes → 400 BAD_JSON，log 裡沒有 stack trace（第 03 課這裡回 500）
  • 合約檢查：犯三種不同的錯（動詞不對、路徑不存在、內文空）——確認每個回應都是同樣的 { "error": { "code", "message" } } 形狀，只有 code 不同
  • 讀 MDN 方法表——找到 safe／idempotent 兩欄，對照你伺服器的實際行為
狀態碼方言表（截至目前）
碼意義什麼時候用
200OK成功，帶內文
201Created新資源已誕生——URL 放進 Location
204No Content成功但沒話可說（DELETE）
400Bad Request呼叫方送了垃圾——他們的錯
404Not Found沒有這個資源（路徑或 id）
405Method Not Allowed路徑存在、動詞不對——用 Allow 列出可用的
500Internal Server Error你搞壞的——log 記好，對外什麼都不透露

4xx／5xx 的分界是一枚除錯指南針：4xx → 拿客戶端的請求就能重現；5xx → 去讀伺服器 log。（401/403 第 06 課登場——認證。）
