第 09 課 · 維運

部署與設定：離開筆記電腦

現在，你的 API 只在你的 Mac 醒著的時候存在：localhost:3322、跑在同一台機器 Docker 裡的 Postgres、放在程式碼旁邊的 .env。螢幕蓋上，產品就下線。今天它要搬到一台不屬於你的機器——設定來自環境、資料庫在公開的 socket 後面、前面掛上 HTTPS，再用一個健全狀態檢查（health check）定義什麼叫「活著」。

約 45 分鐘 動手做 維運

為什麼是這一課

第 01–08 課蓋的一切，都建立在一個前提上：你的筆電、醒著、Docker 開著。當 dev server 可以，當產品不行。Mission 說了「ship it：公開的 URL、真的資料庫、有安全感。」從你 Mac 上的 node server7.mjs 到同一份程式碼跑在伺服器上，中間那條縫有名字——部署（deploy）——而它基本上是一個觀念用四種方式呈現：你的機器和雲端之間所有不同的東西，都走環境傳遞，永遠不寫進程式碼。

核心觀念

設定（config）＝每個環境之間會變的東西——連接埠、資料庫 URL、機密（secrets）——而且只在啟動時透過 process.env 進入程式。 同一個 commit 於是可以在你的筆電和 production 上原封不動地跑；環境負責供應差異（經典出處是 twelve-factor 的 Config 原則）。至於部署，就是：把程式碼複製到一台受監督的機器、把設定交給它、在前面掛上 TLS，再用健康檢查證明它活著。

步驟一——連接埠與 URL 不再是常數

你的 server7 已經做到一半了：utils/db.mjs 讀 process.env.DATABASE_URL——那是你在第 06 課蓋的。但連接埠還是常數：

// server7.mjs —— 原本是：const PORT = 3322
const PORT = process.env.PORT ?? 3322

?? 3322 保留所有本地習慣——沒有環境變數，就跟往常同一個埠。在 production，平台指派連接埠，然後用 PORT 交給你；拒絕聽這個埠的伺服器，永遠不會上線。

本地，環境住在 .env（依然沒被追蹤——正確），Node 零依賴就能載入：

$ node --env-file=.env server7.mjs

還缺一道防線。pg.Pool 是懶連線——少了 DATABASE_URL，伺服器照樣開心地啟動，然後在第一個請求上回 500，最糟糕的時機才發現。改成快速失敗（fail fast）：

// utils/db.mjs 最上面
if (!process.env.DATABASE_URL) {
  console.error("DATABASE_URL is not set — refusing to start without a database")
  process.exit(1)
}

啟動時的設定錯誤，是部署 log 裡一行紅字。同一個錯誤若發生在請求時，是一個使用者盯著 500 INTERNAL。兩者出自同一個失誤；只差在時機。

步驟二——資料庫離開筆電

你的 Postgres 是跟伺服器同一台機器上的 Docker 容器。同一顆碟、同一顆電源鈕、同一個單點故障。它搬到託管服務：我們用 Render 的免費方案——不用信用卡，兩下點擊開好一個免費 Postgres。先建資料庫，記下 region，然後拿 Internal Database URL（不是 External）：internal 走平台私有網路——更快，而且不用設 TLS。External URL 也能用，但要加 ?ssl=true。

接著是你第 06 課的 migration runner 等到的那一刻。全新的資料庫會照 commit 的原樣重播你的帳本——utils/migrations/*.sql，不多不少。你曾經直接改在本地資料庫上、卻從來沒寫回 migration 檔的每個 hotfix，都會在這裡回來。這不是找麻煩；這是你的帳本第一次接受誠實的測試。（跑下去就知道了。我讀過你 commit 的 0004_auth.sql——裡面有個東西正等著跟你見面。）

Push 到 main，Render 自動重建、重新部署——git push 就是部署按鈕。盯著第一次部署的 log：npm install、你自己的 migration runner 印出 applying 0001_init.sql…，然後是你自己寫的那行：server is running。同一份程式碼，另一台機器。就這麼簡單。

Render 幫你設好兩件事：PORT（步驟一讓你的伺服器聽它了）和 NODE_ENV=production——步驟五會用到。

步驟四——「活著」的定義：健康檢查

程序活著，不等於服務能用。連線池可能死了、DNS 可能騙人、資料庫可能正在重啟。「活著」是一個主張，主張需要證據：

async function health(_req, res) {
  try {
    await pool.query("SELECT 1")                     // 最深的依賴，最便宜的探針
    return json(res, 200, { ok: true })
  } catch {
    return fail(res, 503, "UNHEALTHY", "database unreachable")
  }
}

// routes：
{ method: "GET", pattern: "/health", handler: health },

注意它檢查的是什麼：不是「檔案載入成功」，而是「我碰得到那個少了就不能工作的東西嗎」。把服務設定裡的 Health Check Path 設成 /health——平台從此輪詢它，把失敗的部署當失敗處理，崩潰的程序會被平台的監督者（supervisor）重啟。那個監督者正是 PaaS 替你做的部分：在 VPS 上，你得自己寫成 systemd unit 或 pm2。練習裡會叫你故意讓伺服器崩潰，親眼看它爬起來。

免費方案的誠實聲明：沒流量約 15 分鐘後，執行個體會休眠（spin down），之後的第一位訪客要等約 1 分鐘的冷啟動（cold start）。健康檢查擋不掉休眠——它擋掉的是說謊。課程 API 夠用；哪天重要了，付費執行個體就是解法。

步驟五——HTTPS 與 Secure 旗標

你的 URL 從第一秒起就是 https://。你一行 TLS 都沒寫——Render 在它的邊緣終結 TLS：瀏覽器 ↔ Render 是帶真憑證的 HTTPS（Let's Encrypt，自動續約），私有網路內部 Render 跟你的程序講純 HTTP。TLS 終結（TLS termination）＝解密發生在代理（proxy），不在你的程式碼裡。跟 VPS 前面掛 nginx 或 Caddy 同一個形狀——某天你會手動設定的東西，今天當功能享用。

HTTPS 替你賺到最後一個 cookie 旗標。第 07 課的 session cookie 是 HttpOnly; SameSite=Lax——加上 Secure，瀏覽器從此拒絕在純 HTTP 上送出它：

const SECURE = process.env.NODE_ENV === "production" ? "; Secure" : ""

return json(res, 200, { id: user.id, email: user.email }, {
  "set-cookie": `sid=${sid}; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800${SECURE}`,
})

為什麼要條件判斷？localhost 沒有 TLS——Secure cookie 永遠不會被送回，本地登入會悄悄壞掉。又一個活在環境裡的決策，而不是程式碼的第二個版本。

四個值得注意的地方

  • 你的 handler 一個都沒改。路由、驗證、權限——原樣部署。這是第 01–08 課在回收本金：從不依賴 localhost 的程式碼，部署起來不必害怕。
  • 部署會重播你的歷史。全新機器：npm install 照 package-lock.json、schema 照 migration 帳本。只存在你筆電上的東西（手工修掉的欄位、在 psql 裡 drop 掉的表），production 一概沒有。repo 是唯一事實來源，否則就沒有任何東西是。
  • 機密是儀表板資料，不是 repo 資料。DATABASE_URL 是憑證——誰讀到它，誰就能讀你使用者的筆記。它住在 Render 的環境設定裡；repo 只保存「它必須存在」的知識（萬一外洩：輪換它，一下點擊，重新部署）。
  • 你的測試跟著你上線。第 08 課的 suite 講純 HTTP——把它的 base 指到 production URL，它審計的就是線上合約，不是本地副本。

  • 讓它睡：放著 15 分鐘以上，再 curl 一次——感受約 1 分鐘的冷啟動，並知道移除它的升級路徑
