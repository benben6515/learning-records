驗證：Session vs Token

HTTP 沒有記憶——所以「呼叫者是誰？」必須騎在每一個請求上。今天：scrypt 密碼雜湊、session 表、HttpOnly cookie、401 vs 403，還有終於有了主人的筆記。然後我們徒手解碼一個 JWT，從此 token 對你不再神秘。

約 45 分鐘 動手做 安全

為什麼是這一課

你用過 Firebase/Supabase 的驗證——登入「就是會動」，然後一個 token 出現。今天你擁有整套機制：註冊使用者、安全地雜湊密碼、發出登入證明、每個請求檢查它、並把資料劃上界線讓 bob 讀不到 alice 的筆記。與第 06 課同一條 stack（Postgres＋server 骨架），四個新端點，零新依賴——密碼學用 Node 內建的 node:crypto。

核心觀念

驗證（authentication）證明你是誰；授權（authorization）決定你能碰什麼——而因為 HTTP 無狀態，兩者都騎在每個請求上。攜帶「誰」有兩種方式：伺服器記得（一列 session＋放在 cookie 裡的 id），或伺服器驗證（客戶端出示一個簽名過的 token）。驗證的世界裡其他一切都是這兩句話的細節（OWASP 驗證 cheat sheet）。

步驟一——migration 0003_auth.sql：users、sessions、所有權

CREATE TABLE users (
  id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,                  // 23505 → 你的 409
  password_hash TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  sid        TEXT PRIMARY KEY,                 // 256 位元隨機數，hex
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL DEFAULT now() + interval '7 days'
);

ALTER TABLE notes ADD COLUMN user_id INTEGER REFERENCES users(id) ON DELETE SET NULL;

(做了第 06 課選配的 0003_add_priority.sql？把這份命名為 0004_auth.sql——runner 只在乎順序。）三條約束已經在替你工作：UNIQUE email、sessions→users 的 REFERENCES、還有由資料庫時鐘（而非你的程式碼）執行的 7 天過期。

步驟二——server7.mjs：雜湊、cookie、劃界

先處理密碼——本課唯一真正危險的一行。雜湊，永遠不加密：加密可逆；雜湊是單向研磨。而且它必須慢——慢是讓暴力窮舉幾十億次猜測變得不划算的特性。Node 內建 scrypt，OWASP 認可的家族：

import { randomBytes, scrypt as _scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";
const scrypt = promisify(_scrypt);                 // 非同步版——scryptSync 會阻塞迴圈（L02！）

async function hashPassword(password) {
  const salt = randomBytes(16).toString("hex");    // 每人獨特——殺死彩虹表
  const hash = (await scrypt(password, salt, 64)).toString("hex");
  return `${salt}:${hash}`;                        // 兩個都存；永遠不存密碼
}
async function verifyPassword(password, stored) {
  const [salt, hash] = stored.split(":");
  const test = await scrypt(password, salt, 64);
  return timingSafeEqual(Buffer.from(hash, "hex"), test);   // 常數時間比較
}

然後是 session 機械——cookie 解析（一個標頭，零依賴）＋每個受保護 handler 都會呼叫的查詢：

const getSid = (req) =>
  (req.headers.cookie || "").split("; ").find((c) => c.startsWith("sid="))?.slice(4);

async function getUser(req) {
  const sid = getSid(req);
  if (!sid) return null;
  const { rows } = await pool.query(
    `SELECT u.id, u.email FROM sessions s
     JOIN users u ON u.id = s.user_id
     WHERE s.sid = $1 AND s.expires_at > now()`, [sid]);
  return rows[0] ?? null;
}

四個值得注意的地方

  • sid 唯一的職責是「猜不到」。256 位元隨機數——沒有簽章、沒有編碼、沒有意義。持有就是證明（像飯店房卡）；伺服器去 sessions 查它，DB 的 expires_at 決定它還開不開得了門（OWASP Session 管理）。
  • HttpOnly＋SameSite=Lax 是兩面不同的盾。HttpOnly 禁止 JavaScript 讀取 cookie——XSS 偷不走它看不見的東西（MDN cookies）。SameSite 阻止瀏覽器跨站自動附帶——解除 CSRF 武裝。（正式環境再加 Secure——限 HTTPS；我們在 localhost。）
  • 401 vs 403 是合約級的區別。401＝「我不認識你」（無效/過期 session）——客戶端該去登入。403＝「認識你，但不行」——bob 要 alice 的筆記；再登入一次也沒用（MDN 401）。我們的錯誤碼直接說明白：UNAUTHENTICATED vs FORBIDDEN。
  • 授權是一條 WHERE。沒有中介魔法：列清單＝WHERE user_id = $1；讀單筆＝先查、再比對主人。你未來讀到的大多數「越權存取」CVE，都是少一條 WHERE 或跳過一次主人檢查——現在你看得到防止它們的那一行。

另一半——JWT，徒手解碼

Token 派把記憶搬到別處：伺服器簽名聲明（user id、到期日），客戶端帶著它；每個請求驗證簽章，而不是查 session。JWT 是三段 base64url——練習裡自己解中間那段，看可讀的 JSON 掉出來：JWT 是簽名的，不是加密的——誰都讀得懂；沒有金鑰誰也改不動（jwt.io 簡介）。

Session vs Token——記憶住在哪
Session＋cookieJWT（Bearer）
伺服器記得？記得——一列 sessions不記得——驗證簽章
能立即撤銷？能——DELETE 那列（logout 有效！）難——等到過期，或養黑名單
憑證被偷…cookie 被偷（HttpOnly 幫忙）token 被偷（常放 localStorage：XSS 讀得到）
擅長場景單一伺服器/來源、傳統網頁多服務免共享 DB 驗證；手機/原生 App

Firebase/Supabase 給你 JWT，因為他們在邊緣驗證——但上面的取捨還是你該懂的。

實戰練習——兩個使用者、一條界線

動手做 · 註冊、登入、劃界、403、登出、解碼 JWT
  • 寫 0003_auth.sql（或 0004），跑 node migrate.mjs——用 docker exec bd-pg psql -U postgres -d notes -c "\d sessions" 檢查
  • 組出 server7（server6＋上面的零件）。埠備註：如果遇到 EADDRINUSE——有東西住在 3000（我驗證時就被一台 Vite dev server 撞過）——換埠，curl 跟著換
  • 註冊：curl -i -X POST -H "content-type: application/json" -d '{"email":"alice@test.dev","password":"correct horse"}' http://localhost:3000/auth/register → 201；同 email 再來 → 409 EMAIL_TAKEN（23505 穿著合約出現）
  • 再註冊 bob。然後三次登入：alice 對密碼（200＋set-cookie: sid=…; HttpOnly; SameSite=Lax）、alice 錯密碼、ghost@…——確認兩個失敗是逐位元組相同的 401
  • 從標頭存下 alice 的 sid；curl -b "sid=ALICE_SID" http://localhost:3000/auth/me → 200；不帶 cookie → 401 UNAUTHENTICATED
  • 自己的筆記：alice POST {"title":"alice secret"} → 201；bob 登入，GET /notes → []——他的清單，不是她的；那列資料是看不見，不是被藏起來
  • 界線：bob GET alice 的 note id → 403 {"code":"FORBIDDEN"}；bob DELETE → 403。bob 重新登入——仍然 403：403 ≠ 401
  • 登出：curl -i -X POST -b "sid=ALICE_SID" http://localhost:3000/auth/logout → 204＋cookie 清空；重用舊 sid → 401——撤銷就是一條 DELETE，這是 session 的勝利
  • 看機密：docker exec bd-pg psql -U postgres -d notes -c "SELECT email, left(password_hash,20) FROM users;"——salt+hash 亂碼；任何地方都不存在 password 欄
  • 徒手解碼 JWT：從 jwt.io 拿任意 token，切開點點、echo "中段" | base64 -d——你剛讀完一個「安全」token 的聲明。簽名 ≠ 加密，從此永遠
