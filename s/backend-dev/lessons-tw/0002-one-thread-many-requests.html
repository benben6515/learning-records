第 02 課 · 事件迴圈

一個執行緒，多個請求

你第 01 課的伺服器只是一個 JavaScript 函式——而它仍能同時服務數百個請求。今天你要親眼看到這個把戲成立，再親眼看到它垮掉。

約 30 分鐘 動手做 Node.js

為什麼是這一課

任務宣言說沒有任何一層是魔法。上一課你建造了伺服器；這一課你見到呼叫你那個函式的引擎。這就是「我會用 async/await」與「我知道為什麼某個使用者上傳大檔案時，整個 API 會凍住三秒」的差別。

核心觀念

你的 JavaScript 只跑在一個呼叫堆疊（call stack）上——一個執行緒。但耗時的工作不是。計時器、磁碟、socket、DNS：Node 把這些交給作業系統與一小組工作執行緒（libuv，隨 Node 內建）。工作完成後，它的回呼（callback）進入佇列，事件迴圈（event loop）再把它推回堆疊——但只在堆疊清空之後。

1 · 你的 handler 在堆疊上執行 → 2 · 向 Node 發出耗時 I/O → 3 · handler 返回、堆疊清空
4 · I/O 在執行緒外完成 → 5 · 回呼在佇列排隊 → 6 · 迴圈把它放上堆疊

這個模型你早就認識——它就是瀏覽器的事件迴圈，搬到了伺服器（MDN：Event loop）。同樣的單一堆疊、同樣的佇列，只是 Node 讓它面對 socket 與磁碟，而非 DOM。

四條規則

  1. 一次一件事。你所有的 JS 都在同一個呼叫堆疊上執行。
  2. I/O 在別處跑。等待發生在執行緒之外（OS 非同步 API＋libuv 執行緒池，預設 4 條）。
  3. 迴圈要等安靜。佇列裡的回呼，只在堆疊清空時才會被執行。
  4. 所以一個同步大戶堵住所有人。3 秒的同步迴圈會凍住每一個請求——新的、舊的都一樣。這不是 Node 的 bug，這是第 3 條規則一字不差的後果（Node 官方：The Node.js Event Loop）。
為什麼這樣能擴展

對 I/O 密集的工作，CPU 在每次等待時都閒著——所以一條執行緒加上非同步 I/O，就能同時撐住數千個等待。代價是：遇到 CPU 密集工作（影像處理、超大 JSON、加密），單執行緒就是瓶頸——解法是 worker threads 或佇列，之後的課再談。

程式碼——三個端點，一個真相

存在第 01 課檔案的旁邊，取名 server2.mjs：

import { createServer } from "node:http";

const server = createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");

  // GET /hello — 瞬間完成，純同步，幾個微秒
  if (req.method === "GET" && url.pathname === "/hello") {
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ msg: "hello" }));
    return;
  }

  // GET /work?ms=3000 — 3 秒的同步 CPU 工作。整台伺服器被堵住。
  if (req.method === "GET" && url.pathname === "/work") {
    const ms = Number(url.searchParams.get("ms") ?? 3000);
    const start = Date.now();
    while (Date.now() - start < ms) {}   // 忙等：事件迴圈整個凍結
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ blockedForMs: Date.now() - start }));
    return;
  }

  // GET /idle?ms=3000 — 3 秒的非同步等待。誰也不堵。
  if (req.method === "GET" && url.pathname === "/idle") {
    const ms = Number(url.searchParams.get("ms") ?? 3000);
    setTimeout(() => {
      res.writeHead(200, { "content-type": "application/json" });
      res.end(JSON.stringify({ waitedMs: ms }));
    }, ms);                              // 計時器在 JS 之外跑；我們現在就返回
    return;
  }

  res.writeHead(404);
  res.end();
});

server.listen(3000, () => console.log("listening on http://localhost:3000"));

/work 與 /idle 唯一的差別，是那三秒發生在哪裡：堆疊上，還是堆疊外。一樣的延遲，相反的爆炸半徑。

實戰練習——看它垮掉，再看它撐住

動手做 · 兩個終端機、三秒鐘、一個頓悟

時間就是回饋：-w "%{time_total}" 會印出每個請求花了多久。看數字，不要看程式碼。

  • 存檔並啟動：node server2.mjs——先量基準：curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/hello → 幾毫秒
  • 終端機 A：curl "http://localhost:3000/work?ms=3000"（3 秒同步工作——先別按任何東西）
  • 立刻在終端機 B：再量一次 /hello → 約 3 秒。整台伺服器被一個請求凍住了
  • 換解藥：終端機 A：curl "http://localhost:3000/idle?ms=3000"（3 秒非同步等待）
  • 等待期間，終端機 B：量 /hello → 幾毫秒。一樣三秒，零波及
  • 各用一句話大聲說出來：步驟 3 為什麼卡？步驟 5 為什麼不卡？（說得出來，第 3 條規則就是你的了）
你剛剛證明了什麼

「Node 很快，因為它是非同步的」只是口號。你現在握有機制：非同步意味著堆疊會清空，迴圈才能繼續服務。任何霸佔堆疊的同步程式——while 迴圈、fs.readFileSync、對 100 MB payload 的 JSON.parse、crypto.pbkdf2Sync——都會讓店裡所有其他請求一起停擺。

日後的細節：promise 的回呼（.then）是微任務（microtask）——會插隊到計時器之前。混用時順序才有影響；準備好時，官方 event-loop 指南講得很清楚。
