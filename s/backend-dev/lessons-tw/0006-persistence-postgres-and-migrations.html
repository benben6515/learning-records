第 06 課 · 持久化 II

持久化 II：PostgreSQL 與 Migration

SQLite 是你信任在程序內的檔案。PostgreSQL 是住在socket 後面的資料——獨立伺服器、真正的型別、多個並發寫入者——schema 也演化成一份份有版本的檔案。今天：Docker、連線字串、30 行的 migration 工具，以及又一次「同一份合約」的 server6。

約 45 分鐘 動手做 資料

為什麼是這一課

第 05 課的 DatabaseSync 跑在你的程序裡——一個寫入者、一台機器。真實後端的資料跨程序、跨部署、跨機器共享，所以資料庫必須自己是個程序、透過網路連線。這個翻轉改變你今天碰到的每樣東西：連線字串取代檔名、非同步查詢取代同步呼叫（第 02 課，又見面了）、還有——因為你再也不能隨手改 CREATE TABLE——migration：schema 的變更成為有序、有版本、只跑一次的檔案。

核心觀念

PostgreSQL 是伺服器；你的程式碼從此是它的客戶端。同一份 CRUD 合約（L03–L05，原封不動），但引擎住在另一個程序裡——這裡用 Docker 容器扮演「另一台機器」。兩個後果：第一，每個查詢都跨網路，所以要非同步發問、要池化連線（pg Pool 文件）；第二，schema 不能再隨手改——它是有歷史的共享狀態，變更因此成為 migration。

步驟零——資料庫即「另一台機器」

$ docker run -d --name bd-pg \
    -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=notes \
    -p 5432:5432 postgres:17-alpine        // 伺服器，在你機器上，裝在箱子裡

$ docker exec bd-pg pg_isready -U postgres  // accepting connections

還有每個後端 repo 都有的一行——連線字串，一條 URL 講完五件事：

postgres://postgres:dev@localhost:5432/notes
//        └─ 帳號 ─┘└密碼┘ └主機┘└埠┘└─ 資料庫

這是課程的第一個依賴——前五課零 npm 是故意的：

$ npm init -y && npm install pg

步驟一——migration：schema 變更即檔案

migrations/0001_init.sql——notes 表誕生（對照 L05：TIMESTAMPTZ 取代 TEXT、IDENTITY 取代裸的 INTEGER PRIMARY KEY、還多一條引擎強制執行的 CHECK）：

CREATE TABLE IF NOT EXISTS notes (
  id         INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title      TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

migrations/0002_add_done.sql——schema 會演化；既有資料活下來：

ALTER TABLE notes ADD COLUMN done BOOLEAN NOT NULL DEFAULT false;

以及整套「migration 工具」——一張帳本表、排序過的檔案、每份一筆交易（CREATE TABLE 文件）：

import { readdirSync, readFileSync } from "node:fs";
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

await pool.query(`CREATE TABLE IF NOT EXISTS schema_migrations (
  name TEXT PRIMARY KEY,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
)`);

const applied = new Set(
  (await pool.query("SELECT name FROM schema_migrations")).rows.map((r) => r.name)
);
const files = readdirSync("migrations").filter((f) => f.endsWith(".sql")).sort();

for (const f of files) {
  if (applied.has(f)) continue;
  console.log("applying", f);
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query(readFileSync(`migrations/${f}`, "utf8"));
    await client.query("INSERT INTO schema_migrations (name) VALUES ($1)", [f]);
    await client.query("COMMIT");               // 兩行都發生，或都不發生
  } catch (err) {
    await client.query("ROLLBACK");
    console.error(`${f} failed — rolled back:`, err.message);
    process.exit(1);
  } finally {
    client.release();
  }
}

await pool.end();
console.log("up to date");

node migrate.mjs 先套用 0001 再 0002；再跑一次只印 up to date——帳本記得。那個 try/ROLLBACK 是錯誤防護網（L03）戴上資料庫帽子：失敗的 migration 不會留下半套 schema。

步驟二——server6.mjs：同一份合約，網路引擎

路由、分派、405、防護網：與 L04/L05 一字不差。資料層現在是字串＋$1 參數＋await（? 換了衣服；規則沒換）：

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

const q = {
  list:   "SELECT id, title, done, created_at FROM notes ORDER BY id",
  get:    "SELECT id, title, done, created_at FROM notes WHERE id = $1",
  has:    "SELECT 1 FROM notes WHERE id = $1",
  insert: "INSERT INTO notes (title) VALUES ($1) RETURNING id, title, done, created_at",
  upsert: `INSERT INTO notes (id, title) VALUES ($1, $2)
           ON CONFLICT (id) DO UPDATE SET title = excluded.title
           RETURNING id, title, done, created_at`,
  del:    "DELETE FROM notes WHERE id = $1",
};

// handler 換了形狀：(await pool.query(q.list)).rows —— rows[] 是新的 .all()

  { method: "POST", pattern: "/notes", handler: async (req, res) => {
      const note = parseJson(await readBody(req));
      if (note === null) return fail(res, 400, "BAD_JSON", "body is not valid JSON");
      if (!note.title) return fail(res, 400, "VALIDATION", "title is required");
      try {
        const created = (await pool.query(q.insert, [note.title])).rows[0];
        return json(res, 201, created, { location: `/notes/${created.id}` });

四個值得注意的地方

  • 所有東西都要 await 了——事件迴圈感謝你。每個查詢都是網路 I/O；同步的 DatabaseSync 呼叫會凍住每個請求（L02 的規則）。Pool 保溫幾條 TCP 連線，查詢不必每次付連線成本——你池化的是連線，不是結果（Pool 文件）。
  • 資料庫現在強制執行你以前手動檢查的型別與規則。TIMESTAMPTZ 存真正的時刻＋時區（文件）——API 現在回 2026-09-08T03:30:22.111Z，不是 SQLite 的 TEXT。標題長度的 CHECK 由引擎強制；handler 只是把錯誤碼 23514 翻成合約的 400（錯誤碼附錄）。縱深防禦：你的 400 檢查和 DB 的 CHECK 都會跑。
  • Migration 是 schema 的 git 歷史。有編號、有順序、只跑一次。新同事？node migrate.mjs 按順序蓋出完整 schema。要改？新檔案——永遠不改已套用的（帳本不會重跑，隊友的資料庫也會分岔）。
  • 並發寫入就這麼……動了。server6 跑著的同時，docker exec … psql——第二個客戶端——插入一列；兩邊看到一致的世界。那是 MVCC，PostgreSQL 的並發機械，做著 SQLite 單一寫入者鎖做不到的事（MVCC 章節）。我實測的另一個真實細節：id 回來是 1, 4, 7——兩次被 CHECK 拒絕的插入仍然燒掉了序號。Identity id 保證唯一，不保證連續；別把邏輯蓋在「連續」上。

實戰練習——整條stack都自己來

動手做 · 容器、migration、合約、第二寫入者
  • 啟動「另一台機器」：docker run -d --name bd-pg -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=notes -p 5432:5432 postgres:17-alpine，然後 docker exec bd-pg pg_isready -U postgres（映像檔文件）
  • 專案：npm init -y && npm install pg；export DATABASE_URL=postgres://postgres:dev@localhost:5432/notes；寫上面兩份 migration＋migrate.mjs
  • node migrate.mjs 跑兩次——第一次套用 0001、0002；第二次印 up to date。看帳本：docker exec bd-pg psql -U postgres -d notes -c "SELECT * FROM schema_migrations;"
  • 組出 server6.mjs（server5＋網路資料層），啟動：node server6.mjs
  • 建立：curl -i -X POST -H "content-type: application/json" -d '{"title":"buy milk"}' http://localhost:3000/notes → 201；注意 done:false（誕生於 migration 0002）和真正的 ISO 時間戳
  • 引擎強制規則：POST 一個 250 字標題 → 400 VALIDATION "title must be 1–200 chars"——這條規則你的 handler 一行都沒寫；DB 丟 23514，handler 翻譯
  • 合約回歸：PUT /notes/7 兩次（201、200）、錯動詞 405、壞 JSON 400——第三顆引擎，同樣的承諾
  • 並發寫入：伺服器跑著的同時，docker exec bd-pg psql -U postgres -d notes -t -c "INSERT INTO notes (title) VALUES ('from psql');" → GET /notes 看到兩個寫入者的列——沒有鎖、沒有戲
  • 寫你自己的 migrations/0003_add_priority.sql（ALTER TABLE notes ADD COLUMN priority INTEGER NOT NULL DEFAULT 0;），重跑 runner，確認只套用 0003
  • 拆掉重建：docker rm -f bd-pg，重跑 docker run＋migrate＋server——整條 stack 從兩份 migration 檔重建。可重現性就是重點
