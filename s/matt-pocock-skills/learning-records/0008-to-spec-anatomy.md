# `to-spec` — synthesize, never interview

`to-spec` takes the conversation `grill-with-docs` already finished and **freezes** it into a fixed-shape spec (a PRD). The whole skill lives in one contrast with its upstream partner: **`grill-with-docs` interviews** (one question at a time, decisions stay yours, builds the glossary + ADRs); **`to-spec` synthesizes** (zero decision-questions, just writes what's settled). Same conversation, opposite jobs. The frontmatter makes this literal — `disable-model-invocation: true` — so the skill is structurally user-triggered and its prose opens with "Do NOT interview the user — just synthesize what you already know." If `to-spec` starts asking *decision* questions ("what should happen when the bitmask overflows?"), the grilling upstream was skipped or under-cooked — stop and go grill; never fake a decision into the spec.

**The anatomy is fixed — you fill it, you don't invent it.** Seven sections: **Problem Statement** + **Solution** (both from the *user's* perspective, in glossary vocabulary); **User Stories** — the SKILL.md's actual word is *"extremely extensive,"* a LONG numbered list of `As an <actor>, I want <feature>, so that <benefit>` covering all aspects (the list IS the spec's completeness check); **Implementation Decisions** — modules, interfaces, schema, API contracts, architectural choices — **no file paths or code snippets** (they rot); **Testing Decisions** — external behaviour only, which modules, prior art; **Out of Scope**; **Further Notes**. Every term in Problem/Solution/Stories must trace to a `CONTEXT.md` entry — reaching for an undefined word is the signal to either coin it (run `domain-modeling`) or admit you're drifting from the ubiquitous language. This is where Lesson 5's glossary discipline gets *enforced*: the spec is the file that catches vocabulary drift.

**The test-seam rule — the counterintuitive one.** Before writing, sketch the seams at which the feature will be tested. The rule that breaks instinct: **prefer existing seams over new ones; use the *highest* (most external) seam possible; the fewer seams the better — the ideal number is one.** "Fewer is better" feels wrong because instinct screams "more tests = safer," but each seam is a *coupling point* — five unit tests pinned to internal functions shatter on every refactor, while one test through a high boundary (full request→response, or the rendered UI) gives confidence with minimal brittleness. "The interface is the test surface." One high seam beats many low ones.

**Evidence:** free-recall — stated the load-bearing contrast (grill interviews / to-spec synthesizes) and the frontmatter mechanism (`disable-model-invocation`); on the three-rule "spot the broken rule" drill, named all three correctly: #1 ("what about overflow?" — a question) breaks *synthesize-don't-interview*; #2 (`src/utils/permissions.js` path) breaks *no file paths/code*; #3 (unit-test the internal `bitPositions()` helper) breaks the *seam rule* — should test external behaviour through one high seam, not a low internal function.

**Nuance sharpened from the primary source (the lesson's "zero questions" is imprecise):** the SKILL.md Step 2 ends with an explicit **"Check with the user that these seams match their expectations"** — *before* writing. So "zero questions" scopes only to *decisions/requirements* (those belong to grill); `to-spec` does ask exactly one thing — "does my seam sketch match what you expect?" That's a *confirmation of a synthesis product*, not a re-opened decision. The reconciliation: the question's *content* doesn't matter, its *existence-at-this-stage-about-a-decision* is the tell. A seam check is fair game; a "what should we do?" is not.

**Second precision worth pinning — the prototype exception to "no code":** a snippet IS allowed when it *encodes a decision more precisely than prose* — a state machine, reducer, schema, or type shape from a prior `prototype` run. Inline it, trimmed to the decision-rich parts (not a working demo). The rule isn't "no code ever," it's "no code that *rottenly describes implementation*"; decision-encoding code survives because prose literally can't say it as well.

**Implications:** Lesson 8 — `to-tickets`, the last stop of the spec-driven spine (awareness level). The `ready-for-agent` label `to-spec` slaps on the published issue is *literally* `to-tickets`'s input: a multi-session build runs `to-tickets` to split the spec into blocker-ordered tracer-bullet tickets; a single-session build skips straight to `implement`. And per Lesson 1/3 — no extra triage on your own output; the label is the hand-off.
