設定與分級

跑一次的前置條件，以及處理原始議題的入口坡道。

兩個技能坐在議題追蹤器的邊界上：一個設定它，一個處理掉進它裡面的東西。

/setup-matt-pocock-skills——跑一次的前置條件

在每個 repo 跑一次，而且是在任何其他工程技能之前。它寫的是設定檔——不硬編行為。三個決定，各有一個你能一個字接受的建議答案：

  • 議題追蹤器——議題住哪裡（GitHub、GitLab、本地 .scratch/ markdown，或其他）。它會提議符合你 git remote 的那一個。
  • 分級標籤——只有裝了 triage 才問。保留預設值（needs-triage、needs-info、ready-for-agent、ready-for-human、wontfix），除非你的追蹤器已用別的字串。
  • 領域文件——單一情境（根目錄一份 CONTEXT.md + docs/adr/）幾乎適用每個 repo；只有當它嗅到 monorepo 訊號時才用多情境。

產出：docs/agents/ 底下的檔案（issue-tracker.md、domain.md，以及裝了 triage 時的 triage-labels.md）+ 你的 CLAUDE.md 或 AGENTS.md 裡一段 ## Agent skills 區塊。若 triage／to-spec／to-tickets 開始猜你的議題住哪，就是你跳過了這一步。

/triage——處理原始進來的議題

主流程的一個入口坡道。當 bug 回報與功能請求堆積如山，triage 把它們推過一套小型的角色狀態機，並留下一份代理可直接施工的簡報。

每項兩個角色，絕不零個或兩個以上

每個分級項目都帶恰好一個分類角色（bug／enhancement）和一個狀態角色（needs-triage、needs-info、ready-for-agent、ready-for-human、wontfix）。它建議並等待——告訴你它的判斷與理由，只在你指示下才動作。

先驗證，再寫簡報

這一步把 triage 與隨手貼標籤區分開來。它會照回報者的步驟重現 bug，或 checkout 那個 PR 並跑測試。以一條程式碼路徑確認 → 強簡報；失敗或細節不足 → needs-info。它還會跑兩道程式庫檢查：冗餘（已實作 → wontfix）與先前已否決（.out-of-scope/ 早已說不）。

一個 PR 就是一個附帶程式碼的議題

當追蹤器把外部 PR 當作請求介面，triage 會把它們推過同一套機器——狀態只是改對著 diff 來讀。ready-for-agent＝附上了一份簡報，代理接下下一步；ready-for-human＝可以合併了。

什麼時候不要 triage triage 只用在不是你建立的議題——原始的 bug 回報、進來的功能請求。/to-tickets 產出的票早已是代理可直接施工的，所以別 triage 它們。分級你自己的票是白做工。
