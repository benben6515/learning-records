實作、審查與收尾

implement 負責建造（一張票一張票來，或一次跑完整份規格）；code-review 在兩條軸線上評判；pr 塑造 PR；retro 把迴圈閉起來。

主流程的建造與收尾段：/implement 或 /implement-spec 建造，/code-review 評判，/pr 塑造 pull request，/retro 把迴圈閉起來。

/implement——是手，不是腦

它建造規格或一組票所描述的工作——驅動 /tdd、型別檢查與完整測試套件，然後交給審查並提交到當前分支。

它不決定要建什麼 規格早已談定，接縫也早已議定。implement 執行那份計畫，而不是重新開啟它。思考發生在上游——在 grill-with-docs 與 to-spec 裡。若規格還不存在，先去寫規格。

預先議定的接縫

implement 運作所依的觀念是接縫（seam）——一道穩定的介面，是一道功能接受測試之處，且是在寫任何程式碼之前就（在 to-spec 期間）選定的。它不會在施工中途發明接縫；它用的是已經挑好的那些，並透過 tdd 針對它們寫測試。在預先議定的接縫上施工，正是讓實作保持誠實的關鍵：測試針對的是某個耐久的東西，所以底下的程式碼可以移動，而測試不必跟著移動。

在那個核心之外，它把迴圈維持得很緊——經常型別檢查、邊做邊跑單一測試檔、最後跑一次整套套件——然後以一次審查與一次提交收尾。

/implement-spec——一次跑完整份規格

逐張票自己開的並行替代方案。你已經跑過 /to-spec 與 /to-tickets；這時改用 /implement-spec（user-invoked）一次跑完整份規格：

  • 它把票讀成任務圖（task graph）而非清單——阻塞邊定義出可立即開工的frontier。
  • 它在 frontier 上並行派出implementer 子代理，各自在自己的 worktree、自己的分支上施工，都用 tdd 建票。一張票合併後，新解鎖的票就孵化新的子代理。
  • 全部落在一條整合分支（integration branch）上；只有當追蹤器以 PR 收案（或你要求）時，才在第一次合併後開 draft PR。否則就用追蹤器收案的方式結掉每張票。
  • 最後對整合分支跑一次 /code-review，並用單一 implementer 子代理修掉審查提出的所有問題。
選哪個？ 想留在迴圈裡、親自判斷每一片？逐張 /implement，每張全新上下文。想當指揮、讓並行替你等？/implement-spec。同一批票、同一批接縫——差別只在誰開車。

/code-review——兩條軸線，絕不混併

它審查 HEAD 與你給定的某個固定基準點（commit、分支、tag、merge-base）之間的 diff，沿著兩條分開的軸線，以並行子代理執行，好讓兩者不污染彼此的上下文：

軸線問題來源
Standards（標準）它建得對嗎？它是否遵循這個 repo 寫程式的方式？CODING_STANDARDS.md／CONTRIBUTING.md + 一份約 12 項 Fowler 壞味道的固定基線（Mysterious Name、Duplicated Code、Feature Envy、Data Clumps……）
Spec（規格）它是對的東西嗎？它是否做了該 issue／規格所要求的？原始的 issue 或規格（由 setup 接好的議題追蹤器）
為什麼絕不混併 一項變更可能通過其中一條軸線、卻在另一條失敗。單一個混合判決會讓其中一條掩蓋另一條。所以報告把它們放在分開的 ## Standards 與 ## Spec 標題之下，各自帶摘要。這裡刻意不有個橫跨兩軸的單一贏家。

兩條規則守住 Standards 基線

  • 一份有文件紀錄的 repo 標準，永遠優先於 Fowler 基線。
  • 每一個壞味道都是判斷題，絕不是硬性違規。

沒有規格 → Spec 軸線跳過

Spec 軸線需要某個能找到原始規格的地方——commit 訊息裡的 issue 引用、你傳入的路徑，或是 docs/／specs/ 底下的規格。沒有的話，它回報「找不到可用規格」，而不是憑空發明需求。Standards 軸線什麼都不必設定——它永遠帶著內建的 Fowler 壞味道基線。

/pr——pull request 本文的形狀

model-invoked：當成果開成 PR，代理會自己抓它來用。本文有三個固定部分：

  • Summary——能讓改動一目瞭然的最小視覺：一張圖、一份 diff 草圖、一棵呼叫樹、一個檔案樹——哪個能一眼呈現形狀就用哪個。
  • Evidence——改前／改後：失敗的執行或截圖，接著通過的那個。是「證明它會動」，不是「宣稱它會動」。
  • Merge Danger——判定單向門或雙向門，外加一個詞的爆炸半徑。合併之後還回得了頭嗎？它碰到哪些地方？

/retro——主流程的最後一步

user-invoked；在它回顧的那個 session 裡跑，清空之前先跑（清空之後，改指向那個 session 的紀錄）。它回顧整個寫程式的 session，對代理的環境（而非程式碼）提出改進：

  • 導覽指針——代理花太久才找到某樣東西；留一個指針。
  • 自動化檢查——一個自動化檢查本可抓住的錯誤，變成 linter 規則、pre-commit hook 或 CI job。整個 repo 連一道防護欄都沒有，本身就是一條發現。
  • Coding standards——機械性違規變成確定性檢查，絕不寫成散文規則；CODING_STANDARDS.md 只留給審查代理該執行的真正判斷題。
  • Steering files、工具經濟、資訊存取——剪掉無效指令、精簡昂貴的工具呼叫、把缺的資訊接出來。
機械性錯誤變成確定性檢查。判斷題變成 coding standards。下一次建構從更好的環境出發。
向老師提問 卡住了或好奇？儘管追問——任何不清楚的地方都可以問。
