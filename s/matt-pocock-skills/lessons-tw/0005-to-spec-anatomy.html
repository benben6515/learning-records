to-spec — 規格解剖

它凍結對話。它不訪談。

你現在已經備齊規格所依據的兩份產物——詞彙表與ADR。to-spec 就是它們匯流之處：它把你在 grill-with-docs 已經談過的對話，凍結成一份固定形狀的規格（PRD），讓 implement 可以照著施工。整個技能就活在這一組對比裡：

一個核心觀念

grill-with-docs
訪談。一次一題。決策歸你。建立詞彙表 + ADR。
to-spec
綜合。零個問題。只把你已談定的東西寫下來。凍結成規格。
同一場對話 · 截然不同的職責
如果 to-spec 開始問你問題，就是上游出了問題——你跳過了、或沒把盤問煮夠。停下來去盤問；別在規格裡捏造一個決策。

解剖（固定形狀）

每份規格都有相同的段落。你不是在發明結構——你是在填它：

  • 問題陳述與解決方案——都從使用者的觀點出發，用詞彙表的用語。
  • 使用者故事——一份冗長的編號清單：「作為一個 <角色>，我想要 <功能>，以便 <效益>」。要涵蓋所有面向。
  • 實作決策——模組、介面、結構描述（schema）、API 合約。不含檔案路徑或程式碼片段（它們會腐朽）。
  • 測試決策——只測外部行為、不測內部細節；測哪些模組；前例。
  • 不在範圍內與補充說明。

接縫規則 — 那條違反直覺的

動手寫之前，to-spec 會先勾勒接縫（seam）——也就是這個功能將被測試的施力點。接縫就是測試的插入點。那條令人意外的規則：

接縫規則 優先用既有接縫，而非新接縫。盡可能用最高（最外部）的接縫。接縫越少越好——理想值是一個。

直覺大喊「測越多越安全」時，為什麼「越少越好」？因為每個接縫都是一個耦合點。從一個高層邊界測整個功能（例如完整的請求→回應流程，或渲染後的 UI），能用最少的脆弱度換來信心。五個釘在內部函式上的單元測試，每次重構都會壞——而「介面就是測試面」。一個高接縫，勝過多個低接縫。

你的具體收穫 — 找出被破壞的規則

每個片段都破了三條規則之一。說出是哪一條。

  1. 規格開頭：「在我寫下來之前——當位元遮罩溢位時該發生什麼事？」
  2. 一則實作決策寫著：「修改 src/utils/permissions.js 裡的 parsePermissionBits()，讓它回傳各個位元的位置。」
  3. 一則測試決策寫著：「單獨對內部的 bitPositions() 幫手函式做單元測試。」

答案：#1 破了綜合而非訪談（它是個問題 → 那是盤問的活）。#2 破了不含檔案路徑／程式碼。#3 破了接縫規則——它在測一個低階的內部函式，而不是透過一個高接縫測外部行為。推理過程見參考文件。

它在流程裡的位置

grill-with-docs → to-spec → 議題 · ready-for-agent → implement

to-spec 會把規格連同 ready-for-agent 標籤一起發布——不再額外分級（第 1 課：別分級你自己的產出）。從這裡起，多回合的建構會先跑 to-tickets；單回合的建構則直接進 implement。
