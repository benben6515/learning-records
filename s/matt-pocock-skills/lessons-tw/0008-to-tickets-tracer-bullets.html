to-tickets — 曳光彈與前緣

規格驅動主幹的最後一站。一份規格變成一套讓代理能在全新視窗中施工的票。

在第 7 課裡，你把對話凍結成了一份規格。to-tickets 接手這份規格，把它拆成票（tickets）——每一張都是一個獨立、可展示的切片，讓一個全新的 implement 工作階段能靠自己的力量把它蓋起來。這是認識層級：你要等到第一次真正的多工作階段建構時，才會真正演練它。但這個心智模型很小，現在就值得握住，因為它正是第 3 課那條「每個 implement 用全新視窗」規則之所以行得通的原因。

一個核心觀念：曳光彈是一道垂直切片

每一張票都切出一條窄但完整、貫穿每一層的路徑——結構描述（schema）、API、UI、測試。垂直，不是水平。自己就能展示。大小塞進一個上下文視窗。

讓人卡住的字是垂直（vertical）。直覺會想按層來切——「先把所有結構描述做完，再把所有 API 做完，再把所有 UI 做完。」那是一道水平（horizontal）切片，在這裡是錯的：沒有任何東西能展示，直到最後一層落地才行。曳光彈（tracer bullet）則相反，它針對一小條薄的行為，端到端貫穿所有層：

水平切片（避免）垂直切片／曳光彈（以此為目標）
「把整個授權結構描述蓋出來。」
無法單獨展示。		 「使用者能登入並看到一個受保護的頁面，端到端。」
一落地就能展示。
「把整個側邊欄 UI 蓋出來。」 「選單依 permissionBits 位元遮罩過濾其項目，端到端。」
先預重構 切票時，留意是否有機會預重構（prefactor）——「先讓變更容易，再做那個容易的變更」。任何預重構都會變成它自己的一張（或多張）前置票，讓後面的切片依附其上。

阻塞邊與前緣

每一張票都會宣告它的阻塞邊（blocking edges）——也就是必須先完成、它才能開工的其他票。沒有阻塞的票可以立刻開工。所有目前未被阻塞的票所成的集合，稱為前緣（frontier），而你永遠只做前緣上的票：

T1 · 登入端到端
↓ 阻塞
T2 · 選單依 permissionBits 過濾
↓ 阻塞
T3 · 依角色的選單管理
開工：前緣 = {T1} · T1 收掉後：{T2} · T2 收掉後：{T3}

這正是接回第 3 課的橋樑。因為票是各自獨立的垂直切片，而且帶有明確的阻塞邊，所以每一個 implement 都能全新開始、只讀自己的那張票、做前緣上的事，而不會打亂其他工作階段。那條「不中斷視窗」規則（grill → spec → tickets）之所以存在，正是為了在思考還熱的時候把這些邊捕捉下來——之後再讓施工扇出到一個個乾淨、各自獨立的視窗。

你至少該認得的例外

並非所有東西都是曳光彈。一次大範圍重構（wide refactor）——一個機械性的變更，其爆炸半徑橫跨整個程式庫（改一個欄位名、改一個共用符號的型別）——沒辦法用單一一條垂直切片就讓它綠燈落地，因為一次編輯會同時弄壞成千上萬個呼叫點。硬把它塞進曳光彈，只會做出一個壞掉的建構。

大範圍重構 → 擴充–收縮 別把它做成曳光彈。把它排成序列：擴充（expand：在舊形式旁邊加上新形式，什麼都不壞）→ 分批遷移（migrate）呼叫點，每一批是一張自己的票，CI 之所以維持綠燈，是因為舊形式還在 → 收縮（contract：一旦沒有呼叫者了，就刪掉舊形式）。目前你只需要認得這種情況就好；真正的手續，等你撞上再說。

它如何發布

to-tickets 為每個項目寫一張票，依相依順序（阻塞者在前）。邊的形態，取決於 setup-matt-pocock-skills 為你的 repo 設定了什麼：

  • 本地檔案 → 每張票一個檔案，放在 .scratch/<feature>/issues/NN-slug.md 之下，以文字寫「Blocked by」。（你的專案用 GitHub，所以這不是你——但這是單人／無遠端的途徑。）
  • 真實追蹤器（GitHub、Linear……） → 每張票一個 issue，使用平台原生的阻塞／子議題連結。這才是你的途徑。每張票會拿到 ready-for-agent 標籤——天生就能被代理抓取，不必分級。

與規格同一條規則：票裡不放檔案路徑或程式碼片段（它們會腐朽）——除了能編碼決策的原型。

你的具體收穫 — 把這些說出口

  1. 用一句話定義曳光彈（四個性質：垂直、貫穿所有層而完整、可展示、塞進一個上下文視窗）。
  2. 為什麼水平切片在這裡是錯的？
  3. 什麼是前緣（frontier）？為什麼把阻塞邊寫明，就能讓每個 implement 全新地跑？
  4. 說出唯一一種不是曳光彈的情況，以及處理它的模式。

認識層級——若你能答出這些，模型就到手了。真正的演練，等你第一次在自己的專案上跑真正的多工作階段建構時再來。
