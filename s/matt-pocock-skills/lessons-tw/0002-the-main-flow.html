主流程：從想法到交付

大多數工作都走這條骨幹路線。把它背起來。

大多數工作都走同一條路線。把它背起來——它是整套技能的骨幹。

grill-with-docs → to-spec → to-tickets → implement → code-review

逐步走過

  1. /grill-with-docs——一次一個問題地窮追不捨地訪談你，直到想法變銳利。有狀態：邊問邊把談定的用語寫進 CONTEXT.md、把硬決策寫進 ADR。沒有程式庫？改用 /grill-me——同樣的訪談，但無狀態。
  2. 原型分支。若某個問題需要一個能跑的答案（狀態模型、你必須親眼看到的 UI），就繞個路：/handoff 出去 → 開全新 session → /prototype → /handoff 回來 → 在原本的執行緒裡引用結果。
  3. 規模分支。
    • 多 session → /to-spec（把執行緒綜合成一份規格——不重新訪談），再 /to-tickets（拆成曳光彈票，每張宣告自己的阻塞邊），再逐張 /implement。
    • 單一 session → 就在這裡直接 /implement。
    無論哪條，/implement 內部都會驅動 /tdd（一次一道紅—綠切片），然後在提交前跑 /code-review（Standards + Spec，並行子代理）。
單一紀律 把步驟 1–3 留在同一個未中斷的上下文視窗裡。在 /to-tickets 之前不要壓縮、也不要清空——盤問、規格、票必須建立在同一份思考上。之後每一張 /implement 都從全新的視窗開始，只讀自己的那張票。

智慧區上限

模型還能銳利推理的那個視窗，大約是 12 萬 token——稱為智慧區（smart zone）。若某次 session 在 /to-tickets 之前就逼近它，別在衰退的推理上硬撐：/handoff，在全新的執行緒裡繼續。

整個流程就是這樣。入口坡道（triage、wayfinder）與獨立工具（prototype、research）掛在它上面——之後的課會講。

向老師提問 卡住了或好奇？儘管追問——任何不清楚的地方都可以問。
