診斷 bug：緊密迴圈

給那些一眼看不穿的難纏 bug 用的緊密迴圈紀律。

回饋迴圈的「難纏 bug」版本。/diagnosing-bugs 針對那些一眼看不穿的 bug——間歇性的 flake、悄悄出現在兩個已知良好狀態之間的回歸——跑一套紀律化的診斷迴圈。

緊密迴圈本身，就是這項技能

其他一切——二分法、假設檢定、埋儀器——一旦你有了訊號，都是機械式的。所以 diagnosing-bugs 在第一階段花上不成比例的力氣：構造一條能驅動實際 bug 程式碼路徑、並斷言使用者確切症狀的 pass／fail 指令，然後把它收緊到快、可重現、且代理跑得起來。

那個拒絕 在你擁有緊密的回饋迴圈之前，它拒絕提出假設——一條在這個 bug 上已經會轉紅的可執行指令。在那條指令存在之前，靠讀程式碼來建立理論，正是這項技能要防止的那種失敗。沒有能轉紅的迴圈，就沒有診斷。

一個 30 秒會飄的迴圈，只比沒有好一點點；一個 2 秒、可重現的迴圈，則是除錯超能力。

迴圈的階梯

它給你一道建造那個迴圈的方式階梯，大致依偏好排序：

  • 失敗的測試
  • curl 腳本
  • CLI diff
  • 無頭瀏覽器
  • 重播的 trace
  • 拋棄式測試架
  • 模糊測試迴圈
  • git bisect run
  • 差分執行
  • 需要人介入的 bash 腳本——只作為最後手段

非確定性的 bug

對 flake 而言，目標不是乾淨的重現，而是更高的重現率：迴圈觸發、平行化、加壓，直到 flake 變得可除錯。

這樣子就算有在工作

  • 它在提出理論之前，就建造並執行一條重現指令——並貼上呼叫方式與它的紅色輸出。
  • 迴圈斷言的是你確實回報的症狀，而不是某個鄰近的失敗。
  • 假設以一份排序過、可證偽的清單送達，而且是在任何一條被測試之前先給你看。
  • 除錯儀器有標記（[DEBUG-...]），而且在宣告完成之前會被 grep 掉。

它在哪裡交接

它是一個隨時可抓的獨立工具——壞掉了就丟進來，修復與回歸測試都就位後就退出。它的事後檢討會在真正的發現是「沒有一個好接縫能把 bug 鎖死」時，交接給 /improve-codebase-architecture——這時問題是程式碼，而不是 bug。
