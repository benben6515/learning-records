improve-codebase-architecture 如何消化這些文件

這個技能讀進你一路建立的所有東西——並找出程式碼想要深化之處。

這是最後一塊，而且它把迴圈關上。較早各課的每一份產物都餵進它：CONTEXT.md（L5）為好的接縫命名；ADR（L6）記錄下不要重新爭論的決策。improve-codebase-architecture 讀這兩份，掃描摩擦，並提出深化機會（deepening opportunities）——也就是把淺模組變成深模組的重構。目標：可測性與 AI 可導航性。

一個核心觀念：深 vs 淺

一個深模組（deep module）把大量行為藏在一個小介面背後。一個淺（shallow）模組的介面，幾乎和它的實作一樣複雜。把淺的那些深化。
深 — 以此為目標
小介面
深的實作
複雜度被藏起
槓桿 + 局部性
淺 — 避免
大介面
薄的實作
只是穿過去

深度用兩種方式賺回它的代價：對呼叫者的槓桿（leverage）（一份實作、N 個呼叫點、M 個測試）與對維護者的局部性（locality）（修一次，處處都修好）。「這個到底淺不淺？」的快測：

刪除測試 想像把這個模組刪掉。如果複雜度就這麼消失了，那它只是個穿遞性的東西（淺——深化或移除的候選）。如果複雜度重新出現在 N 個呼叫者身上，那它是有賺回代價的。「對，它把東西集中起來」就是你要的訊號。

這套詞彙——模組、介面、深度、接縫（seam）、轉接器（adapter）、槓桿、局部性——出自 codebase-design 參考文件。請精確使用這些詞；別漂移成「元件（component）」或「服務（service）」。（你在第 7 課已見過的一條規則——「介面就是測試面」——正是一條 codebase-design 原則。同一套詞彙，再次出現。）

流程

  1. 探索 — 先界定範圍（YAGNI）。掃描之前，先讀 CONTEXT.md 與相關的 ADR。把你的注意力加權在最近變動過的程式碼上（git log 的熱點）——深化在未來可能變動之處才划得來。自然而然地記下摩擦：那些逼你在許多小模組之間跳來跳去的概念；介面和它的實作一樣複雜；純粹函式只是為了可測而被抽出來，而真正的 bug 卻藏在它們被呼叫的方式裡。
  2. 以 HTML 報告呈現候選項。每張卡片：檔案、問題、解法、效益（以局部性／槓桿／可測性來表達）、一個前／後視覺化，以及一個強度徽章（強／值得探索／推測性）。它此刻還不提介面——它問的是：「你想探索哪一個？」
  3. 盤問你挑中的那一個。跑 /grilling（那個 L4 的基本工具）來走一遍決策樹——限制、相依、深化後模組的形狀、什麼留在接縫背後。隨著決策結晶，文件就地更新，透過 /domain-modeling。

它如何尊重並刷新你的文件

  • 領域用詞彙表的詞彙，架構用設計詞彙。如果 CONTEXT.md 定義了「訂單」，它就講「訂單收件模組」——而不是「FooBarHandler」。
  • 尊重 ADR——不重新爭論。某個候選若與一則 ADR 牴觸，只有當摩擦真實到值得重開時才浮現，而且會被明確標記（「與 ADR-0007 牴觸——但值得重開，因為……」）。
  • 回寫。用詞彙表裡沒有的概念為深化後的模組命名？補進去。在盤問途中把一個模糊的詞磨利？就地更新 CONTEXT.md。你用一個具決定性分量的理由否決了一個候選？提一則 ADR，讓未來的審查別再建議它。

你的具體收穫 — 把這些說出口

  1. 定義深模組 vs 淺模組（介面大小相對於實作）。
  2. 說出刪除測試，以及哪個答案代表「淺」。
  3. 說出深度的兩個回報（槓桿、局部性），以及各自是給誰的。
  4. 這個技能如何使用 CONTEXT.md 和 ADR——又如何回寫它們？

若你能答出這些，你就完成了規格驅動主幹的概念導覽。

向老師提問 挑一題：「在你的專案裡，授權位元遮罩的邏輯散落各處——那是個淺叢集嗎？把它深化會長什麼樣子？」 · 「我們『為了可測性』抽了一堆純工具函式——技能警告真正的 bug 藏在它們被呼叫的方式裡。我怎麼判斷我們是不是那種情況？」 · 「為什麼深度是介面的性質，而不是實作的？深模組難道不能由許多小部件組成嗎？」
