The Deep-Module Vocabulary — codebase-design

The shared architecture language every designing skill speaks. Use these terms exactly.

Design deep modules: a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface. Leverage for callers, locality for maintainers, testability for everyone.

Ground truth: codebase-design/SKILL.md and DEEPENING.md. This is the vocabulary improve-codebase-architecture is built on, and it must be used exactly — don't drift to "component," "service," "API," or "boundary."

Deep vs shallow

Deep module — aim here
small interface
deep implementation
complex logic hidden
few methods, simple params · lots behind it
Shallow module — avoid
large interface
thin impl
many methods, complex params · just passes through

When designing an interface, ask: Can I reduce the methods? Simplify the parameters? Hide more complexity inside?

Glossary

TermMeaningAvoid
ModuleAnything with an interface and an implementation. Scale-agnostic: a function, class, package, or tier-spanning slice.unit, component, service
InterfaceEverything a caller must know to use the module correctly — type signature and invariants, ordering, error modes, config, performance. (Broader than the TS interface keyword.)API, signature
ImplementationWhat's inside a module — its body of code.—
AdapterA concrete thing that satisfies an interface at a seam. Describes role (what slot it fills), not substance. (A small adapter can have a large implementation, e.g. a Postgres repo.)—
DepthLeverage at the interface: behaviour a caller/test can exercise per unit of interface they must learn. Deep = much behaviour behind a small interface; shallow = interface nearly as complex as the implementation.—
Seam(Michael Feathers) A place where you can alter behaviour without editing in that place — the location where a module's interface lives. Where the seam goes is its own design decision.boundary (overloaded with DDD's bounded context)
LeverageWhat callers get from depth: more capability per unit of interface learned. One implementation pays back across N call sites and M tests.—
LocalityWhat maintainers get from depth: change, bugs, knowledge, and verification concentrate in one place. Fix once, fixed everywhere.—

Principles

  • Depth is a property of the interface, not the implementation. A deep module can be internally composed of small, mockable parts — they just aren't part of the interface. Internal seams (private, used by the module's own tests) are fine alongside the external seam.
  • The deletion test. Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep.
  • The interface is the test surface. Callers and tests cross the same seam. If you need to test past the interface, the module is probably the wrong shape.
  • One adapter = a hypothetical seam. Two adapters = a real one. Don't introduce a seam unless something actually varies across it. A single-adapter seam is just indirection.

Deepening by dependency category

From DEEPENING.md. When you deepen a cluster of shallow modules, the category of its dependencies decides how the deepened module is tested across its seam:

CategoryExampleHow to deepen / test
1. In-processPure computation, in-memory stateAlways deepenable. Merge and test through the new interface. No adapter needed.
2. Local-substitutablePGLite for Postgres, in-memory FSDeepenable if a stand-in exists. Test with the stand-in in-suite. Seam stays internal.
3. Remote but owned (Ports & Adapters)Your own services across a networkDefine a port at the seam. Deep module owns the logic; transport is an injected adapter. In-memory adapter for tests, HTTP/gRPC/queue for prod.
4. True external (Mock)Stripe, Twilio — third-partyTake the dependency as an injected port; tests provide a mock adapter.
Replace, don't layer — when testing a deepened module Old unit tests on the shallow modules become waste once tests at the deepened interface exist — delete them. Write new tests at the interface; assert on observable outcomes, not internal state. Tests should survive internal refactors — if a test changes when the implementation changes, it was testing past the interface.

How the terms relate

  • A module has exactly one interface.
  • Depth is a property of a module, measured against its interface.
  • A seam is where a module's interface lives; an adapter sits there and satisfies it.
  • Depth produces leverage (callers) and locality (maintainers).
