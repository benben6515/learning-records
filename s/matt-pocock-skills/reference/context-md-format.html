CONTEXT.md — Format & Rules

The glossary. Opinionated, tight, project-specific, and devoid of implementation.

CONTEXT.md is a glossary and nothing else. Not a spec, not a scratchpad, not a decision log.

This is the project's ubiquitous language — the canonical names every other skill uses in issue titles, specs, test names, and refactor proposals. Ground truth: CONTEXT-FORMAT.md and the domain-modeling skill.

The four rules

RuleWhat it means
1. Be opinionated When several words name one concept, pick the best one and list the rest under _Avoid_:. Don't list synonyms as equals — choose.
2. Keep it tight One or two sentences max. Define what it is, not what it does.
3. Project-specific only General programming concepts (timeouts, error types, utility patterns) don't belong — even if the project uses them heavily. Test: is this unique to this context, or a general concept? Only the former belongs.
4. Devoid of implementation No file paths, no class names, no tech choices, no "how it works." If it's a decision or a behaviour, it goes in a spec or an ADR — not here.

The template

# {Context Name}

{One or two sentence description of what this context is and why it exists.}

## Language

**Order**:
{A one or two sentence description of the term}
_Avoid_: Purchase, transaction

**Invoice**:
A request for payment sent to a customer after delivery.
_Avoid_: Bill, payment request

**Customer**:
A person or organization that places orders.
_Avoid_: Client, buyer, account

Group terms under subheadings when natural clusters emerge; a flat list is fine when terms form one cohesive area.

A good entry (authoritative example)

Good Customer — A person or organization that places orders. Avoid: Client, buyer, account.
One sentence. What it is. Synonyms banished to _Avoid_. No implementation. Project-specific.

Anti-patterns — spot the broken rule

Bad — breaks Rule 4 (implementation) OrderService — A class in src/services/ that handles order creation, in the ordering module. Uses PostgreSQL and emits domain events.
File path, class name, tech stack, behaviour — all implementation. This belongs in code + maybe an ADR, never the glossary.
Bad — breaks Rule 3 (not project-specific) Timeout — The maximum time to wait for a response before failing.
A general programming concept. Even if the project uses timeouts everywhere, it's not unique to this domain.
Bad — breaks Rules 1 & 2 (not opinionated / not tight) Account — Used for various things in the system, like logins and billing.
Vague ("various things"), describes what it does not what it is, and lists no _Avoid_ synonyms. Probably two concepts mashed together — split it.

The inline discipline (from domain-modeling)

The glossary isn't written in a batch at the end. It's maintained inline, as terms resolve — usually during a grill-with-docs session:

  • Challenge conflicts. When someone uses a term that clashes with the glossary, call it out immediately: "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"
  • Sharpen fuzzy language. When a vague/overloaded term appears, propose the precise canonical term.
  • Update inline, don't batch. The moment a term resolves, write it. Don't collect them for later.
  • Create lazily. No CONTEXT.md until the first term actually resolves. Don't scaffold an empty one.

Single vs multi-context

  • Single context (most repos): one CONTEXT.md at the repo root. dashboard_frontend is this.
  • Multi-context: a root CONTEXT-MAP.md lists the contexts, where each lives, and how they relate; each context gets its own CONTEXT.md. The skill infers which applies — if unclear, it asks.

For a monorepo with genuinely separate bounded contexts (e.g. ordering/, billing/), reach for the map. For one cohesive app, a single root file is correct — don't invent contexts.
