ADRs — Format & the Three-Criteria Gate

Architectural Decision Records. Offered sparingly. The discipline is restraint.

Offer an ADR only when all three are true. Miss one — skip. The gate is AND, not OR.

Where CONTEXT.md holds terms, ADRs hold decisions — but only the rare decision that a future explorer genuinely needs explained. Ground truth: ADR-FORMAT.md and the domain-modeling skill.

The three-criteria gate

1. Hard to reverse
changing your mind later costs AND 2. Surprising without context
a future reader asks "why?" AND 3. Real trade-off
genuine alternatives existed all three ⇒ ADR miss any one ⇒ skip it
  • Easy to reverse? You'll just reverse it — skip.
  • Not surprising? Nobody will wonder why — skip.
  • No real alternative? There's nothing to record beyond "we did the obvious thing" — skip.

The format

Live in docs/adr/, sequentially numbered: 0001-slug.md, 0002-slug.md. Created lazily — the directory appears when the first ADR is needed.

# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}

That's the whole template. An ADR can be a single paragraph. The value is recording that a decision was made and why — not filling out sections.

Optional sections (only when they add genuine value): Status frontmatter (proposed | accepted | deprecated | superseded by ADR-NNNN), Considered Options (when rejected alternatives are worth remembering), Consequences (when non-obvious downstream effects need calling out).

What qualifies

  • Architectural shape. "We're a monorepo." "The write model is event-sourced; the read model projects into Postgres."
  • Integration patterns between contexts. "Ordering and Billing talk via domain events, not synchronous HTTP."
  • Technology choices that carry lock-in. Database, message bus, auth provider, deployment target — not every library, just the ones that'd take a quarter to swap.
  • Boundary & scope decisions. "Customer data is owned by the Customer context; others reference it by ID only." The explicit no-s are as valuable as the yes-s.
  • Deliberate deviations from the obvious path. "Manual SQL instead of an ORM because X." Stops the next engineer "fixing" something deliberate.
  • Constraints not visible in the code. "Can't use AWS because of compliance." "Response times must be under 200ms because of the partner API contract."
  • Non-obvious rejected alternatives. Considered GraphQL, picked REST for subtle reasons — otherwise someone suggests GraphQL again in six months.

What does NOT qualify

  • Anything easily reversible (lint config, a utility function's shape, a variable name).
  • Anything obvious from reading the code (the framework in package.json).
  • Decisions with no real alternative ("we used the standard library").
  • Ephemeral reasons ("not worth it right now") — those won't help a future explorer.

Terms vs decisions — where it goes

ArtefactHoldsGate
CONTEXT.mdTerms (the ubiquitous language)Is it a project-specific concept? Then yes.
docs/adr/*.mdDecisions (load-bearing choices)All 3 criteria of the gate.

Not sure where something belongs? If it answers "what do we call this?" → glossary. If it answers "why did we choose this?" → ADR (if it clears the gate).

When skills offer an ADR

  • domain-modeling — inline, the moment a decision clears the gate during a session. Offered, not imposed.
  • improve-codebase-architecture — when you reject a deepening candidate with a load-bearing reason, it offers: "Want me to record this as an ADR so future reviews don't re-suggest it?" Only when the reason would actually help a future explorer.

And the flip side: if a candidate contradicts an existing ADR, that's surfaced explicitly ("contradicts ADR-0007 — but worth reopening because…") rather than silently overridden. ADRs are respected, not re-litigated — unless the friction is real.
