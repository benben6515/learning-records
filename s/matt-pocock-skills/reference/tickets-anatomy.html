Ticket Anatomy — to-tickets

Break a spec into tracer-bullet tickets that declare their blocking edges.

A ticket is a tracer bullet: a narrow but complete vertical slice that an agent can build in one fresh context window. Every ticket declares which other tickets block it. You always work the frontier — the tickets whose blockers are all done.

Ground truth: to-tickets/SKILL.md. This is the last stop of the spec-driven spine: it takes a published spec and fans it out into tickets each labelled ready-for-agent — no further triage.

The process — five steps

  1. Gather context. Work from what's in the conversation, plus any passed reference (spec path, issue, URL). Read its full body and comments.
  2. Explore the codebase (optional). Use the CONTEXT.md vocabulary in titles; respect ADRs in the area you touch. Look for a chance to prefactor — "make the change easy, then make the easy change."
  3. Draft vertical slices. Break the work into tracer-bullet tickets, each with its blocking edges (see rules below).
  4. Quiz the user. Present a numbered list: each ticket's title, what it delivers, and what it's blocked by. Ask if granularity, edges, and merges/splits feel right. Iterate to approval.
  5. Publish to the configured tracker in dependency order (blockers first). Form depends on the tracker — see below.

Vertical-slice rules — the tracer bullet

A tracer bullet is vertical
  • Cuts a narrow but complete path through every layer — schema, API, UI, tests. Vertical, not a horizontal slice of one layer.
  • Completed slice is demoable / verifiable on its own.
  • Sized to fit one fresh context window.
  • Any prefactoring is done first, as its own leading ticket(s).
Horizontal slice — avoidVertical slice / tracer bullet — aim

Blocking edges & the frontier

Each ticket declares its blocking edges — the tickets that must finish before it can start. A ticket with no blockers starts immediately. The set of currently-unblocked tickets is the frontier, and that is always what you work:

T1 · login end-to-end
↓ blocks
T2 · menu filters by permissionBits
↓ blocks
T3 · per-role menu management
start: frontier = {T1} · after T1 closes: {T2} · after T2: {T3}

Because tickets are independent slices with explicit edges, each implement can run fresh, read only its ticket, and work the frontier without clobbering other sessions. This is precisely why the unbroken-window rule (grill → spec → tickets) captures the edges while the thinking is warm.

The exception — wide refactor → expand–contract

A wide refactor is one mechanical change — rename a column, retype a shared symbol — whose blast radius spans the whole codebase. A single edit breaks thousands of call sites at once, so no vertical slice can land green. Don't tracer-bullet it. Sequence it as expand–contract:

expand → migrate (batched) → contract
add the new form beside the old (nothing breaks) · migrate call sites in batches, each its own ticket blocked by the expand, CI green batch-to-batch · delete the old form once no caller remains
Last-resort variant When even a batch can't stay green alone, keep the sequence but let batches share an integration branch that all block a final integrate-and-verify ticket — green is promised only there.

How it publishes — two shapes

The tickets are the same either way; only the shape of the blocking edges changes, based on what setup-matt-pocock-skills configured:

  • Local files → one file per ticket under .scratch/<feature>/issues/<NN>-<slug>.md, numbered from 01 in dependency order. "Blocked by" as text. One ticket per file — never a combined file.
  • Real tracker (GitHub, Linear…) → one issue per ticket in dependency order, using the platform's native blocking / sub-issue links. Apply the ready-for-agent label — agent-grabbable by construction, no triage.

The four rules that get broken most

RuleWhy
1. Slice vertically, not horizontally "Do all the schema, then all the API" is a horizontal slice — nothing is demoable until the last layer lands. A tracer bullet goes end-to-end through all layers for a thin sliver of behaviour.
2. Every ticket declares its blockers The frontier depends on it. Without explicit edges, sessions can't run independently or pick safe work. The edge list is the whole point of capturing this in the warm window.
3. Don't tracer-bullet a wide refactor One mechanical change with a codebase-wide blast radius can't land green in a vertical slice. Use expand–contract: add new form → migrate in batches → delete old form. Forcing it into a tracer bullet just produces a broken build.
4. No file paths or code in tickets Same rule as the spec — they rot. Record behaviour from the user's perspective. Only exception: a prototype snippet that encodes a decision better than prose (state machine, schema), trimmed to the decision-rich parts.

The handoff

to-spec → to-tickets → frontier · ready-for-agent → implement (fresh window)
  • Single-session build? implement can take the spec directly — to-tickets is optional.
  • Multi-session build? to-tickets splits the spec into frontier tickets; each implement starts fresh and reads its ticket.
  • Never close or modify the parent issue.
