Spec Anatomy — to-spec

Synthesize the conversation into a fixed-shape spec. No interviewing.

to-spec takes what was already discussed and freezes it. The thinking happened in grill-with-docs; this skill just captures it. If you're interviewing here, you skipped the grilling.

Ground truth: to-spec/SKILL.md. The spec (you may know it as a PRD) is published to the issue tracker labelled ready-for-agent — no further triage.

The process — three steps

  1. Explore the repo (if you haven't). Use the CONTEXT.md vocabulary throughout; respect any ADRs in the area you're touching.
  2. Sketch the test seams first. Prefer existing seams to new ones; use the highest seam possible; the fewer seams the better — the ideal number is one. Confirm the seams with the user before writing.
  3. Write the spec from the template below and publish it to the issue tracker with the ready-for-agent label.

The anatomy

## Problem Statement
The problem, from the user's perspective.

## Solution
The solution, from the user's perspective.

## User Stories
A LONG, numbered list. Each:
  "As an <actor>, I want <feature>, so that <benefit>."
Extensive — cover all aspects of the feature.

## Implementation Decisions
- Modules built/modified, and their interfaces
- Schema changes, API contracts, specific interactions
- Architectural decisions, technical clarifications
NO file paths or code snippets (they go stale). Exception: a prototype
snippet that encodes a decision better than prose (state machine, reducer,
schema, type shape) — inline it, trimmed to the decision-rich parts.

## Testing Decisions
- What makes a good test: external behaviour only, not implementation details
- Which modules will be tested
- Prior art: similar tests already in the codebase

## Out of Scope
What is explicitly not in this spec.

## Further Notes
Anything else.

The three rules that get broken most

RuleWhy
1. Synthesize — don't interview to-spec has disable-model-invocation energy: it writes what's settled, it doesn't reopen it. Questions belong to grill-with-docs. If something is genuinely undecided, stop and go grill it — don't fake a decision in the spec.
2. Fewest seams; ideal = 1 Each seam is a coupling point that makes tests brittle. Test through the highest (most external) boundary you can — one seam covering the whole feature beats five unit tests at internal functions. "The interface is the test surface."
3. No file paths or code Paths and snippets rot the moment the codebase moves. Record decisions (interfaces, contracts, schemas) in prose — stable. Only a decision-encoding prototype (e.g. a state machine) survives, because it says something prose can't.

The ready-for-agent bridge

This is where the spec-driven spine hands off to the build phase:

to-spec → publishes issue, label → ready-for-agent → implement
  • The spec is published with the ready-for-agent triage label — no additional triage. (Recall Lesson 1: don't triage your own output.)
  • For a multi-session build, to-tickets then splits this spec into tracer-bullet tickets; each implement runs fresh, reading the ticket.
  • For a single-session build, implement can take the spec directly.

Vocabulary note

Every term in the spec's Problem/Solution/Stories must come from CONTEXT.md. If you reach for a word the glossary doesn't define, that's a signal — either coin it (run domain-modeling) or you're drifting from the ubiquitous language. See the CONTEXT.md reference.
