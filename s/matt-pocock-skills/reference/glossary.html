Glossary

The domain language of the Matt Pocock skills set. Every lesson uses these terms.

The skills’ own CONTEXT.md is the canonical source. Use these terms exactly; don’t drift to near-synonyms.

TermDefinition
Issue trackerThe tool that hosts a repo’s issues — GitHub Issues, Linear, a local .scratch/ markdown convention, or similar. Skills like to-tickets, to-spec, triage, and wayfinder read from and write to it. Avoid: backlog manager, backlog backend, issue host.
IssueA single tracked unit of work inside an Issue tracker — a bug, task, spec, or slice produced by to-tickets. Avoid “ticket” except when quoting external systems that call them tickets, or for a Decision ticket.
Decision ticketA wayfinder unit — a child Issue of a wayfinder:map holding a question whose resolution is a decision, not a slice of a build to execute. The decision qualifier is what keeps it distinct from an implementation issue.
Triage roleA canonical state-machine label applied to an Issue during triage (e.g. needs-triage, ready-for-agent). Each role maps to a real label string in the Issue tracker via docs/agents/triage-labels.md.
Smart zoneThe context-window size (~120k tokens on state-of-the-art models) within which the model still reasons sharply. Sessions approaching it before to-tickets should /handoff rather than push on degraded. aihero.dev dictionary.
Seam(Feathers’ term) A place you can change behaviour without editing there. The stable interface a feature is tested at. A well-placed seam gives tests something durable to aim at while the code underneath moves freely. Chosen before any code is written (during to-spec).
Deep moduleA module that hides a lot of behaviour behind a small, stable interface. Depth is measured as leverage — how much a caller (or a test) can exercise per unit of interface it has to learn. Opposite: shallow (interface nearly as complex as the implementation).
DepthProperty of the interface, not the implementation. A deep module can be internally composed of small, swappable parts that never surface to callers.
Blocking edgesThe dependency links between tickets. Every ticket declares the tickets that block it. On a real tracker these are native blocking links; locally they’re text in one file per ticket. The set of unblocked, unclaimed tickets is the frontier.
FrontierThe open, unblocked, unclaimed tickets — the edge of the known in wayfinder, or the takeable work in to-tickets. A tracker’s native blocking renders it visually.
Tracer bulletA thin vertical slice that cuts through all integration layers end-to-end (schema, API, UI, tests), demoable on its own. The first TDD cycle proves one path works end-to-end before you build outward. Opposite: horizontal slice (one layer, nothing works until all land).
Ubiquitous language(DDD, Evans) The shared vocabulary between devs and domain experts, used consistently in conversations, code, and files. In the skills set, captured in CONTEXT.md as a pure glossary — no implementation detail, no spec.
ADRArchitecture Decision Record, under docs/adr/. The bar is high: offered only when a choice is hard to reverse, surprising without context, and the result of a real trade-off. Miss any one and there is no ADR.
HITL / AFK(wayfinder) Human-in-the-loop vs away-from-keyboard. Every wayfinder ticket is HITL (grilling, prototype — needs a live exchange) or AFK (research — agent alone). The agent never answers its own questions on a HITL ticket.
Context hygieneKeeping steps 1–3 of the main flow (grill-with-docs → to-spec → to-tickets) in one unbroken context window — don’t compact or clear until after to-tickets — so the grilling, spec, and tickets build on the same thinking. Each implement then starts fresh.
Red-green loopWrite one failing test (red), add just enough code to pass it (green), then repeat for the next behaviour. Refactor only when green, never while red. The engine inside tdd and implement.
