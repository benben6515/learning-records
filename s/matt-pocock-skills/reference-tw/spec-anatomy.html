規格解剖 — to-spec

把對話綜合成固定形狀的規格。不訪談。

to-spec 接住已經談定的東西並把它凍結。思考發生在 grill-with-docs；這個技能只負責捕捉。如果你在這裡訪談，代表你跳過了盤問。

事實來源：to-spec/SKILL.md。規格（你也許叫它 PRD）發布到議題追蹤器，標上 ready-for-agent——之後不再分級。

流程——三步

  1. 探索 repo（如果還沒）。全程使用 CONTEXT.md 詞彙；尊重你觸及範圍內的任何 ADR。
  2. 先草描測試接縫。優先用現成接縫，別開新的；用最高的可用接縫；接縫愈少愈好——理想數字是一。寫之前先跟使用者確認接縫。
  3. 寫規格，依照下方範本，發布到議題追蹤器並打上 ready-for-agent 標籤。

解剖

## Problem Statement（問題陳述）
問題，從使用者視角。

## Solution（解法）
解法，從使用者視角。

## User Stories（使用者故事）
一份很長的編號清單。每則：
  「作為〈角色〉，我想要〈功能〉，以便〈效益〉。」
要廣——涵蓋功能的所有面向。

## Implementation Decisions（實作決策）
- 建立／修改的模組，以及它們的介面
- Schema 變更、API 合約、具體互動
- 架構決策、技術釐清
不放檔案路徑或程式碼片段（它們會腐爛）。例外：比散文
更能編碼決策的原型片段（狀態機、reducer、schema、
型別形狀）——內嵌，裁到只剩決策密集的部分。

## Testing Decisions（測試決策）
- 什麼算好測試：只測外部行為，不測實作細節
- 哪些模組會被測
- 前例：codebase 裡已有的類似測試

## Out of Scope（不在範圍內）
明確不在這份規格裡的東西。

## Further Notes（備註）
其他一切。

最常被打破的三條規則

規則為什麼
1. 綜合——不要訪談 to-spec 自帶 disable-model-invocation 的氣場：它寫下已定案的事，不重啟它。問題屬於 grill-with-docs。如果真的有未定的事，停下來去盤問——別在規格裡假裝有個決策。
2. 接縫愈少愈好；理想 = 1 每道接縫都是讓測試變脆的耦合點。透過你能用的最高（最外部）邊界測——一道接縫涵蓋整個功能，勝過五個針對內部函式的單元測試。「介面即測試面。」
3. 不放檔案路徑或程式碼 路徑與片段在 codebase 一動就爛。用散文記決策（介面、合約、schema）——才穩。只有編碼決策的原型（如狀態機）能存活，因為它說了散文說不出的東西。

ready-for-agent 橋接

規格驅動主幹在這裡把棒子交給建置階段：

to-spec → 發布 issue、標籤 → ready-for-agent → implement
  • 規格帶著 ready-for-agent 分級標籤發布——不再額外分級。（記得：別分級自己的產出。）
  • 多 session 建置時，to-tickets 接著把這份規格拆成曳光彈票；每個 implement 全新執行，只讀自己的票。
  • 單 session 建置時，implement 可以直接吃規格。

詞彙提醒

規格 Problem／Solution／Stories 裡的每一個術語都必須來自 CONTEXT.md。如果你伸手抓了一個詞彙表沒定義的詞，那是個訊號——要么鑄造它（跑 domain-modeling），要么你正在漂離共用語言。見 CONTEXT.md 參考。
