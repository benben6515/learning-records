ADR — 格式與三條件閘門

架構決策紀錄。節制供給。這門紀律就是克制。

只在三個條件全數成立時才提 ADR。缺一個——跳過。閘門是 AND，不是 OR。

CONTEXT.md 收術語，ADR 收決策——但只有那種未來的探索者真的需要有人解釋的罕見決策。事實來源：ADR-FORMAT.md與 domain-modeling 技能。

三條件閘門

1. 難以逆轉
之後反悔的代價很高 AND 2. 沒上下文會令人意外
未來的讀者會問「為什麼？」 AND 3. 真實取捨
真的存在過替代方案 三個全中 ⇒ ADR 缺任何一個 ⇒ 跳過
  • 容易逆轉？反正你會直接逆轉——跳過。
  • 不令人意外？沒有人會問為什麼——跳過。
  • 沒有真正的替代方案？除了「我們做了顯然的事」沒什麼好記——跳過。

格式

住在 docs/adr/，流水編號：0001-slug.md、0002-slug.md。懶建立——第一則 ADR 需要出現時，目錄才出現。

# {決策的短標題}

{1–3 句：背景是什麼、我們決定了什麼、為什麼。}

範本就這麼多。一則 ADR 可以只有一段。價值在記下有這個決策與為什麼——不是把欄位填滿。

可選區段（只在真的加值時用）：Status frontmatter（proposed | accepted | deprecated | superseded by ADR-NNNN）、Considered Options（被否決的方案值得記住時）、Consequences（不明顯的下游效應需要點出時）。

什麼算數

  • 架構形狀。「我們是 monorepo。」「寫入模型走 event sourcing；讀取模型投影進 Postgres。」
  • Context 之間的整合模式。「Ordering 與 Billing 用領域事件溝通，不是同步 HTTP。」
  • 帶鎖定的技術選型。資料庫、訊息匯流排、驗證供應商、部署目標——不是每個 library，只有那些換掉要花一季的。
  • 邊界與範圍決策。「客戶資料歸 Customer context 擁有；其他人只憑 ID 參照。」明確的不跟要一樣值錢。
  • 對顯然路徑的刻意偏離。「因為 X 所以手寫 SQL 而不用 ORM。」阻止下一位工程師把刻意的東西「修好」。
  • 程式碼看不出來的約束。「因為法規遵循不能用 AWS。」「回應時間必須低於 200ms，因為合作夥伴 API 合約。」
  • 不顯然的被否決方案。考慮過 GraphQL、因細微理由選了 REST——否則六個月後又有人提 GraphQL。

什麼不算數

  • 任何容易逆轉的東西（lint 設定、工具函式的形狀、變數名稱）。
  • 任何讀程式碼就顯而易見的東西（package.json 裡的框架）。
  • 沒有真正替代方案的決策（「我們用了標準庫」）。
  • 一時性的理由（「現在不值得」）——那幫不了未來的探索者。

術語 vs 決策——放哪裡

產物收什麼閘門
CONTEXT.md術語（共用語言）是專案專屬概念嗎？是就收。
docs/adr/*.md決策（承重選擇）閘門三條件全中。

不確定屬於哪邊？如果它回答「這個我們叫什麼？」→ 詞彙表。如果它回答「這個我們為什麼選它？」→ ADR（如果過得了閘門）。

技能何時提出 ADR

  • domain-modeling——內嵌，session 中決策一過閘門的那一刻。是提出，不是強加。
  • improve-codebase-architecture——當你用承重的理由否決某個深化候選時，它會問：「要不要記成一則 ADR，讓未來的審查不再重提？」只在理由真的能幫到未來探索者時。

反面是：如果某候選牴觸既有 ADR，會被明講（「牴觸 ADR-0007——但值得重開，因為……」）而不是默默蓋過。ADR 被尊重、不被重新審判——除非摩擦是真的。
