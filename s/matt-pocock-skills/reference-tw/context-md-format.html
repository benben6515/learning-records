CONTEXT.md — 格式與規則

詞彙表。有立場、精練、專案專屬、零實作。

CONTEXT.md 是詞彙表，除此無他。不是規格、不是草稿、不是決策紀錄。

這是專案的共用語言（ubiquitous language）——其他所有技能在 issue 標題、規格、測試名稱、重構提案裡使用的標準名稱。事實來源：CONTEXT-FORMAT.md與 domain-modeling 技能。

四條規則

規則意思
1. 要有立場 多個詞指同一概念時，挑最好的那個，其餘列在 _Avoid_: 底下。別把同義詞平起平坐地列著——要選。
2. 保持精練 一到兩句為限。定義它是什麼，不是它做什麼。
3. 只收專案專屬 通用程式概念（timeout、錯誤類型、工具模式）不屬於這裡——就算專案用得再兇。檢驗：這是這個 context 獨有的，還是通用概念？只有前者算數。
4. 零實作 沒有檔案路徑、沒有類別名稱、沒有技術選型、沒有「它怎麼運作」。如果是決策或行為，它屬於規格或 ADR——不屬於這裡。

範本

# {Context 名稱}

{一到兩句描述：這個 context 是什麼、為何存在。}

## Language

**Order（訂單）**:
{術語的一到兩句描述}
_Avoid_: Purchase, transaction

**Invoice（發票）**:
送貨後開給客戶的付款請求。
_Avoid_: Bill, payment request

**Customer（客戶）**:
下訂單的個人或組織。
_Avoid_: Client, buyer, account

出現自然聚類時，用小標題分組術語；術語屬於單一內聚領域時，平面清單也可以。

好條目（權威範例）

好 Customer（客戶）——下訂單的個人或組織。避免：Client、buyer、account。
一句話。說它是什麼。同義詞放逐到 _Avoid_。零實作。專案專屬。

反模式——找出被打破的規則

壞——打破規則 4（實作） OrderService——src/services/ 裡負責建立訂單的類別，屬於訂購模組。用 PostgreSQL 並發出領域事件。
檔案路徑、類別名稱、技術棧、行為——全是實作。它屬於程式碼＋也許一則 ADR，永遠不屬於詞彙表。
壞——打破規則 3（非專案專屬） Timeout——失敗前等待回應的最長時間。
通用程式概念。就算專案到處用 timeout，它也不是這個領域獨有的。
壞——打破規則 1 與 2（沒立場／不精練） Account——系統裡各種東西都用它，像登入和帳務。
含糊（「各種東西」），描述它做什麼而非是什麼，也沒列 _Avoid_ 同義詞。很可能是兩個概念糊在一起——拆開。

內嵌紀律（出自 domain-modeling）

詞彙表不是最後一批補寫的文件。它隨術語落定、內嵌維護——通常在 grill-with-docs session 進行中：

  • 挑戰衝突。有人用了與詞彙表相衝突的術語時，立刻指出：「你的詞彙表把『cancellation』定義為 X，但你似乎指 Y——是哪個？」
  • 磨利模糊語言。模糊／超載的詞一出現，提出精確的標準詞。
  • 內嵌更新，別囤積。術語一落定就寫。別收集起來等之後。
  • 懶建立。第一個術語真正落定之前不寫 CONTEXT.md。別先搭一個空的。

單一 vs 多 context

  • 單一 context（多數 repo）：repo 根目錄一個 CONTEXT.md。典型專案就是這樣。
  • 多 context：根目錄的 CONTEXT-MAP.md 列出各 context、各自位置、彼此關係；每個 context 有自己的 CONTEXT.md。技能會推斷適用哪個——不清楚就問。

monorepo 裡有真正分離的 bounded context（如 ordering/、billing/）就用 map。單一內聚應用，根目錄一個檔案才是對的——別憑空發明 context。
