深模組詞彙 — codebase-design

所有設計技能共用的架構語言。精確使用這些術語。

設計深模組（deep module）：小介面後面藏大量行為，放在乾淨的接縫上，透過介面可測。呼叫者得到槓桿、維護者得到局部性、所有人都得到可測性。

事實來源：codebase-design/SKILL.md與 DEEPENING.md。這是 improve-codebase-architecture 賴以建立 的詞彙，必須精確使用——別漂移到「component」「service」「API」或「boundary」。

深 vs 淺

深模組——目標
小介面
深實作
複雜邏輯被藏住
方法少、參數簡單 · 後面藏很多
淺模組——避免
大介面
薄實作
方法多、參數複雜 · 只是直通

設計介面時問自己：方法能減嗎？參數能簡化嗎？裡面還能多藏點複雜度嗎？

詞彙表

術語意義避免
Module（模組）任何有介面與實作的東西。不限尺度：函式、類別、套件、或跨層切片。unit、component、service
Interface（介面）呼叫者要正確使用模組必須知道的一切——型別簽名以及不變量、順序、錯誤模式、組態、效能。（比 TS 的 interface 關鍵字更廣。）API、signature
Implementation（實作）模組裡面的東西——它的程式碼主體。—
Adapter（轉接器）在接縫上具體滿足某介面的東西。描述的是角色（填哪個槽），不是份量。（小轉接器可以有很大實作，如 Postgres repo。）—
Depth（深度）介面上的槓桿：呼叫者／測試每學一單位介面，能驅動多少行為。深 = 小介面後藏大量行為；淺 = 介面幾乎跟實作一樣複雜。—
Seam（接縫）（Michael Feathers）不改某處程式碼就能改變行為的地方——模組介面所在的位置。接縫放哪裡本身就是一個設計決策。boundary（與 DDD 的 bounded context 撞名）
Leverage（槓桿）呼叫者從深度得到的：每學一單位介面換到更多能力。一份實作在 N 個呼叫點與 M 個測試間回收。—
Locality（局部性）維護者從深度得到的：變更、bug、知識與驗證集中一處。修一次，處處修好。—

原則

  • 深度是介面的屬性，不是實作的。深模組內部可以由許多小而可 mock 的部件組成——它們只是不屬於介面。內部接縫（私有、供模組自己的測試用）與外部接縫並存沒問題。
  • 刪除測試（deletion test）。想像刪掉這個模組。複雜度若消失，它是直通層。複雜度若在 N 個呼叫者身上重現，它有在賺自己的飯。
  • 介面即測試面。呼叫者與測試跨越同一道接縫。如果你需要穿過介面去測，模組八成形狀不對。
  • 一個轉接器 = 假設性的接縫。兩個轉接器 = 真的接縫。除非真的有東西跨著它變化，否則別引入接縫。單轉接器的接縫只是間接層。

依依賴類別深化

出自 DEEPENING.md。深化一群淺模組時，其依賴的類別決定深化後的模組怎麼跨接縫受測：

類別例子怎麼深化／測試
1. 同進程（In-process）純計算、記憶體內狀態永遠可深化。合併並透過新介面測試。不需要轉接器。
2. 本地可替換（Local-substitutable）PGLite 代替 Postgres、記憶體 FS有替身就可深化。測試在套件裡用替身跑。接縫保持內部。
3. 遠端但自有（Remote but owned）（Ports & Adapters）跨網路的自家服務在接縫上定義port。深模組持有邏輯；傳輸是注入的轉接器。測試用記憶體轉接器，正式環境用 HTTP／gRPC／佇列。
4. 真外部（True external）（Mock）Stripe、Twilio——第三方把依賴視為注入的 port；測試提供 mock 轉接器。
替換，不要疊加——測深化後的模組時 淺模組上的舊單元測試，在深化介面處的測試出現後就成了廢料——刪掉它們。在介面上寫新測試；斷言可觀察結果，不是內部狀態。測試應該活得過內部重構——如果實作一變測試就跟著變，它就是在穿過介面測。

術語之間的關係

  • 一個模組恰有一個介面。
  • 深度是模組的屬性，相對其介面衡量。
  • 接縫是模組介面所在之處；轉接器坐在那裡滿足它。
  • 深度產出槓桿（給呼叫者）與局部性（給維護者）。
