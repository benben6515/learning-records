Matt Pocock 技能 — 流程圖與詞彙表

一套系統、一條主流程、一條規格驅動主幹，底下是一份共享詞彙。

這些技能不是一堆互不相干的指令。它們構成一條主流程——想法 → 交付——加上兩個匯入主流程的入口坡道，以及一層貫穿全場的文件層。本頁是壓縮版地圖。每一個主張都可回溯到技能自己的 SKILL.md（唯一事實來源）與公開 repo。

主流程：想法 → 交付

大多數工作走的路線。你有一個想法，想把它蓋出來。權威描述住在 ask-matt——路由器技能——裡。

grill-with-docs → to-spec → to-tickets → implement → code-review
全程在底下： domain-modeling 撰寫 CONTEXT.md + ADR
  1. /grill-with-docs —— 用窮追不捨的訪談把想法磨利。手上有 codebase 就從這裡開始。它是有狀態的：把學到的東西保存在 CONTEXT.md 與 ADR 裡。沒有 codebase？改用 /grill-me（同一個 /grilling 基本工具，不留文件軌跡）。
  2. 分岔 —— 有沒有問題需要可執行的答案？如果某個問題需要狀態、業務邏輯，或你必須親眼看的 UI，就繞道原型，兩頭都用 /handoff 橋接：出去 → 全新 session → /prototype → /handoff 回來。
  3. 分岔 —— 這是多 session 建置嗎？
    • 是 → /to-spec（把對話變成規格），再 /to-tickets 拆成一張張曳光彈票，每張宣告自己的阻塞邊。然後逐票 /implement，每張之間清空上下文。
    • 否 → 就在這裡、同一個上下文視窗裡 /implement。
  4. 不論哪條路，/implement 內部驅動 /tdd（一次一道紅—綠切片）來建置每個 issue，最後以 /code-review 收尾——對 diff 做雙軸審查（標準＋規格）——然後才提交。
單一視窗紀律（context hygiene）——最多人栽掉的規則 步驟 1–3（盤問 → 規格 → 票）要留在同一個不中斷的上下文視窗裡。/to-tickets 結束前不要 compact、不要清空——盤問、規格、票必須建立在同一份思考上。之後每個 /implement 都從全新狀態出發，只讀自己的票。上限是智慧區（smart zone）（約 12 萬 token）。如果 session 在 /to-tickets 之前就逼近智慧區，別硬撐著退化中的推理——/handoff 之後全新續戰。

兩個入口坡道

會產生工作的起始情境，之後匯入主流程。

  • bug 與請求不斷堆積 → /triage。它讓 issue 走過五個分級角色，產出代理可直接施工的 issue，之後由 /implement 接手。
別分級自己的票 分級（triage）只給不是你開的 issue——bug 回報、外部功能請求、任何原始素材。/to-tickets 產出的票已經是代理可施工的狀態。再跑一次 /triage 純屬浪費。

規格驅動主幹（你的焦點）

規格驅動開發是主流程中「從磨利的想法到代理可施工的票」這一段。四個技能，加一門支撐紀律：

技能做什麼產出時機
grill-with-docs 窮追不捨的訪談，把計畫／設計磨利。 術語／決策成形時，對 CONTEXT.md + ADR 的編輯。 流程起點，手上有 codebase。
to-spec 綜合對話成一份規格／PRD。不訪談——只寫已談定的內容。 發布到議題追蹤器的規格，標上 ready-for-agent。 想法已定且需多 session。
to-tickets 把規格拆成帶阻塞邊的曳光彈票。 代理可施工的票，阻塞者在前。 多 session 建置，規格之後。
implement 建置一張票，內部驅動 tdd，再 code-review。 已提交、已審查的程式碼。 逐票進行，全新上下文。
domain-modeling （底層） 建立詞彙表＋記錄決策的主動紀律。 CONTEXT.md 術語；docs/adr/ 裡的 ADR。 隨時內嵌——只要有術語或決策落定。

to-spec 規格的解剖

出自 to-spec/SKILL.md。規格有固定形狀：

  • Problem Statement（問題陳述）——使用者視角的問題。
  • Solution（解法）——使用者視角的解法。
  • User Stories（使用者故事）——一份很長的編號清單：「作為〈角色〉，我想要〈功能〉，以便〈效益〉。」要廣——涵蓋所有面向。
  • Implementation Decisions（實作決策）——模組、介面、schema、API 合約、互動方式。不放檔案路徑或程式碼片段（會腐爛）。例外：能用比散文更好的方式編碼某個決策的原型片段（狀態機、schema、型別形狀）。
  • Testing Decisions（測試決策）——什麼算好測試（外部行為，非內部實作）、測哪些模組、前例。
  • Out of Scope（不在範圍內）與Further Notes（備註）。
測試接縫規則 寫規格之前，先草描你要測這個功能的接縫（seam）。優先用現成接縫，別開新的。用盡可能高的接縫。全 codebase 接縫愈少愈好——理想數字是一。先跟使用者確認。

文件層（骨幹）

有兩個產物住在所有規格驅動技能的底下。它們懶建立——有東西可寫才寫——而每個技能探索之前都會先讀它們。

CONTEXT.md —— 詞彙表

出自 CONTEXT-FORMAT.md。它是專案的共用語言（ubiquitous language），除此無他。

  • 有立場。多個詞指同一概念時，挑最好的一個，其餘列在 _Avoid_: 底下。
  • 精練。一到兩句。定義它是什麼，不是它做什麼。
  • 只收專案專屬。通用程式概念（timeout、錯誤類型）不屬於這裡，就算用得再兇也一樣。
  • 零實作。不是規格、不是草稿、不是放決策的地方。

ADR —— 架構決策紀錄

出自 ADR-FORMAT.md。住在 docs/adr/，流水編號（0001-slug.md）。可以只有一段。

只在三個條件全數成立時才提 ADR：難以逆轉 · 沒有上下文會令人意外 · 真實取捨的結果。缺任何一個，就跳過。

什麼算數：架構形狀、context 之間的整合模式、帶鎖定的技術選型、邊界／範圍決策、對顯然路徑的刻意偏離、程式碼看不出來的約束、不顯然的被否決方案。

最佳實踐原則

  1. 盤問 → 規格 → 票同一個視窗；每個 implement 全新開始。思考必須連續；建置必須分隔。
  2. 尊重智慧區。to-tickets 前逼近約 12 萬 token？交接，別硬撐。
  3. CONTEXT.md 是詞彙表，不是規格。實作細節一律出局。
  4. 到處用共用語言。每一個產出（issue 標題、規格、測試名稱）都用 CONTEXT.md 的術語。別漂移到同義詞。
  5. ADR 要節制。只認三條件。別記錯顯而易見或輕易可逆的事。
  6. 文件懶建立。術語沒落定就不寫 CONTEXT.md；決策沒賺到就不開 docs/adr/。
  7. 尊重 ADR——別重新審判。只有摩擦真的大到值得時才重開，而且要明講。
  8. 測試接縫愈少愈好；理想 = 1。優先現成接縫；用最高的那一個。
  9. 規格裡不放檔案路徑或程式碼（除了編碼決策的原型）。它們會腐爛。
  10. 別分級自己的票。to-tickets 的產出已經是代理可施工。
  11. 用 ask-matt 當路由器。忘記哪個技能合用時，問路由器，別用猜的。

詞彙表

術語在本系統中的意義
flow（流程）穿越技能的一條路徑。大多數工作走主流程。
main flow（主流程）想法 → 交付：grill-with-docs → to-spec → to-tickets → implement → code-review。
on-ramp（入口坡道）產生工作、之後匯入主流程的起始情境（如 triage）。
spec / PRD（規格）to-spec 從對話綜合出的固定形狀文件。
ubiquitous language（共用語言）專案議定好的領域詞彙，收在 CONTEXT.md。
CONTEXT.md詞彙表。有立場、精練、專案專屬、零實作。
ADR架構決策紀錄，在 docs/adr/。只能靠三條件賺到。
seam（接縫）功能接受測試之處。用最少、最高的接縫。
deep / shallow module（深／淺模組）深模組用簡單介面藏住大量複雜度（improve-codebase-architecture 的目標）。
deletion test（刪除測試）「刪掉它，複雜度會被集中，還是只是被搬家？」會集中＝繼續看；它可能是淺的。
tracer bullet（曳光彈）貫穿系統、打出一條薄薄端到端切片的票。
blocking edge（阻塞邊）票與票之間的原生依賴；所有阻塞者關閉，票才解鎖。
smart zone（智慧區）模型仍能敏銳推理的約 12 萬 token 視窗。上下文紀律的依據。
grilling（窮追訪談）窮追不捨的訪談基本工具。grill-with-docs = grilling + domain-modeling。
model-invoked / user-invoked（模型／使用者觸發）技能能否自行觸發（付上下文負擔），還是只能靠打字叫名（付認知負擔）。
