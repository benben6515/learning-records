票解剖 — to-tickets

把規格拆成會宣告自己阻塞邊的曳光彈票。

票是一枚曳光彈（tracer bullet）：窄但完整的垂直切片，代理能在單一全新上下文視窗內建完。每張票宣告哪些票阻塞它。你永遠在打理前緣（frontier）——阻塞者全部完工的那些票。

事實來源：to-tickets/SKILL.md。這是規格驅動主幹的最後一站：接下一份已發布的規格，展開成一張張標著 ready-for-agent 的票——之後不再分級。

流程——五步

  1. 蒐集上下文。從對話中已有的內容出發，加上任何傳入的參考（規格路徑、issue、URL）。讀完正文與留言。
  2. 探索 codebase（可選）。標題使用 CONTEXT.md 詞彙；尊重你觸及範圍內的 ADR。找機會前置重構（prefactor）——「先把改動變簡單，再做那個簡單的改動」。
  3. 草擬垂直切片。把工作拆成曳光彈票，每張帶自己的阻塞邊（規則見下）。
  4. 考使用者。給一份編號清單：每張票的標題、交付什麼、被什麼阻塞。問顆粒度、邊、該合併／拆分的地方對不對。反覆到核准。
  5. 發布到設定的追蹤器，依依賴順序（阻塞者在前）。形式依追蹤器而定——見下。

垂直切片規則——曳光彈

曳光彈是垂直的
  • 在每一層——schema、API、UI、測試——切出一條窄但完整的路徑。是垂直的，不是只切一層的水平切片。
  • 完成的切片自己就能 demo／驗證。
  • 大小以塞進一個全新上下文視窗為準。
  • 任何前置重構先做，當作自己的前導票。
水平切片——避免垂直切片／曳光彈——目標
「把整個 schema 蓋完。」
單獨無法 demo。		 「使用者能登入並看到一個受保護頁面，端到端。」
落地那一刻就能 demo。

阻塞邊與前緣

每張票宣告自己的阻塞邊（blocking edges）——必須先完工它才能開工的票。沒有阻塞者的票立刻可開工。目前未被阻塞的票集合就是前緣，而你打理的永遠是它：

T1 · 登入端到端
↓ 阻塞
T2 · 選單依 permissionBits 過濾
↓ 阻塞
T3 · 依角色管理選單
起始：前緣 = {T1} · T1 關閉後：{T2} · T2 之後：{T3}

因為票是帶明確邊的獨立切片，每個 implement 都能全新執行、只讀自己的票、打理前緣而不干擾其他 session。這正是「不中斷視窗規則」（盤問 → 規格 → 票）要在思考還熱的時候把邊捕捉下來的原因。

例外——寬幅重構 → 擴張—收縮

寬幅重構是單一機械式改動——改欄位名、改共用符號型別——其波及半徑橫跨整個 codebase。一次編輯同時弄壞幾千個呼叫點，所以沒有任何垂直切片能綠著落地。別用曳光彈打它。把它排成擴張—收縮（expand–contract）：

expand → migrate（分批） → contract
在舊形式旁加上新形式（什麼都不壞）· 分批遷移呼叫點，每批一張票、被 expand 阻塞，CI 批批保綠 · 沒有呼叫者後刪掉舊形式
最後手段變體 連單批都無法獨自保綠時，保留順序，但讓各批共用一條整合分支，全部阻塞最後一張整合並驗證票——只有那裡承諾變綠。

怎麼發布——兩種形態

票本身兩邊一樣；變的只有阻塞邊的形態，取決於 setup-matt-pocock-skills 設定了什麼：

  • 本地檔案 → 每票一檔，放在 .scratch/<feature>/issues/<NN>-<slug>.md，依依賴順序從 01 編號。「Blocked by」用文字寫。一票一檔——絕不合併成單檔。
  • 真追蹤器（GitHub、Linear……） → 依依賴順序每票一個 issue，用平台的原生阻塞／子 issue 連結。打上 ready-for-agent 標籤——天生代理可抓，不分級。

最常被打破的四條規則

規則為什麼
1. 垂直切，不要水平切 「先做完全部 schema，再做完所有 API」是水平切片——最後一層落地前什麼都不能 demo。曳光彈以薄薄一行為貫穿所有層。
2. 每張票宣告阻塞者 前緣靠它。沒有明確的邊，session 無法獨立執行、無法挑安全的工作。邊清單就是趁熱視窗捕捉這件事的全部意義。
3. 寬幅重構別用曳光彈 波及全 codebase 的單一機械改動不可能在垂直切片裡綠著落地。用擴張—收縮：加新形式 → 分批遷移 → 刪舊形式。硬塞進曳光彈只會得到壞掉的建置。
4. 票裡不放檔案路徑或程式碼 跟規格同一條規則——它們會爛掉。記行為，從使用者視角。唯一例外：比散文更能編碼決策的原型片段（狀態機、schema），裁到只剩決策密集的部分。

交接

to-spec → to-tickets → 前緣 · ready-for-agent → implement（全新視窗）
  • 單 session 建置？implement 可以直接吃規格——to-tickets 可省。
  • 多 session 建置？to-tickets 把規格拆成前緣票；每個 implement 全新開始、只讀自己的票。
  • 絕不關閉或修改父 issue。
