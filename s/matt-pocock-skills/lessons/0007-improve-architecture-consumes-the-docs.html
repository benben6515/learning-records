How improve-codebase-architecture Consumes the Docs

The skill that reads everything you've built — and finds where the code wants deepening.

This is the last piece, and it closes the loop. Every artefact from the earlier lessons feeds into it: CONTEXT.md (L3) gives names to good seams; ADRs (L4) record decisions not to re-litigate. improve-codebase-architecture reads them both, scans for friction, and proposes deepening opportunities — refactors that turn shallow modules into deep ones. The aim: testability and AI-navigability.

The one idea: deep vs shallow

A deep module hides a lot of behaviour behind a small interface. A shallow one has an interface nearly as complex as its implementation. Deepen the shallow ones.
Deep — aim here
small interface

Shallow — avoid

Depth earns its keep two ways: leverage for callers (one implementation, N call sites, M tests) and locality for maintainers (fix once, fixed everywhere). The quick test for "is this shallow?":

The deletion test Imagine deleting the module. If the complexity just vanishes, it was a pass-through (shallow — candidate for deepening or removal). If the complexity reappears across N callers, it was earning its keep. "Yes, it concentrates" is the signal you want.

This vocabulary — module, interface, depth, seam, adapter, leverage, locality — comes from the codebase-design reference. Use those terms exactly; don't drift to "component" or "service." (One rule you already met in L5 — "the interface is the test surface" — is a codebase-design principle. Same vocabulary, appearing again.)

The flow

  1. Explore — scope first (YAGNI). Read CONTEXT.md and the relevant ADRs before scanning. Weight your attention to recently-changed code (git log hot spots) — deepening pays off where future change is likely. Note friction organically: concepts that force bouncing between many tiny modules; interfaces as complex as their implementation; pure functions extracted only for testability while the real bugs hide in how they're called.
  2. Present candidates as an HTML report. Each card: files, problem, solution, benefits (in terms of locality/leverage/testability), a before/after visualisation, and a strength badge (Strong / Worth exploring / Speculative). It does not propose interfaces yet — it asks: "which do you want to explore?"
  3. Grill the one you pick. Runs /grilling (the L2 primitive) to walk the decision tree — constraints, dependencies, the shape of the deepened module, what survives behind the seam. Docs update inline as decisions crystallise, via /domain-modeling.

How it respects and refreshes your docs

  • Uses glossary vocabulary for domain, design vocabulary for architecture. If CONTEXT.md defines "Order," it talks about "the Order-intake module" — not "FooBarHandler."
  • Respects ADRs — doesn't re-litigate. A candidate that contradicts an ADR is surfaced only if the friction is real enough to warrant reopening, and it's flagged explicitly ("contradicts ADR-0007 — but worth reopening because…").
  • Writes back. Names a deepened module after a concept not in the glossary? Adds it. Sharpen a fuzzy term mid-grill? Updates CONTEXT.md right there. You reject a candidate with a load-bearing reason? Offers an ADR so future reviews don't re-suggest it.

Your tangible win — say these out loud

  1. Define a deep module vs a shallow one (interface size relative to implementation).
  2. State the deletion test, and which answer signals "shallow."
  3. Name the two payoffs of depth (leverage, locality) and who each is for.
  4. How does this skill use CONTEXT.md and ADRs — and how does it write back to them?

If you can answer these, you've completed the conceptual tour of the spec-driven spine.
