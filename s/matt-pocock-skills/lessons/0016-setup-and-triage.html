Setup & Triage

The run-once precondition, and the on-ramp that processes raw issues.

Two skills sit at the boundary of the issue tracker: one configures it, one processes what lands in it.

/setup-matt-pocock-skills — the run-once precondition

Run it once per repo, before any other engineering skill. It writes config — it doesn't hard-code behaviour. Three decisions, each with a recommended answer you can accept in a word:

  • Issue tracker — where issues live (GitHub, GitLab, local .scratch/ markdown, or other). It proposes the one matching your git remote.
  • Triage labels — only asked if triage is installed. Keep the defaults (needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix) unless your tracker already uses other strings.
  • Domain docs — single-context (one CONTEXT.md + docs/adr/ at root) fits almost every repo; multi-context only when it spots monorepo signals.

Output: files under docs/agents/ (issue-tracker.md, domain.md, triage-labels.md if triage is installed) + an ## Agent skills block in your CLAUDE.md or AGENTS.md. If triage/to-spec/to-tickets start guessing where your issues live, you skipped this.

/triage — process raw incoming issues

An on-ramp to the main flow. When bug reports and feature requests pile up, triage moves them through a small state machine of roles and leaves an agent-ready brief.

Two roles per item, never zero or two

Every triaged item carries exactly one category role (bug / enhancement) and one state role (needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix). It recommends and waits — tells you its call with reasoning, acts only on your direction.

Verify before you brief

The step that separates triage from ad-hoc labelling. It reproduces the bug from the reporter's steps, or checks out the PR and runs the tests. Confirmed with a code path → strong brief; failed or insufficient detail → needs-info. It also runs two codebase checks: redundancy (already implemented → wontfix) and prior rejection (.out-of-scope/ already says no).

A PR is an issue with attached code

Where the tracker treats external PRs as a request surface, triage runs them through the same machine — states just read against the diff. ready-for-agent = a brief is attached, agent takes the next step; ready-for-human = ready to merge.

When NOT to triage Triage is only for issues you didn't create — raw bug reports, incoming feature requests. Tickets that /to-tickets produced are already agent-ready, so don't triage them. Triaging your own tickets is wasted work.
