Prototype & Research

Two standalone tools that answer a question fast and feed the main flow.

Two standalone tools that answer a question fast and feed the result back into the main flow.

/prototype — throwaway from day one

A small, disposable program whose only job is to answer one design question: does this state model feel right, or what should this UI look like.

It carries no tests, no error handling beyond what makes it run, no abstractions, no persistence. The point is to learn something fast and then delete it. The moment you start hardening it, you've stopped prototyping.

Two branches — pick first, build second

Picking the wrong branch wastes the whole prototype, so the question comes first:

QuestionShape
"Does this logic / state model feel right?"A single shareable HTML file — free-play buttons plus tabbed guided walkthroughs — that pushes the state machine through the awkward cases, drivable by a non-developer.
"What should this look like?"Several radically different UI variations on one route, switchable from a floating bar, so you compare real renders instead of imagining them.

Both branches keep state in memory, run from one command, and surface the full state on every step.

Keep the prototype as a primary source

The answer — verdict plus the question it settled — is what you capture durably (a commit message, an ADR, an issue). The prototype itself is a primary source — the runnable evidence the answer came from.

Where it lives It does not belong in the main branch: no tests, nothing to maintain. But don't destroy it. Capture it on a throwaway branch — out of main, never merged — and leave a context pointer to it on the implementation issue. Main stays clean; the raw exploration stays one click away.

Not for: if something already built is misbehaving and you need to find out why, use /diagnosing-bugs. Prototyping explores what to build, not why the built thing is broken.

/research — delegated legwork

Answers a question by reading the sources that own the answer and leaving a cited Markdown file behind. It works only from primary sources — official docs, source code, specs, first-party APIs — never a secondary write-up of them, so what it saves is traceable back to something authoritative.

The defining move: background agent

The reading runs as a background agent. You keep working; it goes off, follows each claim back to its primary source, and drops a single cited Markdown file into wherever the repo keeps such notes. Research is legwork you delegate, not thinking you outsource — you get back a document to react to, with sources attached.

Feeds the thinking, doesn't replace it The file research produces is something to take into the main flow at /grill-with-docs — research feeds the thinking, it doesn't replace it.

Not for: for sharpening a plan by interview instead of by reading, use /grilling; for exploring what to build with throwaway code, use /prototype.
