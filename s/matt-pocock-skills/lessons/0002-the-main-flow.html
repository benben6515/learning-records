The Main Flow: idea → ship

The backbone route most work travels. Memorize it.

Most work travels one route. Memorize it — it's the backbone of the whole set.

grill-with-docs → to-spec → to-tickets → implement → code-review → retro

Walk-through

  1. /grill-with-docs — interview you relentlessly, round by round, until the idea is sharp. Stateful: writes resolved terms to GLOSSARY.md and hard decisions to ADRs as it goes. No codebase? Use /grill-me — same interview, stateless.
  2. Prototype branch. If a question needs a runnable answer (state model, UI you must see), detour: /handoff out → fresh session → /prototype → /handoff back → reference from the original thread.
  3. Size branch.
    • Multi-session → /to-spec (synthesize the thread into a spec — no re-interviewing), then /to-tickets (split into tracer-bullet tickets, each declaring its blocking edges), then work the tickets one of two ways:
      • /implement per ticket, /clearing between each — you drive.
      • /implement-spec for the whole spec in one run — it reads the tickets as a task graph, runs implementer subagents in parallel across the ready frontier, and lands everything on one integration branch.
    • One session → /implement right here.
    Either way, the code is built by driving /tdd internally (red-green slice at a time), then closed out with /code-review (Standards + Spec, parallel sub-agents). When the work goes up as a pull request, /pr shapes the body: the smallest visual that shows the change, before/after evidence that it works, and a one-way or two-way door call.
  4. /retro — close the loop. After a build — especially one that went sideways — look back over the session and suggest changes to the agent's environment, not the code: navigation pointers, automated checks, coding standards, steering files, tooling. Mechanical mistakes become deterministic checks; judgement calls become coding standards, so the next build starts from a better environment. Run it in the session it's looking back on, before you clear.
The single discipline Keep steps 1–3 in one unbroken context window. Don't compact or clear until after /to-tickets — the grilling, spec, and tickets must build on the same thinking. Each /implement then starts fresh, working from the ticket.

The smart-zone limit

The window within which the model still reasons sharply is ~150k tokens — the smart zone. If a session approaches it before /to-tickets, don't push on degraded: /compact at the nearest phase boundary (never mid-phase) and carry on.

That's the whole flow. On-ramps (triage, diagnosing-bugs, wayfinder) and standalone tools (prototype, research) attach to it — coming in later lessons.
