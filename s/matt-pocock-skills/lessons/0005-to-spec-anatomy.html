to-spec — The Spec Anatomy

It freezes the conversation. It does not interview.

You've now got the two artefacts a spec is built on — the glossary and ADRs. to-spec is where they come together: it takes the conversation you already had in grill-with-docs and freezes it into a fixed-shape spec (a PRD) that implement can build from. The whole skill lives in one contrast:

The one idea

grill-with-docs
Interviews. One question at a time. Decisions are yours. Builds the glossary + ADRs.
to-spec
Synthesizes. Zero questions. Just writes what you already settled. Freezes it into a spec.
same conversation · opposite jobs
If to-spec starts asking you questions, something went wrong upstream — you skipped or under-cooked the grilling. Stop and grill; don't fake a decision into the spec.

The anatomy (fixed shape)

Every spec has the same sections. You don't invent the structure — you fill it:

  • Problem Statement & Solution — both from the user's perspective, in glossary vocabulary.
  • User Stories — a long numbered list: "As an <actor>, I want <feature>, so that <benefit>." Cover all aspects.
  • Implementation Decisions — modules, interfaces, schema, API contracts. No file paths or code snippets (they rot).
  • Testing Decisions — external behaviour only, not internals; which modules; prior art.
  • Out of Scope & Further Notes.

The test-seam rule — the counterintuitive one

Before writing, to-spec sketches the seams at which the feature will be tested. A seam is a testing insertion point. The rule that surprises people:

The seam rule Prefer existing seams over new ones. Use the highest (most external) seam possible. The fewer seams, the better — the ideal number is one.

Why "fewer is better" when instinct screams "more tests = safer"? Because each seam is a coupling point. Testing a feature through one high boundary (say, the full request→response flow, or the rendered UI) gives you confidence with minimal brittleness. Five unit tests pinned to internal functions break every time you refactor — and "the interface is the test surface." One high seam > many low ones.

Your tangible win — spot the broken rule

Each snippet breaks one of the three rules. Name which.

  1. The spec opens: "Before I write this up — what should happen when the bitmask overflows?"
  2. An Implementation Decision reads: "Modify parsePermissionBits() in src/utils/permissions.js to return the bit positions."
  3. A Testing Decision reads: "Unit-test the internal bitPositions() helper in isolation."

Answers: #1 breaks synthesize-don't-interview (it's a question → that's grilling's job). #2 breaks no file paths/code. #3 breaks the seam rule — it's testing a low internal function instead of external behaviour through one high seam. Reason through them in the reference.

Where this sits in the flow

grill-with-docs → to-spec → issue · ready-for-agent → implement

to-spec publishes the spec with the ready-for-agent label — no extra triage (Lesson 1: don't triage your own output). From here, a multi-session build runs to-tickets first; a single-session build goes straight to implement.
