Resolving Merge Conflicts

Resolve by intent, never by text — and never abort.

A reach-for-it-anytime standalone for the moment a merge or rebase stalls. /resolving-merge-conflicts works through the conflict hunk by hunk and finishes the operation — resolved, checked, committed.

Resolve by intent, not by text

The trap in a conflict is treating it as a text problem — picking "ours" or "theirs" to make the markers go away. This skill treats it as an intent problem.

The rule Each side of a hunk exists because someone wanted something. The resolution has to honour both wants where it can, and where they're genuinely incompatible, pick the one that matches the merge's stated goal and note the trade-off out loud. It never invents new behaviour to paper over a clash.

Primary sources first

You can't preserve an intent you haven't read, so the work starts in the history — not in the diff. Before touching a hunk, trace each side back to its primary source: the commit message, the PR, the original issue. Understand why the change was made, then preserve both intents where they're compatible.

Never --abort

The merge always gets finished. --abort is never reached for. Resolving is the point — the skill hands you back a clean, committed tree.

It's working if

  • Each resolved hunk keeps both sides' behaviour, or names the trade-off where it couldn't.
  • No new behaviour appears that wasn't on either branch.
  • The project's own checks — typecheck, tests, format — are found and run green before the commit.
  • The merge or rebase is carried all the way to a finished commit, never aborted.

Where it fits

Natural neighbour is /diagnosing-bugs: a merge that resolves cleanly but misbehaves afterwards is a diagnosis problem, not a conflict one. resolving-merge-conflicts is for the conflict in front of you — not for planning the merge or debugging behaviour that broke afterwards.
