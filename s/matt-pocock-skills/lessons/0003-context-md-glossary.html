CONTEXT.md — The Glossary

Four rules. One load-bearing sentence. The thing every later skill reads first.

In Lesson 2 you saw that grill-with-docs writes a glossary as it interviews you. Now: what is that glossary, and what makes a good one? This is the artefact your whole spec-driven flow depends on — to-spec uses its vocabulary, implement reads it before building, improve-codebase-architecture names modules with it. Get the rules wrong and every downstream skill drifts.

The one idea

CONTEXT.md is a glossary and nothing else. Not a spec, not a scratchpad, not a decision log.

That single sentence is the whole lesson. Everything else is consequence. The most common way people break it: they start stuffing implementation into it — file paths, class names, "how it works." The moment you do, it stops being a glossary and becomes a stale, half-code, half-prose mess that nobody trusts.

The four rules

  1. Be opinionated. When several words name one concept, pick the best one and banish the rest to _Avoid_:. Don't list synonyms as equals — choose.
  2. Keep it tight. One or two sentences. Define what it is, not what it does.
  3. Project-specific only. General programming concepts (timeouts, error types) don't belong, even if the project uses them everywhere. Ask: is this unique to my domain?
  4. Devoid of implementation. No paths, no classes, no tech. Decisions and behaviours go in specs and ADRs — not here.

Here's a good entry, straight from the skill's own example:

Good Customer — A person or organization that places orders. Avoid: Client, buyer, account.

It's written inline, not batched

The glossary isn't a document you sit down to write at the end. domain-modeling maintains it as terms resolve, usually mid-interview: when you and the agent settle what "Customer" means, it gets written right then. And it's created lazily — no empty scaffold; the file appears when the first term crystallises. (This is exactly why your project doesn't have one yet — no term has been forced to resolve. The first grill-with-docs you run will birth it.)

Your tangible win — spot the broken rule

For each entry, name which rule(s) it breaks. (Answers in the reference doc's anti-patterns section — check after.)

  1. OrderService — A class in src/services/ handling order creation; uses PostgreSQL.
  2. Timeout — The maximum time to wait before failing a request.
  3. Account — Used for various things like logins and billing.

If you can name the rule each one violates, you've internalised the discipline — and you'll write a clean glossary on your first real grill-with-docs.
