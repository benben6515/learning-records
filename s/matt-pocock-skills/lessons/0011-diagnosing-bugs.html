Diagnosing Bugs: The Tight Loop

The tight-loop discipline for bugs that resist a first glance.

The hard-bug version of the feedback loop. /diagnosing-bugs runs a disciplined diagnosis loop for the bugs that resist a first glance — the intermittent flake, the regression that crept in between two known-good states.

The tight loop is the skill

Everything else — bisection, hypothesis-testing, instrumentation — is mechanical once you have the signal. So diagnosing-bugs spends disproportionate effort on Phase 1: constructing a pass/fail command that drives the actual bug code path and asserts the user's exact symptom, then tightening it until it's fast, deterministic, and agent-runnable.

The refusal It refuses to hypothesise before you have a tight feedback loop — one runnable command that already goes red on this bug. Reading code to build a theory before that command exists is the exact failure this skill prevents. No red-capable loop, no diagnosis.

A 30-second flaky loop is barely better than none; a 2-second deterministic one is a debugging superpower.

The ladder of loops

It gives you a ladder of ways to build that loop, in rough order of preference:

  • Failing test
  • curl script
  • CLI diff
  • Headless browser
  • Replayed trace
  • Throwaway harness
  • Fuzz loop
  • git bisect run
  • Differential run
  • Human-in-the-loop bash script — only as a last resort

Non-deterministic bugs

For flakes, the goal isn't a clean repro but a higher reproduction rate: loop the trigger, parallelise, add stress until the flake is debuggable.

It's working if

  • It builds and runs a repro command before theorising — and pastes the invocation and its red output.
  • The loop asserts the symptom you actually reported, not a nearby failure.
  • Hypotheses arrive as a ranked, falsifiable list shown to you before any are tested.
  • Debug instrumentation is tagged ([DEBUG-...]) and grepped away before it declares done.

Where it hands off

A reach-for-it-anytime standalone — drop in when something's broken, drop out once the fix and its regression test are in. Its post-mortem hands off to /improve-codebase-architecture when the real finding is that there's no good seam to lock the bug down — the code, not the bug, is the problem.

Ask your teacher Stuck or curious? Ask a follow-up question — anything unclear is fair game.
