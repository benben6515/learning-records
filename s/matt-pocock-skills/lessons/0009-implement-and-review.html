Implement & Code Review

The last two steps: implement builds, code-review judges on two axes.

The last two steps of the main flow: /implement builds, /code-review judges. They close the loop.

/implement — the hands, not the head

It builds the work described by a spec or set of tickets — driving it through /tdd, typechecking, and the full test suite, then handing to review and committing to the current branch.

It does not decide what to build The spec is already settled and the seams are already agreed. implement executes that plan rather than reopening it. The thinking happened upstream — in grill-with-docs and to-spec. If the spec doesn't exist yet, write it first.

Pre-agreed seams

The idea implement runs on is the seam — the stable interface a feature is tested at, chosen before any code is written (during to-spec). It doesn't invent seams mid-build; it uses the ones already picked and writes tests against them via tdd. Working at pre-agreed seams is what keeps the implementation honest: tests target something durable, so the code underneath can move without the tests moving.

Around that core it keeps the loop tight — typecheck often, run single test files as it goes, run the whole suite once at the end — then closes out with a review pass and a commit.

/code-review — two axes, never merged

Reviews the diff between HEAD and a fixed point you supply (commit, branch, tag, merge-base) along two separate axes, run as parallel sub-agents so neither pollutes the other's context:

AxisQuestionSource
StandardsIs it built right? Does it follow how this repo writes code?CODING_STANDARDS.md / CONTRIBUTING.md + a fixed baseline of ~12 Fowler code smells (Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, …)
SpecIs it the right thing? Does it do what the issue/spec asked?The originating issue or spec (issue-tracker wiring from setup)
Why never merged A change can pass one axis and fail the other. A single blended verdict lets one mask the other. So the report presents them under separate ## Standards and ## Spec headings with a per-axis summary. There is deliberately no single winner across axes.

Two rules keep the Standards baseline safe

  • A documented repo standard always overrides the Fowler baseline.
  • Every smell is a judgement call, never a hard violation.

No spec → Spec axis skips

The Spec axis needs somewhere to find the originating spec — an issue reference in the commit messages, a path you pass in, or a spec under docs//specs/. Without one, it reports "no spec available" instead of inventing requirements. The Standards axis needs nothing set up — it always carries the built-in Fowler smell baseline.
