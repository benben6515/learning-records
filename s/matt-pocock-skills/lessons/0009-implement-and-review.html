Implement, Review & Close Out

implement builds (one ticket at a time, or the whole spec in one run); code-review judges; pr shapes the PR; retro closes the loop.

The build-and-close stretch of the main flow: /implement or /implement-spec builds, /code-review judges, /pr shapes the pull request, /retro closes the loop.

/implement — the hands, not the head

It builds the work described by a spec or set of tickets — driving it through /tdd, typechecking, and the full test suite, then handing to review and committing to the current branch.

It does not decide what to build The spec is already settled and the seams are already agreed. implement executes that plan rather than reopening it. The thinking happened upstream — in grill-with-docs and to-spec. If the spec doesn't exist yet, write it first.

Pre-agreed seams

The idea implement runs on is the seam — the stable interface a feature is tested at, chosen before any code is written (during to-spec). It doesn't invent seams mid-build; it uses the ones already picked and writes tests against them via tdd. Working at pre-agreed seams is what keeps the implementation honest: tests target something durable, so the code underneath can move without the tests moving.

Around that core it keeps the loop tight — typecheck often, run single test files as it goes, run the whole suite once at the end — then closes out with a review pass and a commit.

/implement-spec — the whole spec in one run

The parallel alternative to driving each ticket yourself. You ran /to-spec then /to-tickets; now instead of /implement-ing ticket by ticket, /implement-spec (user-invoked) implements the whole spec in one run:

  • It reads the tickets not as a list but as a task graph — the blocking edges define a ready frontier of tickets that can start now.
  • It fires implementer subagents in their own worktrees across that frontier, in parallel, each building its ticket with tdd. As one merges, newly-unblocked tickets spawn fresh subagents.
  • Everything lands on one integration branch; a draft PR opens only when the tracker closes work through PRs (or you ask), after the first merge. Otherwise the tickets are resolved the way the tracker closes work.
  • It closes out with one /code-review over the integration branch, and fixes what review raises in a single implementer subagent.
Which one? Want to stay in the loop and judge each slice yourself? /implement per ticket, fresh context each time. Would rather orchestrate the build and let concurrency do the waiting? /implement-spec. Same tickets, same seams — the choice is only who drives.

/code-review — two axes, never merged

Reviews the diff between HEAD and a fixed point you supply (commit, branch, tag, merge-base) along two separate axes, run as parallel sub-agents so neither pollutes the other's context:

AxisQuestionSource
StandardsIs it built right? Does it follow how this repo writes code?CODING_STANDARDS.md / CONTRIBUTING.md + a fixed baseline of ~12 Fowler code smells (Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, …)
SpecIs it the right thing? Does it do what the issue/spec asked?The originating issue or spec (issue-tracker wiring from setup)
Why never merged A change can pass one axis and fail the other. A single blended verdict lets one mask the other. So the report presents them under separate ## Standards and ## Spec headings with a per-axis summary. There is deliberately no single winner across axes.

Two rules keep the Standards baseline safe

  • A documented repo standard always overrides the Fowler baseline.
  • Every smell is a judgement call, never a hard violation.

No spec → Spec axis skips

The Spec axis needs somewhere to find the originating spec — an issue reference in the commit messages, a path you pass in, or a spec under docs//specs/. Without one, it reports "no spec available" instead of inventing requirements. The Standards axis needs nothing set up — it always carries the built-in Fowler smell baseline.

/pr — the shape of a pull request body

Model-invoked: when the work goes up as a PR, the agent reaches for it. The body has three fixed parts:

  • Summary — the smallest visual that makes the change clear: a diagram, a diff sketch, a call tree, a file tree — whatever shows the shape in one glance.
  • Evidence — before/after: the failing run or screenshot, then the passing one. Proof it works, not a claim that it does.
  • Merge Danger — a one-way or two-way door call, plus a one-word blast radius. Is this reversible after merge, and what does it touch?

/retro — the last step of the main flow

User-invoked; run it in the session it's looking back on, before you clear (after clearing, point it at that session's log). It looks back over the coding session and suggests changes to the agent's environment, not the code:

  • Navigation pointers — the agent took too long to find something; leave a pointer.
  • Automated checks — a mistake an automated check could have caught becomes a linter rule, pre-commit hook, or CI job. A repo with no guardrail at all is itself a finding.
  • Coding standards — a mechanical violation becomes a deterministic check, never a prose rule; CODING_STANDARDS.md is reserved for genuine judgement calls the reviewer agent enforces.
  • Steering files, tool economy, information access — no-op instructions pruned, expensive tool calls streamlined, missing information teed up.
Mechanical mistakes become deterministic checks. Judgement calls become coding standards. The next build starts from a better environment.
