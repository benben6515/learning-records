TDD: Red-Green, One Slice

Red-green, one vertical slice at a time — the loop that gives the agent eyes.

The fix for failure mode #3 (the code doesn't work). Without a feedback loop telling the agent what its code actually does, it flies blind. /tdd gives it eyes.

The leading idea: red-green, one slice at a time

  1. Write one failing test (red).
  2. Add just enough code to pass it (green).
  3. Repeat for the next behaviour — each cycle informed by what the last one taught you.

Refactor only once the suite is green; never while red.

Why one at a time, not batched Batching the tests first ("horizontal slicing") produces tests of imagined behaviour — they check the shape of things and go numb to real changes. tdd takes vertical slices: one test, then just enough code, then the next. Because you just wrote the code, you know exactly which behaviour matters and how to verify it — you never outrun your headlights.

The tracer bullet

The very first cycle is a tracer bullet: one test that proves a single path works end-to-end, before you build outward from it. A thin vertical slice through every layer (schema, API, UI, tests) — demoable on its own.

Two rules that keep tests honest

  1. Tests read like a specification — "user can checkout with valid cart" — and exercise real code paths through the public API. Renaming an internal function never breaks a test. Tests target the seam, chosen before any code is written.
  2. Expected values come from an independent source of truth — a known-good literal, a worked example, the spec — never recomputed the way the code computes them. That recomputation is how a tautological test passes by construction and tells you nothing.

Where it sits

tdd is the engine inside /implement, not a step of its own. implement drives it to build each ticket test-first, then hands to /code-review. You can also reach for tdd directly when there's a concrete behaviour to build without a full spec. Its neighbour is /codebase-design, which it leans on to place a seam before writing the test.

If the behaviour isn't pinned down yet, settle the spec first — for that, use /to-spec.
