The Six Primitives (+ Memory): the loop's part list

Take the loop apart into six parts — each one patches a hole that would otherwise break it.

Last lesson you saw the whole-picture table: a loop is not one long prompt but a small system of six parts. This lesson unpacks them one by one. The read is simple — each primitive maps to a hole that, left unplugged, breaks the loop right there. Learn the parts and the holes they patch; later lessons (maker/checker, state, skills) go deep on each.

Six primitives, six holes. Learning them is learning where a loop fails.

1. Scheduling — the loop's heartbeat

Without scheduling, you ran an agent once — that's not a loop. Scheduling turns "one run" into "runs that recur over time," so it's the heartbeat. Forms vary: /loop (Grok), scheduled tasks / cron in Claude Code, GitHub Actions, /goal (run until a verifiable condition is true). Properties to mind: interval, fire-immediately, recurring vs one-shot, durable (survives restarts).

The hole it patches No heartbeat → no "orchestration over time" → it collapses back into a one-off run.

2. Worktree — parallelism without chaos

Two agents editing the same files at once is merge hell. A git worktree gives each agent its own working directory — shared history, but not a shared working tree. Cleanup matters: when the task is done or handed off, delete the worktree. CLIs like loop-worktree make it mechanical: one worktree per attempt, tracked in a manifest, swept on reject or escalation.

The hole it patches Parallel agents collide on files → give each an isolated checkout; parallel without chaos.

3. Skills — the memory of intent

Every session is a cold start; intent you didn't write down gets filled in by the agent's "confident guesses" — that's intent debt. A skill is the unit that pays it down: usually a SKILL.md encoding project conventions, build/test/lint commands, review standards, domain knowledge, and "we don't do it this way because of X incident." Without skills the loop re-derives everything from scratch each run. A skill is also the unit of reuse — package it as a plugin to share across repos or teams.

The hole it patches Cold start + missing intent confidently guessed wrong → write intent down outside, read it every run, pay down the debt.

4. Connectors (MCP) — from commentator to operator

A loop that can only read the filesystem is at best a commentator. Connectors turn it into an operator: read and update Linear / Jira tickets, post to Slack / Discord, query databases or internal APIs, open branches and PRs on GitHub, trigger deploys. MCP (Model Context Protocol) has become the common substrate, so a connector written for one tool often works in another.

The hole it patches The loop can "talk" but not "act" → wire it to real tools so it can move the world.

5. Sub-agent (maker/checker) — the writer doesn't grade its own work

This is the single most important structural pattern for reliable loops. The agent that wrote the code is a terrible judge of its own work. A second agent (sometimes a stronger model, always different instructions) performs verification. Common splits: Explorer → Implementer → Verifier; Implementer → Security reviewer; Implementer → Test writer + runner. In an unattended loop, that verifier is exactly what lets you (the human) walk away with some confidence. /goal uses the same trick: a different model decides whether the stopping condition has been met.

The hole it patches The implementer grades its own homework → split off a verifier; that's structural, not a model-strength problem.

6. State (memory) — the spine of progress

The model has no long-term memory across sessions. The loop must read from and write to something durable: a STATE.md / LOOP-STATE.json in the repo, a section of a Linear board, a GitHub Project, or a database row. Good state answers three questions: what are we working on now? what did we try last time and what was the outcome? what's waiting for a human? This state file is often the single most important artifact the loop produces.

The hole it patches The model forgets → put progress on disk; sessions can chain together.

Two kinds of memory — don't confuse them

Two of the parts above both look like "memory," and they remember different things:

RemembersAnswers
Skillsmemory of intentwhat we want, how we do it, what we never do
Statememory of progresswhere we are, what we tried, where we're stuck

Together they give the loop a past it can recall and a standard it won't forget. This is why the course says "six primitives (+ Memory)" — the State row is that +Memory.

How they fit: the growth path

You don't need all of them at once. A minimal viable loop starts with the three smallest things; the rest get added only after the previous version has proven its value — and its failure modes:

Minimal viable loop
Scheduling+ triage skill+ state file
Start making changes →
＋ Worktree
Running autonomously →
＋ Sub-agent verification (maker/checker)
Driving tickets / PRs →
＋ Connectors (MCP)
The best loops are grown, not built in one shot — each new part is added only after you've watched the previous version break.

One sentence to take away

Rather than memorize six parts, memorize the six holes they patch: no heartbeat, parallel collisions, guessed intent, can only talk, self-graded work, forgotten the moment you look away. A loop's reliability is exactly the result of plugging those holes one by one. The next three lessons go deep on the three most critical holes — starting with maker/checker.

Ask your teacher Map the six parts onto your own tools, e.g.: "I use opencode — which of these six do I already have, which don't I?" "Are skills the same thing as the AGENTS.md I use now?" "Where do I start with worktrees?" "Which hole is the most dangerous one my loop is missing?" Anything unclear is fair game.
