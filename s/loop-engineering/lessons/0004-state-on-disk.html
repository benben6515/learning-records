State on Disk: the model forgets, the repo doesn't

The second pillar of loop reliability — why durable, cross-session memory must live on disk.

Last lesson was the first pillar (maker/checker). This one is the second: state on disk. The source says the state file is "often the single most important artifact the loop produces." Why would a memory file matter more than the code the loop ships? Because without it, every run starts from zero and nothing chains together.

The model has no long-term memory across sessions — it forgets every time. Write progress to disk and the loop gets a spine.

The problem: every run is a cold start

The model's memory only lasts within a session. Close the session and it remembers nothing. If the loop keeps "where we are, what we tried" only in the model's head, the next run has amnesia — the design checklist flags this directly: no state file means the loop has amnesia every run. So state must live in a durable thing outside the model.

Good state answers three questions

State isn't "write everything down" — it precisely answers three questions:

QuestionAnswer
What are we working on now?The current work item
What did we try last time, and what was the outcome?Attempts and their results (avoid re-hitting the same wall)
What's waiting for a human?Items needing a person, and why

Forms and discipline

Forms vary: a STATE.md / LOOP-STATE.json in the repo, a section of a Linear board, a GitHub Project, or a database row. What matters isn't the form — it's the discipline the loop follows every run:

  • Read: start every run by reading prior state.
  • Write: write back outcomes, timestamps, last actions.
  • Prune: clear resolved / merged / closed items every run.
  • Record human overrides: decisions you changed stay in state.

Separately, a run log (loop-run-log.md) is append-only, recording facts per run — "a loop that ran but didn't log is a loop you can't debug."

How it runs: one pass

Read STATE→ Run triage / act→ Write STATE
Prune closed items→ Append run log
Read → do → write back → prune. The next run picks up where this one left off because of this cycle.

The two memories, one more time

The distinction planted in Lesson 02 closes here:

RemembersAnswers
Skillsmemory of intentwhat we want, how we do it, what we never do (next lesson)
Statememory of progresswhere we are, what we tried, where we're stuck (this lesson)

You need both: without skills the loop doesn't know "how to do it"; without state it doesn't know "where we are."

Its weight in the score

The Loop Ready score (loop-audit) gives the state file 14 points — tied with the verifier as the single highest-weighted signal. And L3 (unattended) is mechanically blocked until three cost signals exist: loop-budget.md, loop-run-log.md, and a budget section in LOOP.md. In other words, even "can you let go" depends on whether your state is written well enough.

Why start at L1 report-only Part of why "Daily Triage at L1, report only" is the recommended first loop is that it teaches you state discipline without auto-merge risk. Build the read/write/prune muscle first; acting comes later.

One sentence to take away

The model forgets; the repo doesn't. State on disk is the spine that chains amnesiac sessions into one continuous thread of work. The next lesson covers the other memory — skills, writing intent on the outside.

Ask your teacher Think about your own work: "Do I have any mechanism today that remembers 'where I got to' across sessions?" "How is STATE.md different from the notes/TODOs I keep?" "If my loop could add only one primitive, why is it state?" Anything unclear is fair game.
