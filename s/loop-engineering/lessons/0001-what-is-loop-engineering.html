What is Loop Engineering: stop prompting

From prompting agents turn-by-turn to designing the system that drives them.

Here's probably how you use agents today: you type a thing, read the reply, type the next thing, holding it the whole time. Boris Cherny (head of Claude Code at Anthropic) says he doesn't do that anymore — "I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops." This course turns that sentence into a model you can use.

Loop engineering = replacing yourself as the person who prompts the agent. You design the system that does it instead. — Cobus Greyling / Addy Osmani

One idea: a loop is a "recursive goal"

Think of a loop as a recursive goal: you define a purpose, and the agent iterates with sub-agents and external memory, until it's done, or until it hands the work back to you. The point is you design it once — you don't keep prompting the steps. The system discovers work, assigns it, verifies results, persists state, and decides the next action.

This is a different layer than "writing a prompt." A year ago, building a loop meant maintaining a pile of bash scripts yourself; now these pieces ship inside the tools (Claude Code, Codex, Grok, opencode), so the "shape" of a loop is becoming tool-agnostic — the loop you design isn't nailed to one tool.

The key distinction: Harness vs Loop

To understand loops, first separate them from "harnesses" — a common point of confusion:

ConceptWhat it isProblem it solves
HarnessThe environment for one agent, one session: tools, context, permissions, rulesMaking "this one run" go well
Loopharness + scheduling + state + a verification chainOrchestrating those runs over time

One line: the harness is the sandbox for a single session; the loop is the system that schedules and orchestrates harness runs. The loop sits one floor above the harness — it runs on a timer, spawns little helpers, and feeds itself.

The whole picture: six primitives (+ Memory)

A loop that runs unattended is not one long prompt — it's a small system of six parts. Meet the whole picture first; later lessons go deep on each one:

PrimitiveJob in the loop
Scheduling / automationsThe heartbeat. No schedule = a one-off run. Forms: /loop, cron, GitHub Actions, /goal.
WorktreeAn isolated git checkout so parallel agents don't collide on files.
SkillsPersistent memory of intent (SKILL.md): conventions, build, and "we don't do it this way."
Connectors (MCP)Let the loop act on real tools: open PRs, update tickets, post to Slack.
Sub-agent (maker/checker)One writes, another verifies. The implementer never grades its own homework.
+ State (memory)The durable spine across sessions (STATE.md). The model forgets; the repo doesn't.

A minimal viable loop usually starts with scheduling + one triage skill + a state file, then adds primitives one at a time as each proves its value.

The most important line: the loop doesn't delete you

The loop changes the work; it doesn't delete you from it. And three problems actually get sharper as the loop gets better, not easier:

  1. Verification is still on you. A loop running unattended is also making mistakes unattended. "Done" is a claim, not a proof — you still read what landed in the repo.
  2. Comprehension debt grows faster. The faster the loop ships code you didn't write, the wider the gap between what exists and what you actually understand.
  3. The comfortable trap of cognitive surrender. Letting the loop run while you stop having opinions is comfortable, and dangerous.
Same loop, opposite outcomes Two people can run the exact same loop and get completely opposite results. One uses it to move faster on work they understand deeply; the other uses it to avoid understanding the work at all. The loop doesn't know the difference. You do. — Addy Osmani: "Build the loop. Stay the engineer."

One sentence to take away

The leverage point has moved from "crafting a single prompt" to "designing the control system that orchestrates agents." Cherny's point isn't that the work got easier — it's that where you push has moved. The next lessons take those six parts one at a time.

Ask your teacher Stuck or curious? For example: "Which of the six primitives should I go deep on first?" "I use opencode — which parts map to which pieces?" "What's the real difference between /goal and /loop?" Anything unclear is fair game.
