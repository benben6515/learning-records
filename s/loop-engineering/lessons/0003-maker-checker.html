Maker / Checker: the writer never grades its own work

The most important pillar of loop reliability — why "the implementer doesn't grade itself" is a structural principle.

Last lesson you met all six primitives. This one goes deep on the fifth — the sub-agent maker/checker split. The source calls it "the single most important structural pattern for reliable loops." Why is one division of labor that weighty? Because it solves the most dangerous question in a loop: who decides "done" and "correct".

The agent that wrote the code is a terrible judge of its own work — not a model-strength problem, a structural fact.

The problem: self-review inherits the same blind spot

Why can't the implementer grade its own homework? Because the blind spot that produced the bug hides that same bug on review. Self-review isn't "slightly unreliable" — it structurally inherits its own assumptions. A stronger model doesn't save you: if you ask the same session to "check again," it looks again with the same assumptions. So the fix isn't "be smarter" — it's a different perspective.

The fix: split off a verifier

A second agent performs verification. It must differ from the implementer — a different model, or at least different instructions. Common splits:

  • Explorer → Implementer → Verifier
  • Implementer → Security reviewer
  • Implementer → Test writer + runner

"Different" can be only in the instructions (same model, different prompt and role), but the safest move is a different model — especially putting a stronger model on the verifier, since it stands in for you when unattended.

The same trick, applied to the stop condition

Maker/checker doesn't only verify code — it can verify "are we done". That's exactly how /goal is designed: it runs until a verifiable condition is true, and a different model decides whether that condition holds. In other words, the implementer claiming "I'm done" doesn't count — the checker has to agree. That's maker/checker applied to the stop condition, not just the code.

How it runs: one pass

Explorer→ Implementer→ Verifier
Verifier passes →
Hand off / open PR
Verifier fails → back to Implementer (max N attempts, then escalate to human)
/goal uses the same trick on the stop condition — a "different" model decides whether "done" holds.

Why this pillar lets you "walk away"

In an unattended (L3) loop, that verifier is exactly what lets you (the human) walk away with some confidence. Without it, "done" is just the implementer's word; with it, there's at least one independent second opinion minding the gate. This is also why the Loop Ready score (loop-audit) gives the presence of a verifier skill 14 points — tied with the state file as the single highest-weighted signal.

Red flags on the checklist Stop and fix before letting the loop run: the verifier is the same session as the implementer, the implementer can mark its own work "done," or the verifier approves without running tests in an isolated worktree.

One sentence to take away

Reliability doesn't come from "a stronger model checking itself" — it comes from separation of duties: one writes, one verifies. This pillar is the precondition for a loop moving from "report" to "unattended." The next lesson covers the other pillar: state on disk.

Ask your teacher Map this onto your own work: "When I use agents today, is there any 'second perspective' minding the gate?" "How do I actually build maker/checker in opencode?" "If verifier and implementer share a model but differ in prompt, does it count?" Anything unclear is fair game.
