Skills: write intent on the outside

Pay down intent debt — write conventions, build, and "we don't do it this way" once, read every run.

The first three lessons covered the parts and the two pillars. This one returns to the third primitive — skills. The source calls it "the persistent memory of intent." Last lesson's state remembers "where we are" (progress); skills remember "what we want, how to do it, what we never do" (intent). Without it the loop re-derives everything from scratch each run — that's intent debt.

Every session is a cold start; intent you didn't write down gets filled by "confident guesses." A skill is the unit that pays the debt.

The problem: how intent debt accrues

Every session is a cold start. The things you have in your head but never wrote down — "we use pnpm not npm," "this field can't be null," "don't touch that file, it bit us once" — the agent doesn't know any of it. It won't stop to ask; it fills the gap with a confident guess. Right is luck; wrong is your cleanup. Every run re-accrues that debt.

The fix: one SKILL.md, written once, read every run

A skill is usually a SKILL.md (optionally with scripts/references) that encodes:

  • Project conventions — which package manager, naming rules, directory layout.
  • build/test/lint commands — exact commands, not "run the tests."
  • Review standards — what counts as "mergeable."
  • Domain knowledge — business rules, data models.
  • "We don't do it this way because of X incident" — the gold.
A skill isn't just instructions — it's scar tissue Entries like "we don't do it this way because of X incident" encode institutional memory (scar tissue) into the skill. They don't teach the agent how to do something; they teach it not to repeat a mistake. This is the most valuable part of a skill — and the hardest to derive from the code alone.

Without skills, the loop re-derives from scratch

The source is blunt: without skills the loop "re-derives everything from scratch on every run." The same conventions, the same build commands, the same "don't step on that landmine" — re-guessed every single run. A skill writes these once and reads them every time, turning repeated guesses into reliable defaults.

The triage skill: most loops' first skill

The minimal viable loop is "scheduling + one triage skill + a state file." The triage skill is the one that "reads the work and decides what to act on," and its output format must be tight — so downstream can parse it. The checklist also reminds: skill descriptions should be "boring and specific" so auto-triggering is accurate.

A skill is also the unit of reuse

A skill doesn't only pay one repo's debt — package it as a plugin and it's shared across repos and teams. A landmine one team hit, once encoded as a skill, never needs to be re-hit by any loop.

Together they give the loop a "standard it won't forget" and a "past it can recall." That completes Phase B (making loops reliable) — the next lesson opens Phase C: autonomy levels.

Map it to your own tools The AGENTS.md you already use is, in essence, "project conventions written on the outside, read every run" — functionally close to a shared skill. The difference: a skill is a structured, triggerable, reusable unit (its own description, output format, packageable). The idea is the same: move intent from "your head" to "disk."

One sentence to take away

A skill writes down "what you thought everyone knew, but only you did." The way to pay down intent debt is plain: write it once, read it every run.

Ask your teacher "In my AGENTS.md today, which entries are conventions and which are 'because we got burned'?" "If I broke it into individual skills, where would I start?" "Why does the triage skill's output format need to be tight?" Anything unclear is fair game.
