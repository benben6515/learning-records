Maker / Checker：實作者不評分自己的作業

讓 loop 可靠最重要的一根支柱——為什麼「寫的人不批改自己」是結構原則。

上一課你認過六個 primitives。這堂課深入第 5 個——sub-agent 的 maker/checker 分工。源文件直接稱它為「讓 loop 可靠最重要的一個結構原則」。為什麼一個分工這麼重要？因為它解的是 loop 裡最危險的一個問題：誰來判斷「做完了」和「做對了」。

寫程式的那個 agent，對自己的程式碼是個差勁的裁判——這不是模型不夠強，是結構性事實。

問題：自我審查會繼承同一個盲點

為什麼實作者不能評分自己的作業？因為產生 bug 的那個盲點，回頭檢查時會把同一個 bug 藏起來。自我審查不是「稍微不可靠」，而是結構性地繼承了自己的錯。換更強的模型也救不了——如果你叫同一個 session「再檢查一遍」，它帶著一樣的假設再看一次。所以關鍵不是「更聰明」，而是換一個視角。

解法：分出一個 verifier

第二個 agent 負責驗證。它必須和實作者不同——換模型、或至少換指令。常見的分工：

  • Explorer → Implementer → Verifier（探索 → 實作 → 驗證）
  • Implementer → Security reviewer（實作 → 安全審查）
  • Implementer → Test writer + runner（實作 → 寫測試並跑）

「不同」可以只差在指令（同一個模型、不同的 prompt 與角色），但最穩的是換模型——尤其是 verifier 用更強的模型，因為它要在 unattended 時替你把關。

同一招，套在「停止條件」上

maker/checker 不只驗程式碼，還能驗「做完沒」。這正是 /goal 的設計：它跑到某個可驗證條件成立才停，而且由另一個模型來判斷那個條件成不成立。換句話說，實作者宣稱「我 done 了」不算數——要 checker 點頭才算。這是把 maker/checker 套用在停止條件上，而不只是套用在程式碼上。

它怎麼跑：一次迴圈

Explorer→ Implementer→ Verifier
Verifier 通過 →
交回給人 / 開 PR
Verifier 不通過 → 退回 Implementer（最多 N 次，超過就升級給人）
/goal 把同一招用在停止條件上——「另一個」模型判斷「done」成不成立。

為什麼這根支柱讓你「敢走開」

在 unattended（L3）的 loop 裡，那個 verifier 正是讓你（人）敢走開的本錢。沒有它，「做完了」只是實作者的一面之詞；有了它，至少有一個獨立的第二意見在把關。這也是為什麼 Loop Ready 評分（loop-audit）給「verifier skill 是否存在」14 分——和 state 檔並列、是所有信號裡最高的單項權重。

設計清單上的紅旗 看到這幾種就停下來修，別讓 loop 繼續跑：verifier 跟 implementer 是同一個 session、實作者能把自己的工作標成「done」、或 verifier 沒在隔離的 worktree 裡跑過測試就放行。

帶走的一句話

可靠不是來自「更強的模型自己檢查自己」，而是來自分工：一個寫、一個驗。這根支柱是 loop 能從「報告」走到「無人看管」的前提——下一課就看另一根支柱：state on disk。

問你的老師 拿你自己的工作對照看看：「我現在用 agent，有沒有任何『另一個視角』在把關？」「opencode 裡要怎麼做出 maker/checker？」「如果 verifier 跟 implementer 用同一個模型但不同 prompt，算不算數？」——任何不清楚的都可以問。
