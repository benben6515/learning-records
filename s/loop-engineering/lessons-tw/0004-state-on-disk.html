State on Disk：模型會忘，repo 不會

讓 loop 可靠的第二根支柱——為什麼跨 session 的持久記憶必須落在磁碟上。

上一課是第一根支柱（maker/checker）。這堂課是第二根：state on disk。源文件說，state 檔「常常是 loop 產出最重要的單一成品」。一個記憶檔為什麼比它產出的程式碼還重要？因為沒有它，loop 每一次跑都從零開始、什麼都接不起來。

模型跨 session 沒有長期記憶——每次都失憶。把進度寫在磁碟上，loop 才有脊椎。

問題：每一次 run 都是冷啟動

模型的記憶只在一個 session 裡有效。session 一關，它什麼都不記得。如果 loop 把「做到哪、試過什麼」只放在模型的腦裡，下一次 run 它就失憶了——設計清單把這條列為紅旗：沒有 state 檔，loop 每次 run 都失憶。所以 state 必須落在模型之外的持久物上。

好的 state 回答三件事

state 不是「把所有東西記下來」，而是精準回答三個問題：

問題回答
我們現在在做什麼？當前的工作項目
上次試了什麼、結果如何？嘗試過的方法與結局（避免重複撞牆）
什麼在等人？需要人類介入的項目與原因

形式與紀律

形式很多種：repo 裡的 STATE.md／LOOP-STATE.json、Linear board 的一段、GitHub Project、或資料庫一列。重點不是用哪種，而是紀律——loop 每次都要做到：

  • 讀：run 一開始先讀上次的 state。
  • 寫：把結果、時間戳、上次動作寫回去。
  • 修剪：每次把已解決／已 merge／已關閉的項目清掉。
  • 記錄人的覆寫：你改過的決定要留在 state 裡。

另外有一個 run log（loop-run-log.md）只追加、不覆蓋，記每次 run 的事實——「一個跑過卻沒記錄的 loop，是你沒辦法 debug 的 loop」。

它怎麼跑：一次迴圈

讀 STATE→ 跑 triage／做事→ 寫 STATE
修剪已關閉項目→ append run log
讀 → 做 → 寫回 → 修剪。下次 run 接得起來，靠的就是這個循環。

兩種記憶，再對照一次

第 02 課種下的區分，在這裡收攏：

記的是回答
Skills「意圖」的記憶我們要什麼、怎麼做、什麼不做（下一課深入）
State「進度」的記憶我們做到哪、試過什麼、卡在哪（本課）

兩者缺一不可：沒有 skills，loop 不知道「該怎麼做」；沒有 state，loop 不知道「做到哪了」。

它在評分裡的份量

Loop Ready 評分（loop-audit）給 state 檔 14 分——跟 verifier 並列、是所有信號裡最高的單項權重。而且 L3（無人看管）會被機械性地擋住，直到三個成本訊號就位：loop-budget.md、loop-run-log.md、以及 LOOP.md 裡的預算段落。換句話說，連「能不能放手」都取決於你的 state 寫得夠不夠。

為什麼先從 L1 report-only 「Daily Triage 在 L1 只報告」之所以是推薦的第一個 loop，部分原因就是它教你把 state 紀律練起來，卻沒有 auto-merge 的風險。先把讀／寫／修剪的肌肉養成，再談動手。

帶走的一句話

模型會忘；repo 不會。state on disk 是把一個個失憶的 session 串成一條連續工作的脊椎。下一課看另一種記憶——skills，把「意圖」寫在外面。

問你的老師 想想你自己的工作：「我現在有任何『跨 session 記得做到哪』的機制嗎？」「STATE.md 跟我用的筆記/TODO 有什麼不一樣？」「如果我的 loop 只能加一個 primitive，為什麼是 state？」——任何不清楚的都可以問。
