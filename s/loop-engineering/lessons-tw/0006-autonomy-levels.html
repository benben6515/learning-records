自主等級 L1 → L2 → L3

先 report-only，再 assisted，最後 unattended——分階上線的邏輯，以及為什麼「絕不跳過 L1」。

Phase B（讓 loop 可靠）講完了零件與兩根支柱。Phase C 談「經營、風險與模式」。這堂課先處理最關鍵的經營問題：loop 該放手到什麼程度？答案是一條分階的階梯——而且它不是單向棘輪，出事時你該往下退。

自主等級不是「越高越好」，而是「證明了才升」。對 production repo 上的新 pattern，絕不跳過 L1。

四個等級，對應不同的檢查表

設計清單把就緒度分成四級，每一級要通過的檢查表段落不同：

等級做什麼要通過
L0 — Draft只有文件上的意圖§1
L1 — Reporttriage → state，不自動動手§1–3、§5
L2 — Assisted有 verifier 的小幅自動修復§1–7
L3 — Unattended沒人盯著跑全部段落

升級路徑：證明了才往下一步

operating-loops 給的升級路徑，每一步都有前提：

L1 只報告→ 穩定 triage 1–2 週
L2 小幅自動修復+ verifier ＋ worktree ＋ 上限次數
L2+ 接 connectors→ 自動更新 PR／ticket
L3 無人看管+ denylist ＋ 預算 ＋ 指標 ＋ 人類 gate
出事就往回退——這不是單向棘輪。

L1 → L2 是影響最深遠的一步

這條階梯上，L1 到 L2 的跨越是影響最深遠的——因為這是 loop 開始動手（act）而不只是報告（report）的轉折。一旦它開始改東西、開 PR，風險性質就變了。所以這一步的前提最硬：要有 verifier、要有 worktree 隔離、要有「最多嘗試幾次」的上限。

為什麼先 report-only

「Daily Triage 在 L1 只報告」是文件給的第一個 loop 建議，理由有二：

  1. 教紀律，沒有風險——它逼你把 state 的讀／寫／修剪練起來，卻沒有 auto-merge 的破壞力。「低風險、極佳的練習對象。」
  2. 先看價值再談動手——report-only 那一週你會看到：過時的 PR、不穩的測試、常態性紅的 main。先證明它「看得準」，再升級去修。
不是單向棘輪 自主等級可以、也應該往下退。發生 production 事件（loop 可能跟 hotfix 打架）、進行中的 schema migration、或關鍵 reviewer 不在卻又開了 auto-merge（別這樣）——這些時候都該退回 report-only。

loop-audit 會機械性地擋住 L3

「能不能放手」不是你自己說了算。loop-audit 會機械性地擋住 L3，直到三個成本訊號就位：loop-budget.md、loop-run-log.md、以及 LOOP.md 裡的預算段落。換句話說，沒把預算與可觀測性準備好，系統就不讓你升到無人看管——這是強制的護欄，不是建議。

帶走的一句話

自主等級是一條「證明了才升、出事就退」的階梯。影響最大的是 L1→L2（loop 開始動手）；而 L3 不是目標，是你在預算、指標、gate 都到位後，才被允許抵達的終點。下一課看這條階梯上會被放大的風險。

問你的老師 「我現在用 agent，大概落在哪一級？」「我想試 L2，前提（verifier、worktree、上限）我缺哪些？」「什麼樣的工作適合一直留在 L1 report-only？」——任何不清楚的都可以問。
